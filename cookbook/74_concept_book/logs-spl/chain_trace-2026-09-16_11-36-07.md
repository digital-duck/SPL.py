## Key

A **key** is the field (or combination of fields) within a stored record that a data structure or algorithm uses to compare, order, and locate elements. It is distinct from the **value** — the payload of information the record carries, which is typically just moved along wherever the key goes but never inspected by the comparison logic itself. When you sort a list of student records by GPA, the GPA is the key; the student's name, ID, and transcript are the value. The comparison predicate — whether it is `<`, `>`, or a custom `compare(a, b)` function — acts exclusively on the key.

This separation matters because it determines *what* an algorithm is allowed to do. A sorting algorithm that compares full records instead of extracting keys first is doing unnecessary work — and if the value is large (an image, a document, a nested object), that waste compounds badly. The standard technique is **key extraction**: given a record $r$, define a function $k(r)$ that maps it to its key, and have every comparison call $k(r_1)$ versus $k(r_2)$ rather than comparing $r_1$ and $r_2$ directly.

**Worked example.** Suppose you have employee records `(id, name, salary)` and want to sort them by salary, highest first. In Python:

```python
employees = [
    (101, "Ana", 72000),
    (102, "Ben", 95000),
    (103, "Cy",  81000),
]
employees.sort(key=lambda r: r[2], reverse=True)
```

Here `key=lambda r: r[2]` is exactly the extraction function $k(r)$: it tells the sort routine to compare salaries, not tuples. Without it, Python would compare `id` first (since tuple comparison is lexicographic), giving the wrong order entirely.

**Problem-solving application.** Keys generalize beyond sorting. In a hash table, the key is what gets hashed to determine bucket placement; the value is stored alongside but plays no role in the hash function. In a binary search tree, every node's key must satisfy the ordering invariant relative to its subtree, while the value is inert cargo. When designing a lookup system — a database index, a cache, a priority queue — the first design question is always: *what is the key?* Choosing it well (unique, cheap to compare, stable) is often the difference between an efficient structure and a subtly broken one, since duplicate or mutable keys can silently corrupt ordering or retrieval guarantees.

### pointer (0.0s)

## Pointer

A pointer is a value whose contents are interpreted as an address — the location of a memory cell rather than data to be used directly. If an ordinary variable is a box holding a number or a character, a pointer is a box holding the *location* of another box. This single idea is the first genuine departure from the array: an array packs elements into contiguous memory in a fixed layout, so its structure is entirely determined by arithmetic on indices. A pointer breaks that constraint. Once a cell can store the address of another cell, memory need not be laid out in one block at all — cells can live anywhere and still be connected, because the connection is data (an address) rather than physical adjacency.

Formally, let memory be modeled as a function $M: \text{Addr} \to \text{Value}$, mapping addresses to the values stored there. A normal variable $x$ at address $a$ satisfies $M(a) = v$ for some value $v$. A pointer variable $p$ at address $b$ satisfies $M(b) = a$, where $a$ is itself an address — so *dereferencing* $p$, written $*p$, means evaluating $M(M(b))$. This two-step lookup — one to fetch the address, one to fetch the value at that address — is the entire mechanism. Nothing else is added.

Consider linking two integers manually. In C:

```c
int x = 42;
int *p = &x;      // p holds the address of x
printf("%d\n", *p); // dereference: prints 42
*p = 99;             // writes through the pointer
printf("%d\n", x);   // prints 99
```

Here `&x` produces the address of `x`, and `*p` reverses that operation.

The problem-solving payoff appears once pointers connect cells that are *not* adjacent in memory. Suppose you need a list that grows and shrinks arbitrarily, with cheap insertion anywhere — something an array cannot do without shifting every subsequent element, an $O(n)$ operation. Define a cell as a pair $(\text{value}, \text{next})$, where $\text{next}$ is a pointer to another cell or a special null address meaning "no cell." Insertion after a given cell becomes a constant-time rewiring of two pointers, regardless of list size, because nothing physically moves. This is the linked list, and it exists only because a memory cell can hold something other than data — it can hold a reference to where the next piece of the structure lives.

### trie (10.8s)

## Trie

A **trie** (from re*trie*val, pronounced "try") is a tree specialized for storing a set of strings so that prefix-based queries are fast. Unlike a binary search tree, where each node holds a whole key, a trie spreads each key across a *path*: every edge is labeled with a single character, and a key is represented not by a node but by the sequence of characters read from the root down to the node marking that key's end. Nodes with a common prefix automatically share the same path down to the point where their characters diverge, so the shared prefix is stored exactly once no matter how many keys extend it.

This structure gives a trie its defining performance guarantee. To insert or search for a key of length $m$, you walk down at most $m$ edges, following the child labeled by each successive character (creating new nodes along the way for an insert if they don't exist). This costs $O(m)$ time — proportional only to the length of the key itself, completely independent of $n$, the number of keys already stored. A balanced BST, by contrast, costs $O(m \log n)$, since each of the $O(\log n)$ comparisons requires comparing full strings.

**Worked example.** Insert "cat", "car", "card", and "dog" into an empty trie. "cat" creates the path root→c→a→t, marking t as an end-of-word node. Inserting "car" reuses the existing c→a path and just adds a new child r. "card" reuses c→a→r and appends d. "dog" starts a fresh path root→d→o→g. The resulting tree has four root-to-marked-node paths, but the letters c, a, and r together are stored only once despite appearing in three different words.

**Problem-solving application.** Tries excel whenever a problem asks "which stored keys share this prefix?" rather than "does this exact key exist?" Autocomplete works by walking down the trie following the characters typed so far — $O(m)$ — then depth-first traversing the subtree rooted there to enumerate every completion. IP routing tables use a binary trie over address bits to find the longest matching prefix for a packet's destination. Dictionary compression exploits the same prefix-sharing to store large word lists in far less space than a flat list would require, since common prefixes like "un-", "re-", or "-ing" are stored once and reused across many entries.

### autocomplete (9.8s)

## Autocomplete

A trie makes autocomplete efficient because the dictionary's structure mirrors the way you type. Each node represents a prefix, and each edge represents the next character. Typing a query of length $m$ walks exactly $m$ edges down from the root, landing on the node that represents everything typed so far. From that node, every word in the dictionary beginning with that prefix lives in the subtree rooted there — no more, no fewer.

This gives autocomplete a clean two-phase cost. First, descend to the prefix node: $O(m)$, one step per keystroke, independent of how large the dictionary is. Second, enumerate the completions by traversing the subtree and collecting every marked end-of-word node: $O(|\text{results}|)$, proportional only to the output size, not to the dictionary size. Total work is $O(m + |\text{results}|)$ — you never pay for words that don't share your prefix.

**Worked example.** Suppose the dictionary contains `car`, `care`, `cart`, `cat`, and `dog`. Typing `ca` walks two edges from the root (`c` → `a`), reaching a node with three words below it: `car`, `care`, `cart`. A depth-first traversal of that subtree, following child pointers and reporting every node flagged as a complete word, yields exactly those three suggestions — `cat` and `dog` are never visited, because they don't branch off the `ca` node.

**Problem-solving application.** Real autocomplete systems add ranking: rather than returning all matches, they return the top $k$ by frequency or recency. A naive approach enumerates the full subtree and sorts, costing $O(|\text{results}| \log |\text{results}|)$. A faster design stores, at each trie node, a small cached list of its most frequent descendant words (updated on insertion), so lookup returns the top $k$ in $O(m + k)$ instead of scanning the whole subtree. This trade-off — a bit more memory and update work per insertion, in exchange for near-constant-time suggestions per keystroke — is the same space-for-time trade you'll see across search engines, IDEs, and mobile keyboards. When designing such a system, always ask: how much of the subtree can I avoid touching by precomputing information at construction time, rather than recomputing it on every query?
