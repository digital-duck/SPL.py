### compare_operation (18.1s)

## Compare Operation

**Definition.** A *compare operation* on a set $S$ is a binary function $\mathrm{cmp}: S \times S \to \{-1, 0, 1\}$ (or equivalently a mapping into an ordered set of signals) that determines the relative ordering of two elements. Formally, for $a, b \in S$ equipped with a total order $\leq$,

$$
\mathrm{cmp}(a, b) =
\begin{cases}
-1 & \text{if } a < b, \\
\phantom{-}0 & \text{if } a = b, \\
\phantom{-}1 & \text{if } a > b.
\end{cases}
$$

The compare operation is the computational primitive underlying sorting, binary search, and decision-tree evaluation. It requires that $\leq$ be a *total order*: reflexive ($a \leq a$), antisymmetric ($a \leq b \wedge b \leq a \Rightarrow a = b$), transitive ($a \leq b \wedge b \leq c \Rightarrow a \leq c$), and total ($a \leq b$ or $b \leq a$ for all $a, b$).

**Worked Example.** Let $S = \mathbb{R}$ and consider $a = 3.7$, $b = 5.2$. Computing $\mathrm{cmp}(3.7,\, 5.2)$: since $3.7 < 5.2$, the result is $-1$. Now consider $a = \pi$, $b = \pi$. Because $a = b$, the result is $0$. Finally, $\mathrm{cmp}(7, 2) = 1$ since $7 > 2$. Notice that $\mathrm{cmp}(a, b) = -\,\mathrm{cmp}(b, a)$ in all three cases, illustrating antisymmetry.

**Key Theorem (Comparison Lower Bound).** Any comparison-based sorting algorithm on $n$ elements requires at least $\lceil \log_2(n!) \rceil$ comparisons in the worst case. By Stirling's approximation, $\log_2(n!) \approx n\log_2 n - n\log_2 e$, so the lower bound is $\Omega(n \log n)$. This follows because each compare operation partitions the remaining permutation space into at most two halves, and the algorithm must distinguish among $n!$ possible orderings; a binary decision tree of depth $d$ has at most $2^d$ leaves, so $2^d \geq n!$ gives $d \geq \log_2(n!)$.

**Lab Cell (SymPy).**

def cmp(x, y):
    xv, yv = float(N(x)), float(N(y))
    return -1 if xv < yv else (0 if xv == yv else 1)

pairs = [(3.7, 5.2), (pi, pi), (7, 2)]
for x, y in pairs:
    print(f"cmp({x}, {y}) = {cmp(x, y)}")
```

### comparison_based_sorting (17.5s)

## Comparison Based Sorting

**Definition.** A *comparison-based sorting algorithm* is any algorithm that determines the sorted order of a sequence solely through pairwise comparisons of elements, using a total order relation $\leq$. Formally, given a sequence $A = (a_1, a_2, \ldots, a_n)$, the algorithm may query $a_i \leq a_j$ for any indices $i, j$, and must produce a permutation $\pi$ such that $a_{\pi(1)} \leq a_{\pi(2)} \leq \cdots \leq a_{\pi(n)}$. No other information about the elements—such as their numerical magnitude or bit representation—may be used.

**Worked Example: Insertion Sort.** Consider $A = (4, 2, 7, 1)$. Insertion sort builds a sorted prefix by inserting each element into its correct position via comparisons.

- Pass 1: Compare $2 < 4$; shift $4$ right. Sorted prefix: $(2, 4, 7, 1)$.
- Pass 2: Compare $7 \geq 4$; no shift. Sorted prefix: $(2, 4, 7, 1)$.
- Pass 3: Compare $1 < 7$, $1 < 4$, $1 < 2$; shift all three right. Sorted prefix: $(1, 2, 4, 7)$.

In the worst case (reverse-sorted input), pass $k$ requires $k$ comparisons, giving $\sum_{k=1}^{n-1} k = \frac{n(n-1)}{2} = O(n^2)$ total comparisons.

**Key Theorem (Information-Theoretic Lower Bound).** *Any comparison-based sorting algorithm requires $\Omega(n \log n)$ comparisons in the worst case.*

*Proof sketch.* There are $n!$ possible permutations of $n$ distinct elements, each corresponding to a distinct sorted order. The algorithm's execution on a given input traces a root-to-leaf path in a binary *decision tree*, where each internal node represents one comparison and each leaf a concluded permutation. A binary tree with $n!$ leaves must have height at least $\lceil \log_2(n!) \rceil$. By Stirling's approximation, $\log_2(n!) = \Theta(n \log n)$, establishing the lower bound. Merge sort and heapsort achieve this bound, making them asymptotically optimal among comparison-based algorithms.

### comparison_tree (17.6s)

## Comparison Tree

**Definition.** A *comparison tree* is a rooted binary tree that models the execution of a comparison-based algorithm on an ordered set. Each internal node is labelled with a comparison $a_i \leq a_j$; the left subtree is followed when the comparison evaluates to true and the right subtree when it evaluates to false. Each leaf is labelled with a distinct outcome—typically a permutation of the input or a search result. For an input of size $n$, the tree has at most $n!$ leaves (when modelling sorting) or $n+1$ leaves (when modelling binary search). The *depth* of a leaf equals the number of comparisons performed along the path from the root to that leaf; the *height* of the tree therefore equals the worst-case comparison count of the algorithm.

**Worked Example.** Consider insertion sort on three distinct elements $\{a, b, c\}$. The algorithm first asks $a \leq b$. If true, it asks $b \leq c$; if that is also true, the sorted order is $a, b, c$ (a leaf at depth 2). If $b \leq c$ is false, it asks $a \leq c$, yielding either $a, c, b$ or $c, a, b$ (leaves at depth 3). The false branch of the root similarly produces three leaves. Altogether the tree has six leaves—one for each of the $3! = 6$ permutations—and height 3, matching the worst-case comparison count of insertion sort for $n = 3$.

**Key Theorem (Information-Theoretic Lower Bound).** *Any comparison-based sorting algorithm requires at least $\lceil \log_2(n!) \rceil$ comparisons in the worst case.*

*Proof sketch.* A binary tree of height $h$ has at most $2^h$ leaves. Since a correct sorting algorithm must distinguish all $n!$ permutations, the tree must have at least $n!$ leaves, giving $2^h \geq n!$, hence $h \geq \log_2(n!)$. Because $h$ is an integer, $h \geq \lceil \log_2(n!) \rceil$. By Stirling's approximation, $\log_2(n!) \approx n\log_2 n - n\log_2 e$, so no comparison sort can beat $\Omega(n \log n)$.

### comparison_sorting_lower_bound (14.6s)

## Comparison Sorting Lower Bound

**Definition.** A *comparison-based sorting algorithm* determines the sorted order of $n$ elements solely through pairwise comparisons of the form "is $a_i \leq a_j$?" Each comparison yields one bit of information (yes or no), and the algorithm may branch on that result. The *comparison sorting lower bound* states that any such algorithm must perform at least $\Omega(n \log n)$ comparisons in the worst case to sort $n$ distinct elements.

**Decision Tree Model.** Every comparison sort can be modeled as a binary *decision tree*: each internal node represents a comparison, each edge represents an outcome, and each leaf represents a permutation of the input that the algorithm has determined to be the sorted order. Because there are $n!$ possible input permutations, the decision tree must have at least $n!$ leaves. A binary tree of height $h$ has at most $2^h$ leaves, so we require

$$2^h \geq n! \implies h \geq \log_2(n!).$$

Applying Stirling's approximation, $\log_2(n!) = \Theta(n \log n)$, which establishes the lower bound.

**Worked Example.** Consider $n = 3$ elements $\{a, b, c\}$. There are $3! = 6$ possible orderings. A decision tree sorting three elements needs at least $\lceil \log_2 6 \rceil = 3$ comparisons in the worst case. Algorithms such as insertion sort on three elements indeed require up to 3 comparisons: compare $a$ vs.\ $b$, then introduce $c$ with at most two further comparisons, confirming the bound is tight.

**Key Theorem.** *(Information-theoretic lower bound)* Any deterministic comparison-based sorting algorithm requires at least $\lceil \log_2(n!) \rceil \geq n\log_2 n - n\log_2 e$ comparisons in the worst case. Algorithms such as merge sort and heapsort achieve $O(n \log n)$ comparisons, showing the bound is asymptotically tight.

```

### non_comparison_sorting (18.2s)

## Non Comparison Sorting

**Definition.** A *non-comparison sorting algorithm* is a sorting procedure that determines the output order of elements without performing pairwise comparisons between keys. Instead, such algorithms exploit structural properties of the keys themselves — typically that the keys are integers (or strings) drawn from a bounded domain — to achieve sub-linearithmic time complexity in many practical settings.

The fundamental lower bound for comparison-based sorting states that any deterministic comparison sort requires $\Omega(n \log n)$ comparisons in the worst case, because the decision tree of all possible orderings of $n$ elements has $n!$ leaves and therefore height at least $\log_2(n!) = \Theta(n \log n)$. Non-comparison sorts escape this bound by using additional information about the key domain.

---

**Worked Example: Counting Sort.**
Suppose we wish to sort the array $A = [3, 1, 4, 1, 5, 9, 2, 6]$, where every key lies in $\{0, 1, \ldots, k\}$ with $k = 9$.

1. **Count.** Allocate a count array $C[0{:}k]$ initialised to zero. For each $a \in A$, increment $C[a]$. After this pass, $C[v]$ holds the number of occurrences of value $v$.
2. **Cumulate.** Replace $C[j] \leftarrow C[j] + C[j-1]$ for $j = 1, \ldots, k$. Now $C[v]$ is the number of elements $\leq v$, giving the final position of the last occurrence of $v$ in the output.
3. **Place.** Traverse $A$ from right to left; place each element $A[i]$ at output index $C[A[i]] - 1$, then decrement $C[A[i]]$.

The result is the sorted array $[1, 1, 2, 3, 4, 5, 6, 9]$.

---

**Key Theorem** *(Counting Sort Complexity).* Let $n = |A|$ and let every key belong to $\{0, \ldots, k\}$. Counting sort runs in $\Theta(n + k)$ time and uses $\Theta(n + k)$ auxiliary space. When $k = O(n)$, this yields $\Theta(n)$ time — strictly better than the $\Omega(n \log n)$ comparison lower bound.

Radix sort extends this idea by processing keys digit by digit (from least significant to most significant), applying a stable counting sort at each digit position. For $d$-digit keys in base $b$, Radix sort runs in $\Theta(d(n + b))$ time.

---

**Lab Cell.**

```python
from sympy import symbols, Function
from collections import Counter

def counting_sort(A, k):
    C = [0] * (k + 1)
    for a in A:
        C[a] += 1
    for j in range(1, k + 1):
        C[j] += C[j - 1]
    output = [0] * len(A)
    for i in range(len(A) - 1, -1, -1):
        output[C[A[i]] - 1] = A[i]
        C[A[i]] -= 1
    return output

A = [3, 1, 4, 1, 5, 9, 2, 6]
print(counting_sort(A, k=9))   # [1, 1, 2, 3, 4, 5, 6, 9]
```

### stable_sorting (17.0s)

## Stable Sorting

**Definition.** A sorting algorithm is called *stable* if it preserves the relative order of elements that compare as equal. Formally, given a sequence $A = (a_1, a_2, \ldots, a_n)$ with a comparison key $k : A \to K$ where $K$ is a totally ordered set, a stable sort produces a permutation $\sigma$ such that:

$$k(a_{\sigma(i)}) \leq k(a_{\sigma(i+1)}) \quad \text{for all } 1 \leq i < n,$$

and additionally, whenever $k(a_i) = k(a_j)$ and $i < j$, we have $\sigma^{-1}(i) < \sigma^{-1}(j)$. That is, equal-key elements appear in the output in the same left-to-right order as they did in the input.

**Worked Example.** Consider a list of student records sorted first by grade, then by name. Suppose the input is:

$$[(B, \text{Zara}),\ (A, \text{Mia}),\ (B, \text{Ada}),\ (A, \text{Leo})]$$

A stable sort by grade alone yields:

$$[(A, \text{Mia}),\ (A, \text{Leo}),\ (B, \text{Zara}),\ (B, \text{Ada})]$$

Because the algorithm is stable, Mia precedes Leo (both grade $A$) and Zara precedes Ada (both grade $B$), mirroring their original positions. An unstable sort might instead produce $(A, \text{Leo}), (A, \text{Mia}), \ldots$, silently corrupting a secondary ordering already present in the data.

**Key Theorem.** *Merge Sort is stable and runs in $\Theta(n \log n)$ time.* During the merge step, when two elements share the same key, the merge procedure always takes the element from the left sub-array first, thereby preserving original order. No comparison-based sorting algorithm can achieve better than $\Omega(n \log n)$ worst-case comparisons (by the decision-tree lower bound), so Merge Sort is asymptotically optimal among stable comparison sorts.

Stability matters practically whenever records carry multiple attributes and are sorted in successive passes — a common pattern in database ORDER BY pipelines and radix-sort implementations.

**Lab Cell.**

```python

records = [('B','Zara'), ('A','Mia'), ('B','Ada'), ('A','Leo')]

# Python's built-in sort is guaranteed stable (Timsort)

print(stable_result)
# [('A','Mia'), ('A','Leo'), ('B','Zara'), ('B','Ada')]

# Verify stability: among equal keys, original indices are preserved

```

### counting_sort (23.7s)

## Counting Sort

**Definition.** Counting sort is a non-comparison-based sorting algorithm that determines the position of each element in the output array by counting occurrences. Given an input array $A$ of $n$ integers with values in the range $[0, k]$, it produces a sorted output array $B$ in $\Theta(n + k)$ time and $\Theta(n + k)$ auxiliary space. Because no element-to-element comparisons are performed, the algorithm circumvents the $\Omega(n \log n)$ lower bound that governs all comparison-based sorts.

The algorithm proceeds in three phases. First, a count array $C$ of length $k+1$ is initialised to zero; a single pass over $A$ increments $C[A[i]]$ for each $i$. Second, $C$ is transformed in place by prefix summation: for $j = 1, \ldots, k$, set $C[j] \leftarrow C[j] + C[j-1]$, so that $C[j]$ now records how many elements of $A$ are $\leq j$. Third, $A$ is traversed in reverse order; each element $A[i]$ is placed at index $C[A[i]] - 1$ in the output array $B$, and $C[A[i]]$ is decremented. Traversing $A$ in reverse is essential for **stability**: elements with equal keys retain their original relative order.

**Worked example.** Let $A = [3, 1, 4, 1, 5, 9, 2, 6]$ and $k = 9$.

After the count phase: $C = [0,2,1,1,1,1,1,0,0,1]$.

After prefix summation: $C = [0,2,3,4,5,6,7,7,7,8]$.

Reading $A$ from right to left places $6$ at index $6$, then $2$ at index $2$, and so on, yielding $B = [1,1,2,3,4,5,6,9]$.

**Theorem (Correctness and Stability).** After the prefix-summation step, $C[v]$ equals the number of elements in $A$ with value $\leq v$. Therefore, the last occurrence of value $v$ in a right-to-left pass over $A$ is placed at position $C[v]-1$, and each earlier occurrence at the next lower available position. Elements with equal keys thus appear in $B$ in the same order as in $A$, establishing stability. $\square$

**Complexity summary.**

| Phase | Time | Space |
|---|---|---|
| Count | $\Theta(n)$ | $\Theta(k)$ |
| Prefix sum | $\Theta(k)$ | in-place |
| Scatter | $\Theta(n)$ | $\Theta(n)$ |
| **Total** | $\Theta(n+k)$ | $\Theta(n+k)$ |

Counting sort is optimal when $k = O(n)$; for large $k$ relative to $n$ it is outperformed by comparison-based alternatives.

```python

    for v in A:
        C[v] += 1
    for j in range(1, k + 1):
        C[j] += C[j - 1]
    B = [0] * len(A)
    for i in range(len(A) - 1, -1, -1):
        B[C[A[i]] - 1] = A[i]
        C[A[i]] -= 1
    return B

result = counting_sort(A, k=9)
print(result)                        # [1, 1, 2, 3, 4, 5, 6, 9]
assert result == sorted(A)
```

### radix_sort (18.2s)

## Radix Sort

**Definition.** Radix sort is a non-comparative integer sorting algorithm that processes the digits of each key one position at a time, using a stable subroutine (typically counting sort) at each pass. Given $n$ keys, each representable as a $d$-digit number in base $b$, radix sort runs in $\Theta(d(n + b))$ time. When $d$ and $b$ are treated as constants relative to $n$, this reduces to $\Theta(n)$, breaking the $\Omega(n \log n)$ lower bound that applies to comparison-based sorting.

The two canonical variants differ in direction:

- **LSD (Least Significant Digit):** processes digits from position $1$ (units) up to position $d$ (most significant).
- **MSD (Most Significant Digit):** processes from the most significant digit downward, recursing on each digit bucket.

LSD radix sort is simpler and the standard choice for fixed-width keys; stability at every pass is essential for correctness.

**Worked Example.** Sort the list $[329, 457, 657, 839, 436, 720, 355]$ using LSD radix sort with base $b = 10$ and $d = 3$.

*Pass 1 (units digit):* bucket by digit in position $10^0$:

$$[720] \;[\ ] \;[\ ] \;[\ ] \;[\ ] \;[355] \;[436] \;[457, 657] \;[\ ] \;[329, 839]$$

Concatenate: $[720, 355, 436, 457, 657, 329, 839]$.

*Pass 2 (tens digit):* bucket by digit in position $10^1$:

$$[\ ] \;[\ ] \;[720, 329] \;[839] \;[\ ] \;[355, 457, 657] \;[436] \;[\ ] \;[\ ] \;[\ ]$$

Concatenate: $[720, 329, 839, 355, 457, 657, 436]$.

*Pass 3 (hundreds digit):* bucket by digit in position $10^2$:

$$[\ ] \;[\ ] \;[\ ] \;[329, 355] \;[436, 457] \;[\ ] \;[657] \;[720] \;[839] \;[\ ]$$

Concatenate: $[329, 355, 436, 457, 657, 720, 839]$. Sorted. $\square$

**Theorem (LSD correctness).** After pass $k$, the sequence is sorted with respect to the $k$ least significant digits. *Proof sketch.* By induction: after pass $k-1$ the sequence is sorted on digits $1, \ldots, k-1$. In pass $k$ a stable sort on digit $k$ places keys with smaller digit $k$ before those with larger digit $k$; ties preserve the order from the previous pass, maintaining correctness on digits $1, \ldots, k-1$. After $d$ passes the full key order is established.

**Lab Cell (SymPy).**
```python
from sympy import symbols, floor, Mod

def lsd_radix_sort(keys, base=10):
    max_val = max(keys)
    d = len(str(max_val))           # number of passes
    for k in range(d):
        buckets = [[] for _ in range(base)]
        for key in keys:
            digit = int(Mod(floor(key / base**k), base))
            buckets[digit].append(key)
        keys = [x for bucket in buckets for x in bucket]
    return keys

print(lsd_radix_sort([329, 457, 657, 839, 436, 720, 355]))
# → [329, 355, 436, 457, 657, 720, 839]
```

### integer_sorting_via_indexing (15.4s)

## Integer Sorting Via Indexing

**Definition.** Let $A = [a_1, a_2, \ldots, a_n]$ be a sequence of integers drawn from a bounded range $[0, k-1]$ for some positive integer $k$. *Sorting by indexing* (more commonly called **counting sort**) exploits the discrete structure of the domain: rather than comparing elements pairwise, we construct a *frequency array* $C$ of length $k$, where $C[v]$ records the number of times value $v$ appears in $A$. A prefix-sum pass then converts $C$ into a *position array*, and a final sweep reconstructs the sorted output in $O(n + k)$ time — a decisive improvement over the $O(n \log n)$ comparison lower bound when $k = O(n)$.

**Worked Example.** Let $A = [3, 1, 0, 1, 3, 2]$ with $k = 4$.

1. *Count.* Initialize $C = [0, 0, 0, 0]$. Scan $A$: $C[3]{+}{=}1$, $C[1]{+}{=}1$, $C[0]{+}{=}1$, $C[1]{+}{=}1$, $C[3]{+}{=}1$, $C[2]{+}{=}1$, yielding $C = [1, 2, 1, 2]$.
2. *Prefix sum.* Set $C[j] \leftarrow C[j] + C[j-1]$ for $j = 1, \ldots, 3$: $C = [1, 3, 4, 6]$. Now $C[v]$ is the number of elements $\leq v$, i.e., the last output index (1-based) for value $v$.
3. *Place.* Traverse $A$ right to left. For each $a_i$, place it at output position $C[a_i]$, then decrement $C[a_i]$. The result is $[0, 1, 1, 2, 3, 3]$.

**Key Theorem (Correctness and Stability).** After the prefix-sum step, $C[v] - C[v-1]$ equals the count of occurrences of $v$. The right-to-left placement guarantees that equal elements retain their original relative order — a property called *stability* — which makes counting sort suitable as a subroutine in radix sort.

*Complexity.* Time: $O(n + k)$. Space: $O(n + k)$ auxiliary. When $k = O(n)$, this is linear overall.

**Lab Cell.**

```python
from sympy import symbols, Function
A = [3, 1, 0, 1, 3, 2]; k = 4
C = [0] * k
for v in A:
    C[v] += 1
for j in range(1, k):
    C[j] += C[j-1]
out = [0] * len(A)
for v in reversed(A):
    C[v] -= 1
    out[C[v]] = v
print(out)  # [0, 1, 1, 2, 3, 3]
```
