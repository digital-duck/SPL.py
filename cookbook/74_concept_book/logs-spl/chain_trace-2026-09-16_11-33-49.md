## Memory Cell

A memory cell is a fixed-size, addressable unit of storage: it holds a value, and that value can be read or written by referring to the cell's address rather than to the value itself. This indirection — name the location, not the content — is the foundational abstraction of computing. Every data structure, from an array to a hash table to a linked list, is ultimately a pattern for organizing addresses of memory cells. In this domain, the memory cell is the floor: below it lie transistors, capacitors, and voltage levels, which belong to hardware design, not to the logic of programs.

A memory cell has two defining properties: a fixed width (commonly 8 bits, one byte, though some architectures use different widths) and a unique address, typically a non-negative integer. If a machine has $n$ bits of address space, it can distinguish $2^n$ distinct cells. A 32-bit address space, for instance, addresses $2^{32} \approx 4.3$ billion cells — the historical ceiling behind the "4 GB limit" of 32-bit systems.

**Worked example.** Suppose memory is modeled as a function $M: \text{Address} \to \text{Value}$, where $\text{Address} = \{0, 1, \dots, 2^n - 1\}$ and each value is an 8-bit byte, so $\text{Value} = \{0, 1, \dots, 255\}$. Writing 65 (the ASCII code for 'A') to address 1000 updates the function so that $M(1000) = 65$; reading address 1000 later retrieves that value regardless of what produced it. This is exactly how a C array works under the hood: declaring `char buf[10]` reserves ten consecutive addresses, and `buf[i]` compiles to $M(\text{base} + i)$ — address arithmetic on top of memory cells.

**Problem-solving application.** Suppose a sensor logs one byte per second and you're given 1 MB ($2^{20}$ bytes) of memory. How many seconds of data can you store, and what is the largest address you'll need? The capacity is $2^{20} = 1{,}048{,}576$ cells, so you can log that many seconds (about 12.1 days), and addresses run from $0$ to $2^{20}-1 = 1{,}048{,}575$ — requiring at least 20 bits to represent. This kind of address-space accounting is the first step in any buffer-sizing or memory-budgeting problem you'll encounter in systems programming.

### pointer (0.0s)

## Pointer

A pointer is a value whose contents are interpreted as an address — the location of a memory cell rather than data to be used directly. If an ordinary variable is a box holding a number or a character, a pointer is a box holding the *location* of another box. This single idea is the first genuine departure from the array: an array packs elements into contiguous memory in a fixed layout, so its structure is entirely determined by arithmetic on indices. A pointer breaks that constraint. Once a cell can store the address of another cell, memory need not be laid out in one block at all — cells can live anywhere and still be connected, because the connection is data (an address) rather than physical adjacency.

Formally, let memory be modeled as a function $M: \text{Addr} \to \text{Value}$, mapping addresses to the values stored there. A normal variable $x$ at address $a$ satisfies $M(a) = v$ for some value $v$. A pointer variable $p$ at address $b$ satisfies $M(b) = a$, where $a$ is itself an address — so *dereferencing* $p$, written $*p$, means evaluating $M(M(b))$. This two-step lookup — one to fetch the address, one to fetch the value at that address — is the entire mechanism. Nothing else is added.

Consider linking two integers manually. In C:

```c
int x = 42;
int *p = &x;      // p holds the address of x
printf("%d\n", *p); // dereference: prints 42
*p = 99;             // writes through the pointer
printf("%d\n", x);   // prints 99
```

Here `&x` produces the address of `x`, and `*p` reverses that operation.

The problem-solving payoff appears once pointers connect cells that are *not* adjacent in memory. Suppose you need a list that grows and shrinks arbitrarily, with cheap insertion anywhere — something an array cannot do without shifting every subsequent element, an $O(n)$ operation. Define a cell as a pair $(\text{value}, \text{next})$, where $\text{next}$ is a pointer to another cell or a special null address meaning "no cell." Insertion after a given cell becomes a constant-time rewiring of two pointers, regardless of list size, because nothing physically moves. This is the linked list, and it exists only because a memory cell can hold something other than data — it can hold a reference to where the next piece of the structure lives.

### binary_tree (0.0s)

## Binary Tree

A **binary tree** is a recursive data structure built from a node containing a value and two pointers, `left` and `right`, each either `null` or a reference to another binary tree. Formally, a binary tree $T$ is either empty or a triple $(v, T_L, T_R)$, where $v$ is a value and $T_L, T_R$ are themselves binary trees. This recursive definition is why nearly every operation on trees — search, insertion, traversal — is naturally written as a recursive function that handles the base case (empty tree) and combines results from the left and right subtrees.

The key structural property is **height** $h$, the length of the longest root-to-leaf path. A tree with $n$ nodes has $h \geq \lfloor \log_2 n \rfloor$, because a tree of height $h$ can hold at most $2^{h+1} - 1$ nodes (each level $i$ holds at most $2^i$ nodes). This bound is the reason binary trees matter: if a tree stays **balanced** — height kept near $\log_2 n$ — operations that walk a single root-to-leaf path run in $O(\log n)$ time. If the tree degenerates into a chain (e.g., inserting sorted data into an unbalanced BST), $h$ approaches $n$ and those same operations become $O(n)$, no better than a linked list.

**Worked example.** Consider inserting the values 5, 3, 8, 1, 4 into a binary search tree, where every node's left subtree holds smaller values and its right subtree holds larger ones. Insertion recurses: compare the new value to the current node, descend left or right, and place the new node when a null pointer is reached. Inserting 5, then 3 (left of 5), 8 (right of 5), 1 (left of 3), 4 (right of 3) produces a tree of height 2 for 5 nodes — matching the $O(\log n)$ bound closely, since $\log_2 5 \approx 2.32$.

**Problem-solving application.** Recognizing a binary tree's shape tells you which algorithm to reach for. A **heap** enforces a parent-child ordering (not left/right ordering) to guarantee $O(\log n)$ insertion and extraction of the minimum or maximum — the basis of priority queues and heapsort. A **trie** repurposes the child-pointer idea, using one pointer per possible character rather than just two, to achieve $O(k)$ lookup for a string of length $k$, independent of how many other strings are stored. In each case, the core skill is the same: given an operation, trace which path from root to leaf it must follow, and confirm the tree's balancing invariant keeps that path length at $O(\log n)$.

### comparison (0.0s)

## Comparison

A comparison is a binary predicate: given two elements $a$ and $b$ from a totally ordered set, it returns one of three outcomes — $a < b$, $a = b$, or $a > b$. This is deliberately the *only* operation a comparison-based algorithm is allowed to perform on the data. The algorithm never inspects bits, computes a hash, or indexes into an array by value — it only ever asks "which of these two is smaller?" and branches on the answer. Every sorting algorithm you have likely met — bubble sort, insertion sort, mergesort, quicksort, heapsort — is built entirely out of sequences of these yes/no questions.

Restricting an algorithm to comparisons might look like it weakens it, but it actually makes something powerful provable: a hard lower bound on how fast *any* comparison-based sort can possibly be, regardless of cleverness.

**Worked example.** Suppose you want to sort 3 distinct elements $a, b, c$. There are $3! = 6$ possible orderings. Each comparison you make splits the remaining possibilities roughly in half — a comparison is a yes/no question, so a sequence of $k$ comparisons can distinguish at most $2^k$ outcomes. To distinguish all 6 orderings you need $2^k \geq 6$, so $k \geq 3$ comparisons in the worst case — no algorithm can guarantee sorting 3 elements in 2 comparisons, no matter how it is designed.

**Problem-solving application — the general bound.** For $n$ elements there are $n!$ possible orderings, and a comparison-based algorithm can be modeled as a binary decision tree with one leaf per ordering. A binary tree with $n!$ leaves has depth at least $\log_2(n!)$:

$$
\log_2(n!) = \Omega(n \log n)
$$

by Stirling's approximation. This is why mergesort's and heapsort's $O(n \log n)$ running time is not an accident to be improved upon — it is asymptotically optimal for any algorithm restricted to comparisons. To break the barrier, you must abandon comparison as the sole primitive, which is exactly what non-comparison sorts like counting sort or radix sort do: they exploit structure in the values themselves (e.g., bounded integer range) rather than only asking "which is bigger?"

### heap (10.8s)

## Heap

A **heap** is a complete binary tree that satisfies the *heap property*: in a min-heap, every node's key is less than or equal to the keys of its children; in a max-heap, every node's key is greater than or equal to its children's keys. "Complete" means every level of the tree is fully filled except possibly the last, which fills left to right with no gaps. This completeness is what makes a heap unusually storage-efficient — instead of using pointers, we store it as a flat array. For a node at index $i$ (0-indexed), its children live at indices $2i+1$ and $2i+2$, and its parent is at $\lfloor (i-1)/2 \rfloor$. No pointers, no wasted memory, just arithmetic on indices.

Consider building a min-heap from the array $[5, 3, 8, 1, 4]$. Repeatedly inserting elements and restoring the heap property (by swapping a new element upward past larger parents, called *sift-up*) yields $[1, 3, 8, 5, 4]$: index 0 holds the minimum, and every parent-child pair satisfies parent $\le$ child. Extracting the minimum removes the root, moves the last element to index 0, and *sifts it down* — swapping with the smaller child until the heap property is restored. Because the tree has height $\lceil \log_2(n+1) \rceil$, both sift-up and sift-down touch at most $O(\log n)$ nodes, giving insert and extract-min their $O(\log n)$ cost. Building a heap from scratch, if done via repeated single-element sift-down starting from the last internal node (*heapify*), costs $O(n)$ overall — not $O(n \log n)$ — because most nodes sit near the bottom of the tree, where sift-down work is cheap; only a few nodes near the root pay the full $\log n$ cost, and the sum telescopes to a linear bound.

Heaps solve a specific class of problems: whenever you repeatedly need the current minimum (or maximum) from a changing collection, a heap outperforms sorting the whole collection. Dijkstra's shortest-path algorithm uses a min-heap to always expand the nearest unvisited node in $O(\log n)$ rather than scanning all nodes in $O(n)$. Heapsort exploits the same structure to sort in guaranteed $O(n \log n)$ time and $O(1)$ extra space, unlike quicksort's worst-case $O(n^2)$. When you see "find the k largest/smallest elements" or "process tasks by priority," a heap — implemented as Python's `heapq`, Java's `PriorityQueue`, or a hand-rolled array — is almost always the right tool.

### linked_list (11.8s)

## Linked List

A linked list is a sequence of nodes, where each node pairs a value (a memory cell) with a pointer to the next node in the sequence. Unlike an array, whose elements sit at contiguous, computable addresses, a linked list's elements can live anywhere in memory — the only way to find element $i$ is to start at the head and follow $i$ pointers. This single design choice inverts the array's cost profile: insertion or deletion at a known node is $O(1)$, since it only requires rewiring a constant number of pointers, while access by position is $O(n)$, since there is no arithmetic shortcut to a node's address.

**Worked example.** Suppose we maintain a singly linked list of integers $3 \to 7 \to 12 \to 4$ and want to delete the node holding $7$, given a pointer `prev` to the node holding $3$. The operation is:

$$\text{prev.next} \leftarrow \text{prev.next.next}$$

This single pointer reassignment detaches the node holding $7$ from the chain in constant time, regardless of how long the list is. Contrast this with an array-based list of the same values: deleting index $1$ requires shifting every subsequent element left by one slot, an $O(n)$ operation. The linked list wins precisely because it pays no price for "closing the gap" — there is no gap, only a rerouted pointer.

**Problem-solving application.** The trade-off matters when choosing a data structure for a task. If an algorithm's dominant operation is "insert/remove near a position you already hold a reference to" — as in implementing a queue, an LRU cache's eviction list, or an undo history — a linked list's $O(1)$ splice outperforms an array's $O(n)$ shift. But if the dominant operation is "find the $k$-th element" or "binary search," the array's $O(1)$ random access wins, since the linked list forces a linear $O(n)$ walk to reach any given position.

A concrete design question: given $n$ insertions and $m$ position-based lookups, which structure minimizes total work? An array costs roughly $O(n)$ for insertions (amortized, ignoring resizing) plus $O(m)$ for lookups; a linked list costs $O(n)$ for insertions but $O(nm)$ for lookups in the worst case, since each lookup may require traversing up to $n$ nodes. This asymmetry is why real systems (e.g., a text editor's undo stack versus its character buffer) choose the structure whose $O(1)$ operation matches the workload's bottleneck.

### priority_queue (10.9s)

## Priority Queue

A **priority queue** is an abstract data type that stores a collection of elements, each tagged with a priority, and supports two core operations: `insert(element, priority)` and `extract_max()` (or `extract_min()`), which removes and returns the element with the highest (or lowest) priority. Unlike a plain queue (FIFO) or stack (LIFO), order of removal depends entirely on priority, not arrival time.

The standard implementation is a **binary heap** — a complete binary tree stored in an array, satisfying the heap property: every parent's priority dominates its children's. Because the tree is complete and height-balanced, it has $O(\log n)$ height, so both `insert` and `extract_max` run in $O(\log n)$ time, while `peek()` (view the top element without removing it) is $O(1)$. A naive sorted-array implementation gives $O(1)$ extraction but $O(n)$ insertion; an unsorted array flips those costs. The heap balances both operations, which is why it is the default choice.

**Worked example.** Suppose a hospital triage system assigns priorities 1 (critical) through 5 (routine), using a min-heap so the most critical patient is always extracted first. Patients arrive with priorities $[3, 1, 4, 1, 5]$. Each `insert` places the new element at the next open leaf, then "bubbles up" — swapping with its parent while the heap property is violated. After all five insertions, the min-heap root holds priority 1. Calling `extract_min` removes the root, moves the last leaf into its place, and "bubbles down," swapping with the smaller child until the property is restored. Each insertion or extraction touches at most $\log_2 5 \approx 2$ levels — far cheaper than re-sorting the whole list each time a patient arrives.

**Problem-solving application.** Priority queues are the engine behind several classic algorithms because those algorithms repeatedly ask "what's next best?" from a changing candidate set. Dijkstra's shortest-path algorithm uses a min-priority-queue keyed on tentative distance, always expanding the closest unvisited node next; Prim's algorithm uses it to always add the cheapest edge connecting the growing tree to the rest of the graph. In discrete-event simulation, a priority queue keyed on timestamp ensures events are processed in chronological order regardless of when they were scheduled. In each case, the heap's $O(\log n)$ operations keep the overall algorithm efficient — e.g., Dijkstra's runtime becomes $O((V+E)\log V)$ with a binary-heap priority queue, versus $O(V^2)$ with a naive linear scan.

### queue (10.0s)

## Queue

A **queue** is a linear data structure that enforces **First-In, First-Out (FIFO)** ordering: elements are inserted at one end (the *tail*, via **enqueue**) and removed from the other end (the *head*, via **dequeue**). Whichever element has waited longest is always the next one served. Built on a linked list, a queue keeps a pointer to both `head` and `tail`, so both operations run in $O(1)$ time — insertion happens at `tail.next`, and removal happens by advancing `head`, with no need to traverse the list.

**Worked example.** Consider a print spooler receiving jobs $J_1, J_2, J_3$ in that order. Enqueuing pushes each job to the tail: after all three arrive, the queue holds $J_1 \to J_2 \to J_3$, with `head` pointing to $J_1$ and `tail` pointing to $J_3$. Dequeuing removes $J_1$ first — the printer processes jobs in arrival order, never skipping ahead. In a linked-list implementation:

```python
class Node:
    def __init__(self, val):
        self.val = val
        self.next = None

class Queue:
    def __init__(self):
        self.head = self.tail = None

    def enqueue(self, val):
        node = Node(val)
        if self.tail:
            self.tail.next = node
        else:
            self.head = node
        self.tail = node

    def dequeue(self):
        if not self.head:
            raise IndexError("dequeue from empty queue")
        val = self.head.val
        self.head = self.head.next
        if not self.head:
            self.tail = None
        return val
```

**Problem-solving application.** Queues are the natural mechanism for any process that must respect arrival order or explore "layer by layer." In **breadth-first search (BFS)**, the queue holds the *frontier* — nodes discovered but not yet expanded. Starting from a source node, you enqueue it, then repeatedly dequeue a node, visit its neighbors, and enqueue any unvisited ones. Because the queue is FIFO, all nodes at distance $k$ from the source are dequeued (and thus expanded) before any node at distance $k+1$ — this is exactly why BFS finds shortest paths in unweighted graphs. The same discipline underlies **producer-consumer buffers**: producers enqueue tasks, consumers dequeue them, and FIFO order guarantees fairness — no task is starved indefinitely as long as producers don't outpace consumers forever.

## Operating System Scheduler

An operating system scheduler is the kernel component that decides which runnable task (process or thread) gets access to the CPU at any given moment. Because a CPU can execute only one instruction stream per core at a time, the scheduler must arbitrate among potentially hundreds of tasks competing for that resource, deciding not just *who* runs but *for how long* and *in what order*. The central data structure supporting this decision is a **run queue** implemented as a multi-level priority queue: tasks are grouped into priority classes (e.g., real-time, interactive, batch), and within each class tasks are ordered so that the scheduler can retrieve the highest-priority runnable task in $O(\log n)$ or better time.

The scheduler is invoked at well-defined trigger points. A **timer interrupt** fires periodically (say, every 1–10 ms), causing the hardware to transfer control to the kernel regardless of what the currently running task is doing. This interrupt handler updates bookkeeping (e.g., decrementing the current task's remaining time slice), and if that slice is exhausted, the task is moved from "running" back into the run queue at its priority level. The scheduler then performs a **context switch**: it saves the register state of the outgoing task, dequeues the head of the highest nonempty priority level, and restores that task's saved state, resuming its execution as if uninterrupted.

Consider a run queue with three levels: real-time (RT), interactive (INT), and batch (BATCH), each a FIFO queue. Suppose RT is empty, INT holds tasks $[T_2, T_5]$, and BATCH holds $[T_1, T_3, T_4]$. On the next timer interrupt, the scheduler checks levels top-down, finds INT nonempty, and dequeues $T_2$ — even though $T_1$ arrived earlier — because priority dominates arrival order. This is the multi-level analog of a single-queue priority scheduler.

The design tension scheduler engineers must resolve is between **throughput** (total work completed) and **fairness/latency** (how long any one task waits). A pure priority scheme risks **starvation**: if RT and INT tasks arrive continuously, BATCH tasks may never run. Practical schedulers address this with **priority aging** — incrementing a waiting task's priority the longer it sits idle, so $\text{priority}(t) = \text{priority}_0 + \alpha \cdot \text{wait\_time}$, guaranteeing eventual promotion into a runnable slot. Understanding this queue-plus-interrupt mechanism is the foundation for reasoning about scheduling algorithms like round-robin, multilevel feedback queues, and completely fair schedulers.
