## Connected Graph

A **connected graph** is a graph in which every pair of vertices is linked by at least one path. In other words, you can travel from any vertex to any other vertex by following edges — no vertex is stranded in isolation. If even one pair of vertices has no path between them, the graph is **disconnected**, and the isolated pieces are called **connected components**.

Connectivity is one of the most fundamental properties in graph theory because it determines whether a network can actually function as a single unit. A social network is connected if every person can reach every other person through some chain of mutual friends. A power grid is connected if every substation is reachable from every other. A road network is connected if every city can be reached from every other city.

**Worked Example.** Consider a graph with five vertices: $A, B, C, D, E$ and edges $\{A\text{-}B,\ B\text{-}C,\ C\text{-}D,\ D\text{-}A,\ D\text{-}E\}$. Starting from $A$: you can reach $B$ directly, $C$ via $B$, $D$ directly, and $E$ via $D$. Since every vertex is reachable from $A$ (and by symmetry, from any vertex), this graph is connected. Now remove edge $D\text{-}E$. Vertex $E$ has no remaining edges, so it becomes isolated. The graph splits into two components — $\{A, B, C, D\}$ and $\{E\}$ — and is now disconnected.

**Problem-Solving Application.** To check connectivity in code, use a depth-first search (DFS) or breadth-first search (BFS) starting from any vertex and count how many vertices you visit. If the count equals the total number of vertices, the graph is connected.

```python
def is_connected(graph: dict[str, list[str]]) -> bool:
    if not graph:
        return True
    start = next(iter(graph))
    visited = set()
    stack = [start]
    while stack:
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            stack.extend(graph[node])
    return len(visited) == len(graph)
```

Here `graph` is an adjacency list mapping each vertex to its neighbors. This runs in $O(V + E)$ time — linear in the number of vertices $V$ and edges $E$ — making it practical even for large networks. A natural follow-up question: how many edges must you add to make a disconnected graph connected? The answer is the number of connected components minus one, since each added edge can merge exactly two components into one.

### walk (15.4s)

## Walk

A **walk** in a graph is any sequence of vertices where each consecutive pair is connected by an edge. Formally, a walk from vertex $v_0$ to vertex $v_k$ is written $v_0, e_1, v_1, e_2, v_2, \ldots, e_k, v_k$, where each $e_i$ is an edge joining $v_{i-1}$ to $v_i$. Crucially, a walk places no restriction on repetition — you may revisit vertices and reuse edges as many times as you like. The **length** of a walk is the number of edges traversed, counted with repetition.

This permissiveness is what distinguishes a walk from a path (no repeated vertices) or a trail (no repeated edges). Think of a walk as a literal stroll through a city where backtracking and looping are perfectly allowed.

**Worked example.** Consider the graph below with five vertices:

$$A - B - C - D, \quad B - D, \quad C - E$$

The sequence $A, B, D, B, C, E$ is a valid walk of length 5: it starts at $A$, crosses to $B$, jumps to $D$, backtracks to $B$, continues to $C$, then reaches $E$. The edge $\{A,B\}$ appears once, but $\{B,D\}$ and $\{B,C\}$ are each used once — no rule is broken even though vertex $B$ appears twice.

**Problem-solving application.** Walks become practically important when you model repetitive processes — web crawlers following links, random walks in probability, or Markov chains in statistics. A key result connects walks to matrix algebra: if $A$ is the **adjacency matrix** of a graph, then the entry $(A^k)_{ij}$ counts the number of distinct walks of length exactly $k$ from vertex $i$ to vertex $j$. This gives an efficient way to answer questions like "how many 3-step paths connect two users in a social network?" without enumerating every route manually.

For example, if $A^3$ evaluated at position $(i,j)$ returns 4, then there are exactly 4 walks of length 3 between those two users, including any that double back on themselves.

When you need to guarantee efficiency — no wasted steps — you restrict the walk to a trail or path. But when you need to count all possible routes or model a process that can loop, the unrestricted walk is the right tool.

### degree (14.6s)

## Degree

In a graph, the **degree** of a vertex is the number of edges incident to it — in plain terms, how many neighbors it has. If vertex $v$ has $k$ edges attached to it, we write $\deg(v) = k$. A vertex with degree 0 is called **isolated** (no connections), and a vertex with degree 1 is called a **leaf** (exactly one connection).

One fundamental bookkeeping fact ties all degrees together: the sum of all vertex degrees equals twice the number of edges, because every edge contributes 1 to each of its two endpoints.

$$\sum_{v \in V} \deg(v) = 2|E|$$

This is sometimes called the Handshaking Lemma, and it has an immediate consequence: the number of odd-degree vertices in any graph is always even.

**Worked example.** Consider a graph with five vertices and the edge list $\{(A,B),\,(A,C),\,(B,C),\,(B,D),\,(C,E)\}$. Count the edges touching each vertex:

| Vertex | Edges | Degree |
|--------|-------|--------|
| $A$ | $AB, AC$ | 2 |
| $B$ | $AB, BC, BD$ | 3 |
| $C$ | $AC, BC, CE$ | 3 |
| $D$ | $BD$ | 1 |
| $E$ | $CE$ | 1 |

Sum of degrees: $2+3+3+1+1 = 10 = 2 \times 5$ edges. ✓

**Problem-solving application.** Degree is one of the first things practitioners check when exploring a real network. In a social graph where vertices are users and edges are connections, degree measures raw connectivity: a vertex with very high degree (a **hub**) may be an influencer or a single point of failure. In a road network, a low-degree intersection is a potential bottleneck.

```python
import networkx as nx

G = nx.Graph()
G.add_edges_from([("A","B"),("A","C"),("B","C"),("B","D"),("C","E")])

for node, deg in G.degree():
    print(f"{node}: degree {deg}")

print("Sum of degrees:", sum(d for _, d in G.degree()))
print("2 × |E|:", 2 * G.number_of_edges())
```

Running this confirms the Handshaking Lemma and lets you immediately spot hubs (here, $B$ and $C$ tie for highest degree). Before running any deeper algorithm — shortest paths, clustering, centrality — always inspect the degree distribution; it tells you what kind of graph you are actually dealing with.

### tour (16.5s)

## Tour

A **tour** in graph theory is a walk through a graph that returns to its starting vertex. More precisely, a tour visits edges (or vertices) according to some rule and closes back on itself, forming a cycle. Two classic variants drive most practical applications: an **Eulerian tour** crosses every *edge* exactly once, while a **Hamiltonian tour** visits every *vertex* exactly once. Knowing which kind of tour exists — and how to find it — determines whether a routing problem is easily solvable or computationally hard.

**Eulerian tour.** Euler's 1736 result on the Königsberg bridge problem gives the definitive condition: a connected undirected graph has an Eulerian tour if and only if every vertex has even degree. This is one of the cases where a formal theorem genuinely matters, because it converts an infinite search into a single degree-parity check.

*Worked example.* Consider a small delivery network modeled as a graph:

```python
import networkx as nx

G = nx.MultiGraph()
edges = [(0,1),(0,1),(1,2),(2,3),(3,0),(1,3)]
G.add_edges_from(edges)

# Check Eulerian tour existence
degrees = dict(G.degree())
print("Degrees:", degrees)
print("Eulerian tour exists:", all(d % 2 == 0 for d in degrees.values()))

# Find the tour
if nx.is_eulerian(G):
    tour = list(nx.eulerian_circuit(G))
    print("Tour:", tour)
```

Every vertex has even degree here, so the graph is Eulerian and the circuit is found in $O(|E|)$ time using Hierholzer's algorithm.

**Problem-solving application.** Route-optimization problems frequently reduce to tour existence checks. A snowplow must traverse every street (edge) and return to the depot — that's an Eulerian tour problem. If some vertices have odd degree, you add the minimum number of duplicate edges to make all degrees even (the *Chinese Postman* strategy), then find the Eulerian circuit on the augmented graph.

Hamiltonian tours — visiting every city exactly once in a sales route — look superficially similar but belong to a different complexity class (NP-hard in general). The practical lesson: always identify *which* tour type your problem requires before choosing an algorithm. Confusing the two leads to either an exponential algorithm where a linear one suffices, or an incorrect model that misses repeated edges entirely.

### euler_tour (18.1s)

## Euler Tour

An **Euler tour** (also called an Eulerian circuit) is a walk through a graph that traverses every edge exactly once and returns to its starting vertex. The concept dates to Leonhard Euler's 1736 solution to the Königsberg Bridge Problem, widely regarded as the birth of graph theory. A related notion, an **Euler path**, traverses every edge exactly once but may end at a different vertex than it started.

**When does an Euler tour exist?** This is a question with a clean, verifiable answer — making it one of the few graph problems solvable in polynomial time without brute force.

> **Theorem (Euler, 1736).** A connected undirected graph has an Euler tour if and only if every vertex has even degree.

The proof idea is intuitive: whenever the walk enters a vertex, it must also leave. If any vertex has an odd number of edges, the walk will eventually get "stuck" there with no unused edge to exit on. For directed graphs, the condition upgrades: every vertex must have equal in-degree and out-degree.

**Worked example.** Consider a graph with vertices $\{A, B, C, D\}$ and edges $AB, BC, CD, DA, AC$. Computing degrees: $\deg(A) = 3$, $\deg(B) = 2$, $\deg(C) = 3$, $\deg(D) = 2$. Because $A$ and $C$ have odd degree, no Euler tour exists — but an Euler *path* from $A$ to $C$ (or $C$ to $A$) does, since exactly two vertices are odd.

Now remove edge $AC$, making all degrees even. An Euler tour now exists: $A \to B \to C \to D \to A$ uses every edge exactly once.

**Finding an Euler tour in code.** Hierholzer's algorithm constructs an Euler tour in $O(E)$ time. It works by greedily following unused edges from the start, then splicing in sub-tours whenever it revisits a vertex with unused edges remaining.

```python
from collections import defaultdict

def euler_tour(graph, start):
    adj = defaultdict(list)
    for u, v in graph:
        adj[u].append(v)
        adj[v].append(u)

    stack, tour = [start], []
    while stack:
        v = stack[-1]
        if adj[v]:
            stack.append(adj[v].pop())
        else:
            tour.append(stack.pop())
    return tour[::-1]

edges = [(0,1),(1,2),(2,3),(3,0),(0,2)]
print(euler_tour(edges, 0))
```

A practical use: DNA fragment assembly. Short sequenced reads are edges in a **de Bruijn graph**, and reconstructing the genome corresponds to finding an Euler tour — making this 18th-century puzzle the backbone of modern bioinformatics pipelines.

### fleurys_algorithm (15.2s)

## Fleury's Algorithm

An **Eulerian circuit** is a path through a graph that traverses every edge exactly once and returns to the starting vertex. Fleury's Algorithm is a systematic procedure for constructing such a circuit whenever one exists — that is, whenever the graph is connected and every vertex has even degree.

The algorithm follows one guiding principle: **never burn a bridge unless you have no other choice.** A *bridge* is an edge whose removal disconnects the graph. Crossing a bridge prematurely can strand you in a subgraph with unvisited edges you can no longer reach.

**The procedure:**

1. Verify the graph has an Eulerian circuit (connected, all even degrees).
2. Start at any vertex.
3. At each step, choose any adjacent edge — but prefer a non-bridge edge if one exists. Cross it and delete it from the graph.
4. Repeat until all edges are used.

**Worked example.** Consider a graph with vertices $\{A, B, C, D\}$ and edges $AB, BC, CD, DA, AC$. Every vertex has even degree (each has degree 2 or 4), so an Eulerian circuit exists. Starting at $A$:

- From $A$: edges $AB$, $AD$, $AC$ are available. Edge $AC$ is a bridge at this moment (removing it disconnects $C$ from the rest), so choose $AB$ instead.
- From $B$: only $BC$ remains. Cross it.
- From $C$: edges $CD$ and $CA$ are available. Neither is a bridge yet — choose $CD$.
- From $D$: only $DA$ remains. Cross it.
- From $A$: only $AC$ remains. Cross it, return to $C$ — wait, we end at $C$, not $A$.

Adjust: from $C$ after $BC$, choose $CA$ first, then $AD$, $DC$, back to $C$ via remaining edges. The exact path depends on tie-breaking, but Fleury guarantees you will complete the circuit as long as you check for bridges.

**Applying it.** To implement bridge-checking efficiently, use a depth-first search after each edge deletion: if removing edge $uv$ leaves $v$ unreachable from $u$, it is a bridge. In practice, this check makes Fleury's Algorithm $O(E^2)$, which is acceptable for moderate-sized graphs. For large networks — logistics routing, circuit board tracing, DNA fragment assembly — Hierholzer's Algorithm achieves $O(E)$ by avoiding per-step bridge checks, making it the industrial choice when Fleury's conceptual clarity is no longer needed.

### matching (15.6s)

## Matching

A **matching** in a graph is a set of edges such that no two edges share a vertex. Think of it as a collection of pairings where every participant is paired with at most one partner. A matching is called **maximum** if it contains as many edges as possible, and **perfect** if every vertex in the graph is matched.

Matching problems appear constantly in practice: assigning workers to jobs, pairing students with internships, routing packets in a network switch, or allocating hospital residents to programs. The common structure is always the same — you have two (or more) groups of entities and want to pair them optimally without conflicts.

**Worked example.** Suppose four students (A, B, C, D) each apply to a subset of four projects (1, 2, 3, 4):

| Student | Can work on |
|---------|-------------|
| A       | 1, 2        |
| B       | 2, 3        |
| C       | 3           |
| D       | 1, 4        |

Model this as a bipartite graph — students on the left, projects on the right, with an edge wherever a student is eligible. A maximum matching pairs as many students as possible. One valid matching: A–2, B–3, C–(none), D–1. Can we do better? Try A–1, B–2, C–3, D–4. Every student is matched — this is a perfect matching.

**Finding matchings algorithmically.** The standard tool for bipartite graphs is the **augmenting-path** method. An *augmenting path* alternates between unmatched and matched edges, starting and ending at unmatched vertices. Extending the matching along such a path increases its size by one. The algorithm repeatedly searches for augmenting paths (using BFS or DFS) until none exist; at that point, the matching is maximum. This is the core of the classical **Hopcroft-Karp algorithm**, which runs in $O(E\sqrt{V})$ time.

**Applying it.** In Python, `networkx` provides `max_weight_matching` and `bipartite.maximum_matching` directly:

```python
import networkx as nx
from networkx.algorithms import bipartite

G = nx.Graph()
students = ["A", "B", "C", "D"]
G.add_nodes_from(students, bipartite=0)
G.add_nodes_from([1, 2, 3, 4], bipartite=1)
G.add_edges_from([("A",1),("A",2),("B",2),("B",3),("C",3),("D",1),("D",4)])

matching = bipartite.maximum_matching(G, top_nodes=students)
print({k: v for k, v in matching.items() if k in students})
# {'A': 1, 'B': 2, 'C': 3, 'D': 4}
```

A key theoretical result, **Hall's theorem**, states that a bipartite graph has a perfect matching if and only if for every subset $S$ of one side, the neighborhood $|N(S)| \geq |S|$. This gives you a fast way to *prove* a perfect matching exists — or diagnose why one doesn't.

## Weighted Graph

A **weighted graph** is a graph $G = (V, E, w)$ where each edge $e \in E$ carries a numerical label called a **weight**, given by a function $w: E \to \mathbb{R}$. Weights typically represent cost, distance, time, or capacity — whatever quantity governs the relationship between two nodes. Without weights, a graph only tells you whether a connection exists; with weights, it tells you how much that connection "costs."

Formally, for an edge between vertices $u$ and $v$, we write $w(u, v)$ for its weight. A path from a source to a destination accumulates weight by summing the weights of every edge it traverses:

$$\text{path cost} = \sum_{i=1}^{k} w(v_{i-1},\, v_i)$$

The central problem in most weighted-graph applications is finding the **shortest path** — the one with minimum total weight.

**Worked example.** Consider four cities: A, B, C, D. The road network (with travel times in minutes) looks like this:

```
A --10-- B
|        |
6        3
|        |
C --15-- D
 \      /
   --4--
```

To get from A to D, two candidate paths are:
- $A \to B \to D$: cost $10 + 3 = 13$
- $A \to C \to D$: cost $6 + 4 = 10$

The shortest path is $A \to C \to D$ with total weight 10.

**Problem-solving application.** Dijkstra's algorithm finds shortest paths efficiently. It maintains a priority queue of (cost, node) pairs, always expanding the cheapest unvisited node next.

```python
import heapq

def dijkstra(graph, start):
    dist = {node: float('inf') for node in graph}
    dist[start] = 0
    pq = [(0, start)]          # (cost, node)

    while pq:
        cost, u = heapq.heappop(pq)
        if cost > dist[u]:
            continue           # stale entry
        for v, w in graph[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                heapq.heappush(pq, (dist[v], v))
    return dist

graph = {
    'A': [('B', 10), ('C', 6)],
    'B': [('D', 3)],
    'C': [('D', 4)],
    'D': []
}
print(dijkstra(graph, 'A'))
# {'A': 0, 'B': 10, 'C': 6, 'D': 10}
```

The result confirms that the shortest distance from A to D is 10. Weighted graphs appear everywhere real decisions involve trade-offs: network routing minimizes latency, logistics networks minimize shipping cost, and GPS navigation minimizes travel time — all using the same underlying structure.

### chinese_postman_problem (30.0s)

## Chinese Postman Problem

A mail carrier must travel every street in a neighborhood and return to the post office. The natural question is: what is the shortest possible route? This is the **Chinese Postman Problem** (CPP), named after Chinese mathematician Mei-Ko Kwan, who formalized it in 1962. The goal is to find the minimum-weight closed walk in a weighted graph that traverses every edge at least once.

The key insight connects the CPP to **Eulerian circuits**. A graph has an Eulerian circuit — a closed path that uses every edge exactly once — if and only if every vertex has even degree. When all vertices already have even degree, the postman's optimal route *is* the Eulerian circuit, and no edge needs to be repeated. The total cost equals the sum of all edge weights.

The interesting case arises when some vertices have odd degree. The number of odd-degree vertices is always even (an immediate consequence of summing degrees across all vertices). To make all degrees even, you must "duplicate" some edges — meaning the postman traverses those streets twice. The challenge is choosing *which* edges to duplicate so that the added weight is minimized: find the cheapest way to pair up all odd-degree vertices, where the cost of pairing two vertices equals the shortest path between them.

**Worked Example.** Consider a graph with four vertices $A, B, C, D$ and edge weights: $AB = 4$, $BC = 3$, $CD = 2$, $DA = 5$, $AC = 6$. Suppose vertices $B$ and $D$ have odd degree. The shortest path from $B$ to $D$ runs through $C$: $B \to C \to D$ with total cost $3 + 2 = 5$. Duplicating edges $BC$ and $CD$ adds 5 to the route's total cost. The postman's optimal circuit uses every original edge once, plus $BC$ and $CD$ a second time.

**Solving in practice.** The algorithm has three steps:

1. Compute the degree of every vertex; identify all odd-degree vertices.
2. Find the shortest path between every pair of odd-degree vertices.
3. Pair up the odd-degree vertices in the combination that minimizes total added distance, then duplicate the corresponding edges.

Once the graph has all even degrees, construct the Eulerian circuit. The CPP runs in polynomial time — a rare and practically valuable property — making it directly applicable to street sweeping, snow plowing, and meter-reading route optimization.
