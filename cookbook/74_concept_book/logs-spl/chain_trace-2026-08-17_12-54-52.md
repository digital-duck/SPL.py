## Connected Graph

A **connected graph** is a graph in which every pair of vertices is linked by at least one path. In other words, you can travel from any vertex to any other vertex by following edges — no vertex is stranded in isolation. If even one pair of vertices has no path between them, the graph is **disconnected**, and the isolated pieces are called **connected components**.

Connectivity is one of the most fundamental properties in graph theory because it determines whether a network can actually function as a single unit. A social network is connected if every person can reach every other person through some chain of mutual friends. A power grid is connected if every substation is reachable from every other. A road network is connected if every city can be reached from every other city.

**Worked Example.** Consider a graph with five vertices: $A, B, C, D, E$ and edges $\{A\text{-}B,\ B\text{-}C,\ C\text{-}D,\ D\text{-}A,\ D\text{-}E\}$. Starting from $A$: you can reach $B$ directly, $C$ via $B$, $D$ directly, and $E$ via $D$. Since every vertex is reachable from $A$ (and by symmetry, from any vertex), this graph is connected. Now remove edge $D\text{-}E$. Vertex $E$ has no remaining edges, so it becomes isolated. The graph splits into two components — $\{A, B, C, D\}$ and $\{E\}$ — and is now disconnected.

**Problem-Solving Application.** To check connectivity in code, use a depth-first search (DFS) or breadth-first search (BFS) starting from any vertex and count how many vertices you visit. If the count equals the total number of vertices, the graph is connected.

```python
def is_connected(graph: dict[str, list[str]]) -> bool:
    if not graph:
        return True
    start = next(iter(graph))
    visited = set()
    stack = [start]
    while stack:
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            stack.extend(graph[node])
    return len(visited) == len(graph)
```

Here `graph` is an adjacency list mapping each vertex to its neighbors. This runs in $O(V + E)$ time — linear in the number of vertices $V$ and edges $E$ — making it practical even for large networks. A natural follow-up question: how many edges must you add to make a disconnected graph connected? The answer is the number of connected components minus one, since each added edge can merge exactly two components into one.

## Tree

A **tree** is a hierarchical data structure made up of nodes connected by edges, with one designated **root** node at the top. Every node except the root has exactly one **parent**, and each node can have zero or more **children**. Nodes with no children are called **leaves**. The defining constraint is that a tree contains no cycles — you can never follow edges and return to where you started.

Trees appear everywhere in computing: file systems, HTML document structure, decision algorithms, and expression parsing all rely on tree organization. The key vocabulary you need: the **depth** of a node is its distance from the root (root is at depth 0); the **height** of a tree is the maximum depth among all leaves; a **subtree** is any node together with all its descendants.

**Worked example — evaluating an arithmetic expression.** Consider the expression `(3 + 4) * 2`. A parser represents this as a tree where the root holds `*`, its left child holds `+`, and the `+` node's children hold `3` and `4`; the right child of `*` holds `2`. To evaluate, you perform a **post-order traversal**: process left subtree, then right subtree, then the current node. Evaluating left gives $3 + 4 = 7$; evaluating right gives $2$; applying the root gives $7 \times 2 = 14$.

```python
class Node:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right

def evaluate(node):
    if node.left is None:          # leaf: it's a number
        return node.val
    l, r = evaluate(node.left), evaluate(node.right)
    ops = {'+': l+r, '-': l-r, '*': l*r, '/': l/r}
    return ops[node.val]

tree = Node('*', Node('+', Node(3), Node(4)), Node(2))
print(evaluate(tree))   # 14
```

**Problem-solving application.** Suppose you need to find the maximum value stored in an unsorted binary tree. There is no ordering guarantee, so you must visit every node — a **depth-first search** (DFS) works well: return the maximum of the current node's value, the max from the left subtree, and the max from the right subtree. The recursion bottoms out at leaves, which return their own value. This $O(n)$ traversal is the standard template whenever a tree problem requires considering all nodes with no shortcut structure to exploit.

### routing_protocol (0.0s)

## Routing Protocol

A **routing protocol** is a set of rules that routers use to discover network paths, share reachability information with neighboring routers, and decide which path a packet should take to reach its destination. Without routing protocols, network administrators would have to manually configure every possible path on every router — an approach that breaks immediately when the network changes. Routing protocols automate this: routers talk to each other, build a map of the network, and update that map when links go up or down.

Routing protocols fall into two broad categories. **Distance-vector protocols** (like RIP) have each router broadcast its routing table to its immediate neighbors; every router knows only distances and directions, never the full topology. **Link-state protocols** (like OSPF) have each router flood a description of its own links to every other router, so each router independently builds a complete map and runs shortest-path computation (Dijkstra's algorithm) locally. BGP, the protocol that glues the entire internet together, is a **path-vector protocol** — it advertises full AS (Autonomous System) paths to prevent routing loops across organizational boundaries.

**Worked example.** Suppose routers A, B, and C form a triangle. A connects to B with cost 1, B connects to C with cost 2, and A connects to C with cost 10. Running OSPF, each router floods its link costs to all others. Router A builds the full graph, runs Dijkstra, and finds that the cheapest path to C is A → B → C (cost 3), not the direct link (cost 10). A installs that path in its forwarding table.

**Problem-solving application.** You're a network engineer and the A–B link suddenly fails. How quickly does OSPF recover compared to RIP?

With OSPF, each router detects the failure, floods a new link-state advertisement, and all routers recompute paths within seconds. With RIP, routers rely on periodic table broadcasts and the "count to infinity" problem can cause convergence to take minutes, during which packets loop or are dropped. This is why enterprise and ISP networks prefer OSPF or IS-IS over RIP for interior routing, and why understanding convergence speed — not just path optimality — is the critical criterion when choosing a routing protocol for a production network.

### spanning_tree (0.0s)

## Spanning Tree

A **spanning tree** of a connected, undirected graph $G = (V, E)$ is a subgraph that includes every vertex in $V$ and connects them all using exactly $|V| - 1$ edges, with no cycles. Because it touches every vertex ("spans" the graph) while using the minimum number of edges needed to keep everything connected, a spanning tree is essentially the skeleton of the original graph.

Two properties fall directly from the definition: a spanning tree on $n$ vertices always has exactly $n - 1$ edges, and removing any single edge from it disconnects the graph. A graph with $n$ vertices and more than $n - 1$ edges necessarily contains at least one cycle; a spanning tree strips those cycles away while preserving reachability.

**Worked example.** Consider the graph below with five cities and seven roads between them:

```
A --4-- B
|  \    |
2   3   5
|    \  |
C --1-- D --6-- E
```

One spanning tree connects all five cities using four edges: `A–C (2)`, `C–D (1)`, `A–B (4)`, `D–E (6)`. Another valid spanning tree uses `A–D (3)` instead of `A–C` and `C–D`. Both are correct spanning trees — a graph typically has many. The one that minimizes total edge weight is called a **minimum spanning tree (MST)**.

**Problem-solving application.** Spanning trees appear whenever you need to connect a set of nodes at minimum cost — laying fiber-optic cable between data centers, designing a power grid, or routing packets. Kruskal's algorithm builds an MST greedily: sort all edges by weight, then add each edge to the tree if it does not create a cycle.

```python
import networkx as nx

G = nx.Graph()
G.add_weighted_edges_from([
    ("A","B",4), ("A","C",2), ("A","D",3),
    ("B","D",5), ("C","D",1), ("D","E",6)
])

mst = nx.minimum_spanning_tree(G)          # Kruskal's by default
print(mst.edges(data="weight"))
# [('A','B',4), ('A','C',2), ('C','D',1), ('D','E',6)]  — total cost: 13
```

To deepen your understanding: given a graph, enumerate two distinct spanning trees and verify each has exactly $n - 1$ edges and no cycles. Then compute the total weight of each and identify which one is the MST.

### sink_tree (0.0s)

## Sink Tree

A **sink tree** is a directed graph in which every node has exactly one directed path leading to a single distinguished node called the *sink*. All edges, when followed in their directed direction, eventually funnel into that one destination. If you picture water flowing downhill through a network of channels, every drop—no matter where it starts—reaches the same drain. That drain is the sink; the whole drainage network is the sink tree.

More precisely: given a directed graph $G = (V, E)$, a sink tree rooted at node $r$ is a spanning subgraph of $G$ such that (1) every node $v \neq r$ has out-degree exactly 1, (2) node $r$ has out-degree 0, and (3) following edges from any node eventually reaches $r$. Because each non-root node has exactly one outgoing edge and there are no cycles, the structure is a tree with all edges oriented toward the root.

**Worked example.** Suppose a small campus network has five switches labeled 1–5, with switch 5 acting as the gateway router. Traffic routing rules create directed links: $1 \to 3$, $2 \to 3$, $3 \to 5$, $4 \to 5$. Every packet from switch 1 travels $1 \to 3 \to 5$; every packet from switch 4 travels $4 \to 5$. Drawing this out, the edges form a sink tree rooted at switch 5—two branches merge at 3, then continue to 5. No cycles exist, and every node reaches the sink in finite hops.

**Problem-solving application.** Sink trees appear naturally whenever you need to compute shortest or cheapest paths *toward* a single destination for all nodes simultaneously—exactly the reverse of Dijkstra's algorithm, which fans out *from* a source. To build a minimum-cost sink tree (minimum spanning arborescence), you use **Edmonds' algorithm** (also called Chu–Liu/Edmonds'): repeatedly find the minimum-weight incoming edge for each non-sink node, detect and contract any cycles that form, then expand the solution back. The result is a directed subgraph where every node reaches the sink at minimum total edge cost.

A practical instance: in a logistics network, you want every warehouse to ship goods to a central hub via the cheapest available route. Building the minimum-cost sink tree tells you, for each warehouse, exactly which outgoing link to use so that the total network cost is minimized—without any two warehouses needlessly duplicating expensive shared legs.

### weighted_graph (0.0s)

## Weighted Graph

A **weighted graph** is a graph $G = (V, E, w)$ where each edge $e \in E$ carries a numerical label called a **weight**, given by a function $w: E \to \mathbb{R}$. Weights typically represent cost, distance, time, or capacity — whatever quantity governs the relationship between two nodes. Without weights, a graph only tells you whether a connection exists; with weights, it tells you how much that connection "costs."

Formally, for an edge between vertices $u$ and $v$, we write $w(u, v)$ for its weight. A path from a source to a destination accumulates weight by summing the weights of every edge it traverses:

$$\text{path cost} = \sum_{i=1}^{k} w(v_{i-1},\, v_i)$$

The central problem in most weighted-graph applications is finding the **shortest path** — the one with minimum total weight.

**Worked example.** Consider four cities: A, B, C, D. The road network (with travel times in minutes) looks like this:

```
A --10-- B
|        |
6        3
|        |
C --15-- D
 \      /
   --4--
```

To get from A to D, two candidate paths are:
- $A \to B \to D$: cost $10 + 3 = 13$
- $A \to C \to D$: cost $6 + 4 = 10$

The shortest path is $A \to C \to D$ with total weight 10.

**Problem-solving application.** Dijkstra's algorithm finds shortest paths efficiently. It maintains a priority queue of (cost, node) pairs, always expanding the cheapest unvisited node next.

```python
import heapq

def dijkstra(graph, start):
    dist = {node: float('inf') for node in graph}
    dist[start] = 0
    pq = [(0, start)]          # (cost, node)

    while pq:
        cost, u = heapq.heappop(pq)
        if cost > dist[u]:
            continue           # stale entry
        for v, w in graph[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                heapq.heappush(pq, (dist[v], v))
    return dist

graph = {
    'A': [('B', 10), ('C', 6)],
    'B': [('D', 3)],
    'C': [('D', 4)],
    'D': []
}
print(dijkstra(graph, 'A'))
# {'A': 0, 'B': 10, 'C': 6, 'D': 10}
```

The result confirms that the shortest distance from A to D is 10. Weighted graphs appear everywhere real decisions involve trade-offs: network routing minimizes latency, logistics networks minimize shipping cost, and GPS navigation minimizes travel time — all using the same underlying structure.

## Bellman Ford Algorithm

Finding the shortest path between two points is straightforward when all edges have non-negative weights — Dijkstra's algorithm handles that efficiently. But what happens when some edges carry negative weights? A road network with tolls might use negative weights to represent rebates, or a financial graph might model arbitrage opportunities. Dijkstra's algorithm breaks in these cases. The **Bellman-Ford algorithm** solves the single-source shortest path problem even when edge weights are negative, and it detects negative-weight cycles — loops whose total cost is negative, meaning no finite shortest path exists.

The core idea is relaxation. For a graph with $V$ vertices and $E$ edges, Bellman-Ford initializes the distance to the source as $0$ and all others as $\infty$. It then repeats the following step exactly $V - 1$ times: for every edge $(u, v)$ with weight $w$, if $d[u] + w < d[v]$, update $d[v] = d[u] + w$. After $V - 1$ passes, if any distance can still be reduced, a negative-weight cycle exists.

**Worked example.** Consider a graph with vertices $\{A, B, C\}$ and edges $A \to B$ (weight $4$), $A \to C$ (weight $2$), $C \to B$ (weight $-3$). Source is $A$.

| Pass | $d[A]$ | $d[B]$ | $d[C]$ |
|------|--------|--------|--------|
| Init | $0$ | $\infty$ | $\infty$ |
| 1 | $0$ | $4$ | $2$ |
| 2 | $0$ | $-1$ | $2$ |

After pass 1, $d[B]$ updates to $4$ via $A \to B$ and $d[C]$ to $2$ via $A \to C$. In pass 2, the path $A \to C \to B$ gives $2 + (-3) = -1 < 4$, so $d[B]$ drops to $-1$. The algorithm terminates with shortest distances $d[B] = -1$, $d[C] = 2$.

**Problem-solving application.** In Python, implement Bellman-Ford by iterating over all edges $V - 1$ times and adding a final check for negative cycles:

```python
def bellman_ford(graph, source):
    dist = {v: float('inf') for v in graph}
    dist[source] = 0
    edges = [(u, v, w) for u in graph for v, w in graph[u]]
    for _ in range(len(graph) - 1):
        for u, v, w in edges:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
    for u, v, w in edges:
        if dist[u] + w < dist[v]:
            raise ValueError("Negative-weight cycle detected")
    return dist
```

The time complexity is $O(VE)$, slower than Dijkstra's $O((V + E) \log V)$, but correctness with negative weights — and the cycle check — makes Bellman-Ford the right tool when edge costs can be adversarial or arbitrage-like.

## Big O Notation

When you write an algorithm, two questions matter immediately: does it produce the right answer, and how fast does it run as the input grows? Big O notation is the standard language for answering the second question. It describes the **growth rate** of an algorithm's runtime (or memory use) as a function of input size $n$, ignoring constant factors and lower-order terms that become irrelevant at scale.

Formally, we say $f(n) = O(g(n))$ if there exist constants $c > 0$ and $n_0$ such that $f(n) \leq c \cdot g(n)$ for all $n \geq n_0$. In practice, this means: find the dominant term in your operation count, drop the coefficient, and that's your Big O class.

**Common classes, slowest to fastest growth:**

| Notation | Name | Example |
|---|---|---|
| $O(1)$ | Constant | Array index lookup |
| $O(\log n)$ | Logarithmic | Binary search |
| $O(n)$ | Linear | Single loop over a list |
| $O(n \log n)$ | Linearithmic | Merge sort |
| $O(n^2)$ | Quadratic | Nested loops |
| $O(2^n)$ | Exponential | Naive subset enumeration |

**Worked example.** Consider two functions that check whether a list contains any duplicate values:

```python
def has_duplicate_slow(lst):          # O(n^2)
    for i in range(len(lst)):
        for j in range(i + 1, len(lst)):
            if lst[i] == lst[j]:
                return True
    return False

def has_duplicate_fast(lst):          # O(n)
    seen = set()
    for x in lst:
        if x in seen:
            return True
        seen.add(x)
    return False
```

The first version compares every pair — roughly $n^2/2$ comparisons — so it is $O(n^2)$. The second scans the list once, trading memory for speed, making it $O(n)$. At $n = 10{,}000$, that difference is roughly 50 million operations versus 10,000.

**Problem-solving application.** When optimizing code, locate the innermost loop or the operation that executes most frequently, express its count as a polynomial in $n$, and keep only the highest-degree term. If you see a loop inside a loop, suspect $O(n^2)$ and ask whether a hash set or sort could eliminate one dimension. Sorting costs $O(n \log n)$ but often enables $O(\log n)$ lookups afterward — a classic trade that converts an $O(n^2)$ search into $O(n \log n)$ overall. Practice by estimating Big O before benchmarking; if your estimate and your profiler disagree, that gap reveals a hidden algorithmic cost worth investigating.

## Dijkstras Sink Tree Algorithm

Dijkstra's algorithm finds the shortest path from a single source vertex to every other vertex in a weighted graph with non-negative edge weights. The **sink tree** variant flips this perspective: instead of broadcasting shortest paths *out* from a source, it computes shortest paths *into* a designated sink — a destination vertex that every other vertex wants to reach. The result is a directed spanning tree rooted at the sink, where every tree edge points toward it and the path from any vertex to the sink along the tree is guaranteed to be the shortest available.

**Why flip the direction?** In routing and network optimization, you often want to know the cheapest way for many nodes to deliver data to a single collector. Computing one sink tree answers all of those queries simultaneously, in a single pass.

**How it works.** Run standard Dijkstra on the *reverse* graph — replace every directed edge $(u \to v, w)$ with $(v \to u, w)$. Then launch Dijkstra from the sink on this reversed graph. The shortest path from the sink to any vertex $v$ in the reversed graph equals the shortest path from $v$ to the sink in the original graph. Collect the parent pointers from Dijkstra's relaxation steps; they form the sink tree.

**Worked example.** Consider four cities: A, B, C, and D (the sink), with edges A→B (2), A→C (5), B→D (3), C→D (1). Reverse the edges: B→A, C→A, D→B, D→C. Run Dijkstra from D on the reversed graph. D reaches B at cost 3 and C at cost 1; from B, it reaches A at cost 3+2=5; from C, it reaches A at cost 1+5=6. So A's shortest path to D costs 5, through B. The sink tree edges in the original graph are A→B→D and C→D, with A preferring the A→B→D route.

**Problem-solving application.** Suppose a logistics company has 50 warehouses all shipping to a single distribution hub. Rather than running Dijkstra 50 times (once per warehouse), reverse the road network, run Dijkstra once from the hub, and read off every warehouse's optimal route from the resulting sink tree in $O(1)$ per query. Time complexity remains $O((V + E)\log V)$ using a binary heap — identical to standard Dijkstra, since the reversal is a linear preprocessing step. Whenever a problem involves *many-to-one* shortest paths, reach for the sink tree before considering repeated single-source runs.

## Algorithmic Complexity Comparison

When you write code to solve a problem, there are usually several ways to do it. Algorithmic complexity comparison is the practice of measuring and ranking those approaches by how their runtime (or memory use) scales as the input grows — so you can pick the one that stays fast when inputs get large.

The standard tool is **Big-O notation**. $O(f(n))$ describes the worst-case growth rate of an algorithm's resource use as a function of input size $n$, ignoring constant factors. Common classes, from fastest-growing to slowest:

$$O(1) \;<\; O(\log n) \;<\; O(n) \;<\; O(n \log n) \;<\; O(n^2) \;<\; O(2^n)$$

An algorithm in $O(n^2)$ doesn't just "do more work" than one in $O(n \log n)$ — it eventually becomes catastrophically slower for any large $n$, no matter how well-tuned the constants are.

**Worked example: searching a sorted list.**

Linear search scans every element until it finds a match — $O(n)$ comparisons in the worst case. Binary search instead cuts the remaining candidates in half each step, reaching the answer in at most $\lceil \log_2 n \rceil$ comparisons — $O(\log n)$.

For $n = 1{,}000{,}000$: linear search may need one million comparisons; binary search needs at most 20. That gap is not a tuning detail — it is a structural difference in how each algorithm responds to scale.

**Applying the comparison in practice.**

Suppose you need to check whether any two students in a class share a birthday. A naive approach compares every pair: $\binom{n}{2} = \frac{n(n-1)}{2}$ comparisons, which is $O(n^2)$. An alternative inserts each birthday into a hash set and checks for membership before inserting — one pass, $O(n)$ total.

```python
def has_shared_birthday(birthdays):
    seen = set()
    for b in birthdays:
        if b in seen:
            return True
        seen.add(b)
    return False
```

The hash-set version does not just run faster on your test data; it scales to 10,000 students while the pair-comparison version becomes unusably slow.

The key skill is recognizing which complexity class an algorithm belongs to — by counting loops, recursive calls, or data-structure operations — and then choosing or designing the class that fits your scale requirement.
