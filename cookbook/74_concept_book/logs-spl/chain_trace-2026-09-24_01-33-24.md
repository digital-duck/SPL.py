### parent_structure (0.0s)

## Parent Structure

Every object you construct in Sage lives inside a mathematical structure called its **parent** — a ring, field, or other algebraic set that governs how the object behaves under arithmetic. Where Python asks `type(x)`, Sage asks `x.parent()`, and the answer is not a data type but a piece of mathematics: the integers $\mathbb{Z}$, the rationals $\mathbb{Q}$, the finite field $\mathrm{GF}(7)$, or the symbolic ring $\mathrm{SR}$. This matters because the *same* numeral, say $3$, means something different depending on where it lives. As an element of $\mathbb{Z}$, $3$ has no multiplicative inverse; as an element of $\mathbb{Q}$, it does ($1/3$); as an element of $\mathrm{GF}(7)$, its inverse is $5$, since $3 \cdot 5 \equiv 1 \pmod 7$.

**Worked example.** Consider the following:

```python
a = 3
print(a.parent())              # Integer Ring
b = QQ(3)
print(b.parent())              # Rational Field
c = GF(7)(3)
print(c.parent())              # Finite Field of size 7
print(1/c)                     # 5
print(1/a)                     # 1/3  (Sage promotes to QQ automatically)
```

Sage's default integer `3` already prints `1/3` under division because Sage silently *coerces* it into $\mathbb{Q}$ when needed — but that coercion is only possible because Sage knows both parents ($\mathbb{Z}$ and $\mathbb{Q}$) and knows there is a structure-preserving map $\mathbb{Z} \hookrightarrow \mathbb{Q}$ between them. In $\mathrm{GF}(7)$, no such map to $\mathbb{Q}$ exists — division is intrinsic to the field itself, computed via modular inverses, not by leaving the structure.

**Problem-solving application.** Whenever an operation between two Sage objects fails with a `TypeError: no common canonical parent`, the fix is to inspect `.parent()` on each operand and decide, explicitly, which structure the computation should happen in — then coerce with `QQ(x)`, `GF(p)(x)`, or `SR(x)` before combining them. For instance, mixing a matrix over $\mathbb{Z}$ with one over $\mathrm{GF}(7)$ will raise an error unless you coerce both into a common parent first, since matrix rank, invertibility, and even equality depend on which ring the entries are drawn from. Treating `.parent()` as your first diagnostic — before checking values — is the habit that prevents a large class of Sage errors.

### symbolic_variable (0.0s)

## Symbolic Variable

A symbolic variable is a name that represents an unspecified mathematical object rather than a single stored number. When you write `var('x')` in a computer algebra system such as SymPy or Sage, you are not asking the machine to reserve a memory slot for one value the way `x = 5` would in ordinary programming. Instead, you are creating a placeholder that stands for every number in its domain simultaneously, so that any expression built from `x` remains true no matter what value `x` eventually takes. This is the essential shift from arithmetic, which computes with known quantities, to algebra, which reasons about relationships that hold for entire families of quantities at once — the "floor of generality" on which all higher symbolic mathematics is built.

Consider the expression $(x+1)^2$. If $x$ held a fixed numeric value, evaluating this would require substituting that number and computing a single result. But as a symbolic variable, $x$ lets the system expand the expression algebraically:

$$(x+1)^2 = x^2 + 2x + 1$$

This identity is not a claim about one number — it is a statement that holds for every real (or complex) $x$. The computer algebra system manipulates the symbol according to the rules of algebra (distribution, combining like terms) without ever needing to know what $x$ actually is.

The practical payoff appears in problem-solving. Suppose you need to find where the parabola $f(x) = x^2 + 2x + 1$ touches the $x$-axis. Rather than guessing numbers and checking, you keep $x$ symbolic, factor the expression as $(x+1)^2$, and solve $(x+1)^2 = 0$ to get $x = -1$ — a conclusion derived once, symbolically, that is guaranteed correct for that entire class of question. This is why symbolic computation systems always begin a session with a declaration like `x = var('x')`: it tells the engine "treat this name as a universal placeholder," enabling later commands (`solve`, `diff`, `expand`) to operate on the general form of a problem instead of one numeric instance. Mastering this declaration is the gateway skill to everything that follows — equations, functions, calculus — because each of those depends on manipulating relationships that must hold across a whole range of inputs, not just one.

### symbolic_expression (0.0s)

## Symbolic Expression

A **symbolic expression** is a piece of mathematics represented as a data structure rather than a number. When you write `x^2 + 2*x + 1` after declaring `x` as a symbolic variable, Sage does not evaluate it — it builds a tree whose leaves are symbols and constants and whose internal nodes are operations (`+`, `*`, `^`, `sin`, `exp`, and so on). This tree lives in an algebraic structure called the **Symbolic Ring**, written $SR$. Every symbolic expression is, formally, an element of $SR$, and $SR$ behaves like a ring: expressions can be added and multiplied, and the results are again symbolic expressions, closed under those operations just as $\mathbb{Z}$ is closed under addition and multiplication.

The key distinction from a numerical value is *exactness with deferred evaluation*. An expression such as $\sqrt{2} + \pi$ is stored exactly — no decimal approximation is computed until you explicitly ask for one (e.g., via `.n()`). This matters for problem-solving because operations that would lose precision numerically — differentiation, factoring, simplification, exact equality testing — can be performed symbolically without accumulating floating-point error.

**Worked example.** Define $f(x) = \sin(x)^2 + \cos(x)^2$ as a symbolic expression:
```
x = var('x')
f = sin(x)^2 + cos(x)^2
f.simplify_full()   # returns 1
```
Sage does not "know" the Pythagorean identity by evaluating at sample points; it applies trigonometric simplification rules to the expression tree itself, producing the exact symbolic result $1$.

**Problem-solving application.** Suppose you need the second derivative of $g(x) = x^3 e^{-x}$ at $x = 2$, exactly, not approximately. Build the symbolic expression and manipulate it structurally:
```
g = x^3 * exp(-x)
g2 = diff(g, x, 2)
g2.subs(x=2)
```
The differentiation acts on the tree via the product and chain rules encoded in $SR$'s operation table, and substitution (`subs`) replaces the symbol $x$ with the constant $2$ only at the final step — you control exactly when the exact object collapses into a number. This "build first, evaluate later" workflow is the core habit for symbolic computation: treat expressions as manipulable objects, and postpone numerical evaluation until the structural work (solving, simplifying, differentiating) is complete.

### exact_integer (0.0s)

## Exact Integer

Every integer in mathematics is exact: $7$, $-42$, and $2^{100}$ are each a single, definite value with no ambiguity. Most programming languages betray this idea. A 32-bit or 64-bit integer type stores numbers in a fixed number of bits, so once a computation exceeds that range, the result silently wraps around or overflows — the computer starts lying about arithmetic. Sage refuses to do this. Every Sage `Integer` is arbitrary-precision: it grows however many digits are needed to represent the value exactly, with no upper bound tied to hardware word size. Computing $2^{100}$ in Sage does not overflow and does not round to a nearby floating-point approximation — it returns the one true 31-digit integer, stored digit by digit, just as a mathematician would write it.

**Worked example.** In Sage,
```
sage: 2^100
1267650600228229401496703205376
```
This is not an estimate; it is the exact value, and Sage will use it in further computation without loss. Contrast this with a language using fixed 64-bit integers, where $2^{100}$ cannot be represented at all and the computation either overflows to a meaningless bit pattern or is silently truncated. Sage's `Integer` type instead allocates memory dynamically, so the representable range is limited only by available memory, not by a hardware register.

**Problem-solving application.** Exact integers matter whenever a computation must be trusted, not merely approximated — factoring large numbers, computing exact binomial coefficients for combinatorics, or verifying number-theoretic identities like Fermat's Little Theorem. Consider $100!$, which has 158 digits:
```
sage: factorial(100)
93326215443944152681699238856266700490715968264381621468592963895217599993229915608941463976156518286253697920827223758251185210916864000000000000000000000000
```
A floating-point computation of $100!$ would lose all precision beyond about 15–17 significant digits, making it useless for checking, say, whether $100!$ is divisible by $99^3$. With exact integers, `factorial(100) % 99^3 == 0` returns a provably correct `True` or `False`, because every digit above is exact. This is the floor of exactness that the rest of Sage's number system — rationals, exact reals, symbolic expressions — is built on top of: integers are where "exact" begins.

### simplification (0.0s)

## Simplification

Two symbolic expressions can look completely different yet represent the same mathematical object: $\sin^2(x) + \cos^2(x)$ and $1$ are equal for every $x$, but a computer algebra system has no way to know that just by comparing symbols. Simplification is the process of rewriting an expression into a canonical or reduced form, and deciding sameness is a separate, harder question that a symbolic engine addresses with dedicated tools rather than by staring at syntax.

`simplify_full()` applies a battery of rewrite rules — combining like terms, factoring, reducing fractions, and applying trigonometric identities such as $\sin^2(x) + \cos^2(x) = 1$ or $\tan(x) = \sin(x)/\cos(x)$ — repeatedly, until no rule produces further change. For example:

$$
\texttt{simplify\_full}\left(\frac{\sin^2(x)}{1-\cos^2(x)}\right) = 1
$$

The engine recognizes $1 - \cos^2(x)$ as $\sin^2(x)$ via the Pythagorean identity, then cancels the resulting $\sin^2(x)/\sin^2(x)$.

The subtlety worth internalizing is what `expr == 0` actually means. Writing `expr == 0` does not evaluate a truth value — it constructs an *equation object*, a symbolic statement pairing `expr` with `0`, the same way $x^2 - 4 = 0$ is a statement to be solved or checked, not a boolean. To actually ask "is this expression identically zero?", you call `is_zero()`, which triggers the system's decision procedure: it simplifies the expression fully and, for many classes of expressions, applies deeper certification methods (numerical sampling at several points, or specialized algorithms for polynomials and trigonometric forms) to certify the result.

$$
(\sin^2(x) + \cos^2(x) - 1). is\_zero() \;\rightarrow\; \text{True}
$$

$$
(\sin^2(x) + \cos^2(x) - 1) == 0 \;\rightarrow\; \text{an unevaluated equation}
$$

In problem-solving, this distinction matters most when verifying an identity you've derived by hand, or when a `solve()` call depends on correctly detecting that a denominator or discriminant vanishes: using `==` where you meant `is_zero()` is a common source of silent bugs, since the equation object is truthy in ways that mislead conditional logic. The reliable workflow is: simplify first with `simplify_full()`, then confirm equality with `is_zero()` — never trust raw syntactic comparison for symbolic sameness.

### polynomial_rings (0.0s)

## Polynomial Rings

A polynomial ring $R[x]$ is the set of all polynomials in the variable $x$ with coefficients drawn from a ring $R$, together with the usual operations of addition and multiplication. The choice of $R$ is not cosmetic — it determines what questions about a polynomial can even be answered. Over $\mathbb{Z}[x]$, the polynomial $2x - 1$ has no root, because $\tfrac{1}{2} \notin \mathbb{Z}$. Over $\mathbb{Q}[x]$, it does. Sage makes this dependency explicit: rather than treating a polynomial as a free-floating expression, it requires you to declare the ring first, via `PolynomialRing(QQ, 'x')`, and every polynomial you build lives inside that declared structure as a first-class object with a known *parent*.

This matters because operations like `factor()`, `gcd()`, and `roots()` are not universal algorithms — their correct behavior depends on the ring. Factoring $x^2 - 2$ over $\mathbb{Q}[x]$ gives an irreducible polynomial, since $\sqrt{2}$ is irrational; the same polynomial factors as $(x - \sqrt{2})(x + \sqrt{2})$ over $\mathbb{R}[x]$. A system that doesn't track the ring cannot distinguish these answers — it would have to guess or default to floating-point approximation, silently trading exactness for convenience.

```python
R.<x> = PolynomialRing(QQ, 'x')
f = x^4 - 5*x^2 + 6
print(f.factor())        # (x^2 - 3) * (x^2 - 2) -- irreducible over QQ
print(f.roots())          # [] -- no rational roots

S.<x> = PolynomialRing(QQbar, 'x')  # algebraic closure of QQ
g = S(f)
print(g.roots())          # four exact algebraic-number roots
```

The practical payoff is exact computation with certified correctness. Suppose you need the greatest common divisor of $f(x) = x^3 - x$ and $g(x) = x^2 - 1$ to simplify a rational function $\tfrac{f(x)}{g(x)}$ before integrating it symbolically. Working in $\mathbb{Q}[x]$, `gcd(f, g)` runs the Euclidean algorithm for polynomials — repeated division with remainder, exactly analogous to integer gcd — and returns $x - 1$ (up to a unit), letting you cancel the shared factor and reduce $\tfrac{f(x)}{g(x)}$ to $x(x+1)$ with no rounding error anywhere in the pipeline.

### substitution_evaluation (12.9s)

## Substitution Evaluation

A symbolic expression like $E = mc^2$ or $\int x^2\,dx = \frac{x^3}{3}+C$ carries meaning as a general statement, valid for every value its symbols could take. But at some point you need a number: how much energy does 2 kg of mass release? What is the area under a specific curve between $x=1$ and $x=3$? This is the job of **substitution** — replacing a symbol with a concrete value — followed by **numerical evaluation**, computing the resulting arithmetic. Symbolic systems such as SymPy keep these as two distinct operations, `subs()` and `evalf()` (or `n()`), rather than fusing them, because each step answers a different question and can fail or succeed independently.

`subs(symbol, value)` performs a purely algebraic replacement: it substitutes the value into the expression tree and simplifies where possible, but the result may still be exact and symbolic — for instance, substituting $x = \pi/2$ into $\sin(x)+\sqrt{2}$ gives $1+\sqrt{2}$, not a decimal. `n()` (or `evalf()`) then converts that exact expression into a floating-point approximation, e.g., $1+\sqrt{2} \approx 2.41421356$. Keeping these separate matters: a physics student solving for exact energy in terms of $\pi$ or $\sqrt{g}$ wants to see the exact symbolic answer before deciding whether — and to what precision — to convert it to a decimal.

Worked example: given $f(x) = 3x^2 - 5x + 2$, evaluate $f(4)$.

```python
from sympy import symbols
x = symbols('x')
f = 3*x**2 - 5*x + 2
result = f.subs(x, 4)   # exact: 30
decimal = result.n()     # 30.0000000000000
```

Because $30$ is already an integer, `subs` and `n()` look identical here — but substitute $x = \sqrt{2}$ instead, and `subs` returns $3\cdot2 - 5\sqrt{2}+2 = 8-5\sqrt{2}$, an exact symbolic value, while only `n()` reduces it to $\approx 0.9289$.

This separation becomes essential in problem-solving: when solving equations symbolically (e.g., via a quadratic formula) you often get roots involving radicals; you `subs` known parameters to get an exact closed-form answer first, verify it algebraically, and only call `n()` at the final reporting step — preserving precision and correctness throughout the derivation instead of accumulating rounding error early.

### exact_rational (0.0s)

## Exact Rational

An **exact rational** is a number represented as a ratio of two integers, $\frac{p}{q}$ with $q \neq 0$, stored and manipulated in that form rather than converted to a finite decimal approximation. When you divide 1 by 3 and keep the result as a Rational, you get $\frac{1}{3}$ — not $0.333333$. The value never loses precision, because no rounding step ever occurs; a decimal only appears if you explicitly request one, and even then it's a *view* of $\frac{1}{3}$, not a replacement for it.

This matters because floating-point numbers, which most languages use by default, approximate rationals using finite binary fractions. Some rationals — like $\frac{1}{2}$ or $\frac{1}{4}$ — are exact in binary, but most, including $\frac{1}{3}$ and $\frac{1}{10}$, are not. That's why `0.1 + 0.2` famously evaluates to `0.30000000000000004` in floating-point arithmetic: the inputs were already rounded before the addition happened. An exact rational avoids this entirely by keeping the numerator and denominator as integers and performing arithmetic algebraically.

**Worked example.** Add $\frac{1}{3} + \frac{1}{6}$ using exact rational arithmetic. Convert to a common denominator: $\frac{2}{6} + \frac{1}{6} = \frac{3}{6}$, then reduce by dividing numerator and denominator by their greatest common divisor, $3$: $\frac{3}{6} = \frac{1}{2}$. The result is exactly $\frac{1}{2}$ — not $0.49999999999999994$, which is what naive floating-point addition of the decimal approximations can produce.

**Problem-solving application.** Suppose you're accumulating fractional shares in a financial calculation: $\frac{1}{3} + \frac{1}{3} + \frac{1}{3}$. In floating-point, repeated rounding can leave you with $0.9999999999999999$ instead of $1$ — a discrepancy that compounds over thousands of transactions and can cause audit failures or off-by-a-cent errors at scale. With exact rationals, the sum is computed symbolically: $\frac{1}{3} + \frac{1}{3} + \frac{1}{3} = \frac{3}{3} = 1$, exactly, every time. The lesson generalizes: whenever a computation must preserve mathematical identities (fractions that must sum to exactly $1$, probabilities that must exactly cancel, ratios compared for exact equality), exact rational representation is the correct tool — reserve floating-point for contexts where a bounded, well-understood rounding error is acceptable in exchange for speed.

### number_theory_sage (0.0s)

## Number Theory Sage

Number theory concerns the arithmetic structure of integers — divisibility, primality, and congruences — but its computations quickly outgrow pencil and paper. Factoring a 40-digit number or testing primality of a 300-digit one is infeasible by trial division, yet these operations sit at the core of modern cryptography (RSA, Diffie–Hellman) and algorithm design. Sage wraps the PARI/GP library, a C library purpose-built for number theory, so these industrial-strength computations run at interactive speed inside a readable Python-like syntax.

Four operations anchor this toolkit. `factor(n)` returns the prime factorization of $n$, guaranteed correct by the Fundamental Theorem of Arithmetic: every integer $n > 1$ has a unique expression $n = p_1^{e_1} p_2^{e_2} \cdots p_k^{e_k}$ as a product of primes. `is_prime(n)` certifies primality using a combination of fast probabilistic tests (Miller–Rabin) and deterministic proofs (APR-CL), sidestepping the need to trust a merely "probable" answer. `euler_phi(n)` computes Euler's totient function, $\varphi(n) = \#\{k : 1 \le k \le n,\ \gcd(k,n)=1\}$, which for a factorization $n = \prod p_i^{e_i}$ satisfies

$$
\varphi(n) = n \prod_{p_i \mid n} \left(1 - \frac{1}{p_i}\right).
$$

Finally, `crt(a, b, m, n)` solves the Chinese Remainder Theorem system $x \equiv a \pmod{m}$, $x \equiv b \pmod{n}$ for coprime $m, n$, returning the unique solution modulo $mn$.

These are not independent tricks — they compose. RSA key generation, for instance, needs `is_prime` to find two large primes $p, q$, `euler_phi` to compute $\varphi(pq) = (p-1)(q-1)$ for the private exponent, and `crt` to accelerate decryption via the CRT-optimized RSA algorithm:

```python
p, q = random_prime(2^512), random_prime(2^512)
n = p * q
phi = euler_phi(n)          # = (p-1)*(q-1)
e = 65537
d = inverse_mod(e, phi)
factor(n)                   # infeasible for an attacker without p, q
```

The problem-solving payoff is that Sage lets you verify cryptographic parameters, explore conjectures (e.g., checking Goldbach's conjecture across a range), or prototype an attack on toy-sized keys — all without reimplementing decades of optimized number-theoretic algorithms yourself.

### calculus_sage (0.0s)

## Calculus Sage

Sage extends the symbolic-expression engine to the operations of calculus: differentiation, integration, limits, and series expansion. Each of these is, at its core, an algorithm that transforms one symbolic expression into another according to formal rules — the product rule, the power rule for integration, the epsilon-delta definition of a limit realized as algebraic manipulation. What makes symbolic calculus trustworthy rather than merely suggestive is a built-in consistency check: whenever Sage computes an antiderivative, it verifies the result by differentiating it and confirming that the derivative matches the original integrand. This is a direct, computational enactment of the Fundamental Theorem of Calculus:

$$
\frac{d}{dx}\int_a^x f(t)\,dt = f(x)
$$

**Worked example.** Consider $f(x) = x^2 \sin(x)$. Symbolic differentiation applies the product rule mechanically:

$$
\frac{d}{dx}\left[x^2 \sin(x)\right] = 2x\sin(x) + x^2\cos(x)
$$

Sage arrives at this by decomposing the expression tree — a product node with children $x^2$ and $\sin(x)$ — and applying the stored derivative rule for each node type, then recombining via the product rule. Integrating the same function requires integration by parts twice:

$$
\int x^2 \sin(x)\, dx = -x^2\cos(x) + 2x\sin(x) + 2\cos(x) + C
$$

Sage then differentiates this result symbolically and simplifies, confirming it collapses back to $x^2\sin(x)$. This diff-then-simplify round trip is not a courtesy — it is the mechanism by which a symbolic system self-validates, since integration algorithms (e.g., Risch-style pattern matching) are far more failure-prone than differentiation.

**Problem-solving application.** This verification loop matters most when integrals are found via lookup tables, substitution heuristics, or partial-fraction decomposition, where an error can produce a plausible-looking but wrong antiderivative. Limits and series expansions receive the same treatment: a Taylor series for $e^x\cos(x)$ around $x=0$ is checked by confirming its term-by-term derivative reproduces the series for the derivative of the original function. In practice, this means every symbolic calculus result in a Sage-based workflow carries an automatic certificate: not "trust the algorithm," but "the algorithm checked its own work using the one theorem that ties differentiation and integration together."

### exact_linear_algebra (0.0s)

## Exact Linear Algebra

When Sage builds a matrix over the rationals — `matrix(QQ, [[1, 1/2], [2/3, 1]])` — every subsequent operation is guaranteed exact. Row reduction, kernel computation, and eigenvalue extraction proceed via algorithms that manipulate fractions and algebraic numbers symbolically, never rounding to finite binary precision. This eliminates the central hazard of numerical linear algebra: a matrix with a large condition number producing eigenvalues or a reduced row echelon form (RREF) corrupted by floating-point error. Over $\mathbb{Q}$, the answer Sage returns is *the* answer, not an approximation with an implicit error bar.

**Worked example.** Consider $A = \begin{pmatrix} 4 & 2 \\ 1 & 3 \end{pmatrix}$. Its characteristic polynomial is $\det(A - \lambda I) = (4-\lambda)(3-\lambda) - 2 = \lambda^2 - 7\lambda + 10 = (\lambda - 5)(\lambda - 2)$, giving eigenvalues $\lambda_1 = 5$, $\lambda_2 = 2$ — exact integers, not `4.9999999997`. In Sage: `A = matrix(QQ, [[4,2],[1,3]]); A.eigenvalues()` returns `[5, 2]` exactly. For the eigenspace of $\lambda_1 = 5$, solving $(A - 5I)v = 0$ gives $\begin{pmatrix}-1 & 2 \\ 1 & -2\end{pmatrix}v = 0$, so $v = (2,1)$ spans the kernel — Sage's `.kernel()` returns this basis vector with no rounding whatsoever, even when eigenvalues are irrational (e.g. $\sqrt{2}$), since Sage promotes automatically into an algebraic number field.

**Problem-solving application.** Exactness matters most when a downstream conclusion is qualitative rather than numerical: is a matrix singular, does a homogeneous system have a nontrivial solution, is a given vector actually in the row space? A floating-point computation might report a "determinant" of $10^{-15}$ for a matrix that is exactly singular, tempting a false conclusion of full rank. Over $\mathbb{Q}$, RREF via fraction-free Gaussian elimination reports a pivot count that is unambiguous — rank is a discrete integer, not a threshold judgment call. This makes exact linear algebra the right tool for verifying algebraic identities, checking whether a proposed inverse is truly exact, or confirming a system of linear constraints (as in optimization feasibility) is consistent — cases where "close to zero" and "exactly zero" have entirely different mathematical meanings, and only exact arithmetic can distinguish them.

### plotting_visualization (10.5s)

## Plotting Visualization

Once a symbolic expression is built, plotting it converts the algebra into a picture — not an approximation of the algebra, but a direct rendering of the exact object. A computer algebra system's `plot` command does not "guess" a curve from sampled points the way a calculator might; it evaluates the symbolic expression at enough points to draw a faithful graph, and every point on that graph corresponds to a value the expression actually produces. This matters pedagogically: a picture is a fast, visual proof that a symbolic manipulation was done correctly, and a mismatch between the expected shape and the plotted shape is often the first sign of an algebra error.

**Worked example.** Suppose you have solved for the tangent line to $f(x) = x^3 - 3x$ at $x = 1$, obtaining $f(1) = -2$, $f'(1) = 0$, so the tangent line is $y = -2$. Plotting $f(x)$ and $y = -2$ together on the same axes with `plot(f(x), (x, -2, 2)) + plot(-2, (x, -2, 2), color="red")` should show the red horizontal line just touching the curve at $x=1$ without crossing it — confirming both the derivative computation (slope 0) and the function value. If the line instead crosses the curve, that is immediate evidence of a sign or arithmetic error upstream, well before you'd catch it by re-checking algebra by hand.

**Extending to surfaces and implicit curves.** `plot3d` extends the same principle to functions of two variables, rendering $z = f(x,y)$ as a surface — useful for confirming, say, that a computed critical point is a saddle rather than a local extremum by visually checking whether the surface curves up in one direction and down in another. `implicit_plot` handles relations that are not solved for $y$, such as $x^2 + y^2 = 4$ or a level curve $f(x,y) = c$; instead of evaluating an explicit formula, the system samples the plane and traces where the relation holds, which is essential when an expression cannot be algebraically isolated. In each case, the underlying discipline is the same: the picture is generated from the *exact object itself* — the symbolic expression, not a rounded numerical stand-in — so visualization functions as a genuine check on the correctness of prior symbolic work, catching mistakes that pure algebraic inspection can miss.

### solving_equations (12.1s)

## Solving Equations

Symbolic solving finds exact roots of an equation, expressed as radicals, fractions, or closed-form expressions, rather than decimal approximations. In SPL, the `solve()` function operates over the symbolic ring $\mathbb{Q}[x]$ (or an extension ring containing $\sqrt{\cdot}$, $\pi$, $i$, etc.), so a call like `solve(x**2 - 2, x)` returns $x = \pm\sqrt{2}$, not $x \approx \pm 1.41421$. This matters whenever downstream reasoning depends on exactness — for instance, verifying an identity or feeding a root back into another symbolic expression without accumulating floating-point error.

**Worked example.** Consider $x^2 - 4x + 4 = 0$. Factoring gives $(x-2)^2 = 0$, so $x = 2$ is a root with multiplicity 2 — the graph is tangent to the $x$-axis rather than crossing it. A numeric solver would just report `x = 2.0` once, discarding this structural information. `solve()` preserves it: the returned solution set can be tagged with multiplicity, which is essential in applications like stability analysis (a repeated eigenvalue signals a degenerate mode) or curve-sketching (a repeated root marks an inflection-like tangency, not a sign change).

**Problem-solving application.** Real equations rarely arrive alone — they come with constraints on the domain. Suppose you must solve $\sqrt{x-1} = x-3$. Squaring both sides yields $x-1 = x^2-6x+9$, i.e. $x^2-7x+10=0$, factoring to $(x-2)(x-5)=0$. Blind algebra gives $x=2$ and $x=5$, but $x=2$ fails the original equation ($\sqrt{1}=1 \ne -1$) — it's an extraneous root introduced by squaring. This is where `assume()` becomes the right tool: declaring `assume(x >= 3)` before solving (since $x-3 \ge 0$ is required for the squared equation to be valid) narrows the search space so `solve()` returns only $x=5$ directly, without a manual back-substitution check.

The combination of exact arithmetic and constraint-aware search is what makes symbolic solving more than "algebra by computer": it composes naturally with **simplification** (reducing the equation to a canonical form before pattern-matching for roots) and **substitution/evaluation** (plugging a candidate root back into the original expression to confirm it, or evaluating a solution numerically only at the very last step, once exactness is no longer needed).

### conjecture_loop (12.8s)

## Conjecture Loop

The conjecture loop is the engine of experimental number theory: generate a large batch of exact computations, scan the output for a pattern, then aggressively search for a counterexample before elevating the pattern to a claim. The order matters. A pattern that survives ten cases is a hunch; a pattern you have *tried to break* across ten thousand cases and failed is a conjecture worth someone's time. The loop treats belief as something earned through adversarial testing, not accumulated through repetition.

**Worked example.** Consider the claim that $n^2 + n + 41$ is prime for every nonnegative integer $n$. Using exact-arithmetic tools like Sage, generate values for $n = 0, 1, 2, \ldots, 39$:

$$f(0) = 41,\ f(1) = 43,\ f(2) = 47,\ \ldots,\ f(39) = 1601$$

Every one of these is prime — forty consecutive successes, which feels like overwhelming evidence. But the loop demands you keep pushing, not stop at a comfortable sample size. At $n = 40$:

$$f(40) = 40^2 + 40 + 41 = 1681 = 41^2$$

The pattern breaks. Forty confirmations bought nothing against a single well-placed counterexample, because the formula itself guarantees failure at $n = 41$: $f(41) = 41^2 + 41 + 41 = 41(41+1+1)$, divisible by 41. Plotting $f(n)$ against $n$ and marking composite values in red makes this failure visible at a glance — a good visualization turns "search for a counterexample" from blind guessing into targeted inspection of where the pattern is structurally most likely to fail.

**Problem-solving application.** When you meet a new numerical pattern, apply the loop as a discipline, not a one-off check: (1) compute exactly, not with floating-point approximations that can hide small integer discrepancies; (2) push the range far past where the pattern "feels" confirmed, since many false patterns hold for surprisingly large initial stretches (Euler's polynomial fooled mathematicians for decades); (3) target edge cases suggested by the formula's own structure — values that make a factor vanish, indices near known primes, or boundary conditions — rather than testing randomly; (4) only after failing to break it, state the conjecture precisely and look for a proof. Solving equations exactly and plotting results are not separate skills here — they are the two instruments that make the hunt for counterexamples fast and visible.

## Group Theory Sage

A **group** is a set $G$ with a binary operation satisfying closure, associativity, identity, and inverses. SageMath makes groups computable objects rather than abstract axioms: you construct a group, ask for its order, and inspect its structure interactively — turning group theory from proof-writing into experimentation.

**Permutation groups** act on finite sets. The symmetric group $S_n$ contains all $n!$ permutations of $n$ objects:

```python
S = SymmetricGroup(4)
S.order()                    # 24
A4 = AlternatingGroup(4)     # even permutations only
A4.order()                   # 12
```

A permutation like $(1\,2\,3)$ cycles $1\to2\to3\to1$. Sage composes, inverts, and decomposes these directly — no need to hand-multiply cycle notation.

**Matrix groups** realize symmetry via linear transformations. $GL(n,\mathbb{F})$, the group of invertible $n\times n$ matrices over a field $\mathbb{F}$, and its subgroup $SL(n,\mathbb{F})$ (determinant 1) are standard examples:

```python
G = GL(2, GF(5))
G.order()                    # 480
```

This connects group theory to linear algebra: matrix multiplication is the group operation, and the determinant gives a homomorphism $GL(n,\mathbb{F}) \to \mathbb{F}^\times$.

**Worked example — subgroup lattice and centers.** Take the dihedral group $D_4$ (symmetries of a square, order 8):

```python
D4 = DihedralGroup(4)
D4.center()                       # {e, r^2}, order 2
D4.subgroups()                    # full subgroup lattice
D4.is_abelian()                   # False
```

The center $Z(D_4) = \{g \in D_4 : gh = hg \ \forall h \in D_4\}$ contains only the identity and the $180°$ rotation — reflections don't commute with rotations, so $D_4$ is non-abelian even though it has abelian subgroups (e.g., the rotation subgroup $\cong \mathbb{Z}/4\mathbb{Z}$).

**Problem-solving application.** Sage delegates heavy group-theoretic computation to **GAP** (Groups, Algorithms, Programming), accessible via `gap.eval()` or Sage's `libgap` interface. This matters for research-scale problems: classifying groups of a given order, computing conjugacy classes, or testing isomorphism between two groups with millions of elements — tasks infeasible by hand but routine for GAP's algorithms. For instance, `libgap.StructureDescription(G)` returns a human-readable decomposition (e.g., `"D8"` or `"C2 x C2"`), letting you identify an unknown group's isomorphism type computationally rather than through a multi-page proof.

## Manifolds Geometry

A manifold is a space that looks locally like $\mathbb{R}^n$ but may be curved or connected in complicated ways globally — a sphere, a torus, or spacetime itself. To do calculus on it, you need a **chart**: a smooth invertible map $\varphi: U \to \mathbb{R}^n$ that assigns coordinates to points in an open patch $U$. A **metric tensor** $g_{ij}$ then encodes how to measure lengths and angles at each point, and a **connection** $\nabla$ tells you how to differentiate vectors consistently as you move across the manifold, since "constant vector field" has no meaning without a rule for comparing tangent spaces at different points. Curvature — captured by the Riemann tensor $R^{\rho}{}_{\sigma\mu\nu}$ — measures the failure of this transport to be path-independent: parallel-transport a vector around a small loop and it comes back rotated by an amount proportional to curvature.

SageManifolds turns these abstractions into executable objects. Define a 2-sphere as a manifold, install a chart via stereographic or spherical coordinates, declare the round metric $g = d\theta^2 + \sin^2\theta\, d\phi^2$, and Sage computes the Levi-Civita connection automatically by solving

$$
\Gamma^k_{ij} = \tfrac{1}{2} g^{kl}\left(\partial_i g_{jl} + \partial_j g_{il} - \partial_l g_{ij}\right)
$$

symbolically — the same formula you'd derive by hand, but exact and error-free for arbitrary coordinate choices. From there, `metric.riemann()` and `metric.ricci_scalar()` return the curvature tensors as fully simplified expressions, letting you verify that the sphere has constant positive curvature $R = 2/a^2$ for radius $a$ without touching an index by hand.

The problem-solving payoff is in comparing geometries. Suppose you want to check whether two metrics — one given in Cartesian-like coordinates, one in an unfamiliar parametrization — describe the same underlying manifold. Compute each Ricci scalar and Gaussian curvature in Sage; if they agree as functions of position after accounting for the coordinate change, the metrics are isometric. This is exactly how physicists distinguish genuine spacetime curvature from an artifact of a bad coordinate system, and how geometers classify surfaces by curvature invariants rather than by their coordinate description — a task that is essentially unmanageable by hand once the metric has more than a few nonzero components, but routine once the manifold's charts, metric, and connection are declared as data.

### experimental_mathematics (11.3s)

## Experimental Mathematics

Mathematics is usually taught as a deductive science: state axioms, apply logic, arrive at a proven theorem. But historically — and increasingly today with computer algebra systems like SageMath — mathematicians also work inductively, the way physicists or biologists do. They form a **conjecture** from patterns observed in data, test it computationally against many cases, and only *then* attempt a formal proof. This cycle — conjecture, compute, falsify or believe, prove — is the engine of experimental mathematics, and it reframes theorem-proving as the final stage of a discovery process rather than its entirety.

**The conjecture loop.** Suppose you want to understand how the number of subgroups of a finite group relates to its order. Rather than starting from group-theoretic axioms, you generate many groups in Sage — cyclic groups, dihedral groups, symmetric groups — and tabulate the subgroup count against $|G|$. A pattern might emerge: for $G = \mathbb{Z}_n$, the number of subgroups equals $d(n)$, the number of divisors of $n$. This is now a *conjecture*, not a theorem. The next step is falsification: test it against every cyclic group up to order 500. If it survives, confidence rises; if a counterexample appears, the conjecture is revised or discarded. Only after this computational stress-test is it worth attempting a rigorous proof — here, an easy one via the correspondence between subgroups of $\mathbb{Z}_n$ and divisors of $n$, since every subgroup of a cyclic group is itself cyclic, generated by an element of order $d \mid n$.

**Geometric experiment.** The same loop applies to manifolds and geometry. Computing Gaussian curvature numerically over a triangulated surface lets you conjecture a global relationship — say, that total curvature relates to Euler characteristic — before recognizing it as the Gauss–Bonnet theorem, $\int_M K \, dA = 2\pi \chi(M)$. The computation doesn't replace the proof; it tells you *what* is true so you know what to prove.

**Problem-solving application.** In Sage, this loop is a workflow: write a `for` loop over a parameterized family, extract invariants (order, genus, curvature), inspect the resulting sequence against OEIS or symbolic simplification, and hand the surviving conjecture to a proof assistant like Lean for formal verification. Experimental mathematics doesn't lower rigor — it relocates the expensive, human effort of proof-search to exactly the conjectures that have already earned it.

### math_research (11.2s)

## Math Research

Mathematical research once meant a lone mathematician staring at small cases on paper until a pattern revealed itself. Today, exact computation lets researchers generate thousands of instances of a mathematical object, compute an invariant for each one exactly — not approximately — and search the resulting data for a pattern that no proof yet explains. This is conjecture-hunting at scale: the computer does not prove theorems, but it produces the evidence that tells a mathematician which theorem is worth trying to prove.

The key requirement is exactness. A floating-point computation that is off by $10^{-9}$ can hide or fabricate a pattern; a symbolic or arbitrary-precision computation cannot. Software like SageMath, PARI/GP, or Mathematica can compute, say, the exact rank of an elliptic curve, the exact value of a partition function $p(n)$, or the exact factorization of a large integer, for thousands of inputs in a loop. The researcher then looks at the resulting table — not to find an approximate trend, but to spot an identity or divisibility rule that holds with zero exceptions across every computed case.

A worked example: Ramanujan's congruences for the partition function. By tabulating $p(n)$ exactly for $n$ up to several hundred, one notices that $p(5n+4) \equiv 0 \pmod{5}$ holds in every single row. A single exception would kill the pattern instantly, which is why exact arithmetic is non-negotiable — a numerical approximation could never establish or refute a congruence. The pattern, once seen, becomes the target of a proof; Ramanujan's original congruences were later proved rigorously, and the computational search for further congruences of this type continues today.

The experimental loop that this enables has a repeatable shape: (1) generate a large, exact dataset over some family of objects; (2) compute a candidate invariant for each; (3) search programmatically for regularities — equalities, divisibilities, inequalities that never fail; (4) state the pattern as a formal conjecture, with exact bounds and quantifiers, not a vague trend; (5) attempt a proof, or search for the specific counterexample that would disprove it. In problem-solving practice, this means a student or researcher treats the computer as a hypothesis generator: run the loop over a specific family, log every exact output, and only promote an observation to a conjecture once it has survived an aggressive, exact search for counterexamples.
