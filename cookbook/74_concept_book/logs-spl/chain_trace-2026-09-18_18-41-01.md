### term (0.0s)

## Term

A **term** is any expression that inhabits a type — a concrete piece of data, a computation, or (in dependently typed systems) a proof, all classified by what kind of thing it is. Writing $t : T$ means "term $t$ has type $T$." Under this reading, $3 : \mathbb{N}$, $\lambda x.\,x+1 : \mathbb{N} \to \mathbb{N}$, and, in a system rich enough to express propositions as types, a proof $p : (n = n)$ are all terms — they differ wildly in what they *are*, but each is judged well-formed and slots into its type the same way a value slots into a variable. Naming a term with `def`, as in `def three := 3`, does not create a new kind of object; it just gives the term `3` (already of type $\mathbb{N}$) a handle you can reuse.

**Worked example.** Take `def add1 := λx. x + 1`. To check this term, a type checker assumes $x$ has type $\mathbb{N}$, then checks the body `x + 1` under that assumption; since addition of naturals returns a natural, `x + 1` has type $\mathbb{N}$, so the whole function $\lambda x.\,x+1$ has type $\mathbb{N} \to \mathbb{N}$. The `def` merely names this term `add1`; every later use of `add1` is definitionally the same term as $\lambda x.\,x+1$, and the checker may freely unfold one into the other.

**Problem-solving application.** This uniform treatment — everything is a term, checked against a type — is what makes the Curry–Howard correspondence work: a proposition is a type, and a proof is a term of that type, checked by the *same* process used for programs. Proving $A \to A$ true is literally the same act as writing a term of type $A \to A$ — namely $\lambda x.\,x$ — and checking that term *is* checking the proof. Practically, this means a proof assistant that rejects your proof is rejecting a term for failing to match the goal type, exactly as it would reject `def bad : ℕ := "hello"` for producing a string where a natural number was expected. So debugging a rejected proof uses the same skill as debugging rejected code: identify what type is expected, identify what type your term actually has, and find where the mismatch enters.

### type (0.0s)

## Type

Every expression in Lean has a type, and the type tells Lean — and you — exactly what the expression is and what you're allowed to do with it. Write `#check 5` and Lean answers `5 : Nat`; write `#check "hello"` and it answers `"hello" : String`. The colon reads "has type": the object on the left belongs to the category on the right. This isn't a comment or a suggestion — it's a guarantee Lean checks mechanically before it will accept anything you write. If you claim `5 : String`, Lean rejects it outright, because `5` genuinely is not a member of the string type.

Types matter because they determine which operations make sense. `Nat` (natural numbers), `Int`, `Bool`, and `String` are the basic types you'll meet first, and every value you construct in Lean belongs to exactly one of them. `#check` is your tool for asking, at any point, which type a given expression has — you don't need to guess or read documentation, you just ask Lean directly.

Types become essential once you try to combine pieces. Suppose Lean has a built-in operation that expects a `Nat` — say, doubling a number — and you hand it a `String` instead, like `"three"`. Lean immediately reports a type mismatch: the operation expects a `Nat`, but you supplied a `String`. This is the payoff of a typed language — the error surfaces the moment you write the mistake, not later when the program runs on bad data. Compare this to writing the same logic in an untyped language, where doubling `"three"` might silently produce `"threethree"` or crash deep inside unrelated code far from where the bad value originated.

This same checking is what makes Lean trustworthy as a proof assistant, not just a programming language: it can verify that a mathematical claim is built correctly for exactly the reason it can verify that a number is used where a number is expected. You'll see how that works once you learn how Lean represents statements and proofs — for now, the idea to hold onto is simpler: everything in Lean has a type, and `#check` is how you ask what it is.

### proposition (0.0s)

## Proposition

A proposition is a mathematical claim treated as a first-class object — something you can name, store in a variable, pass to a function, and combine with logical connectives, before you ever decide whether it is true. In classical logic, a proposition is just a statement with a truth value: true or false, and nothing else. But in the type-theoretic view used by proof assistants like Lean and Coq, a proposition is a *type*, and a proof of that proposition is a *term* — a piece of evidence — that belongs to that type. This identification is the Curry–Howard correspondence: propositions correspond to types, and proofs correspond to terms inhabiting them. "$P$ is true" becomes "the type $P$ is inhabited" — you can exhibit some object of type $P$.

Concretely, consider the proposition $P : \text{“for all naturals } n, \, n + 0 = n\text{”}$. In a proof assistant this is written as a type:
$$P : \forall n : \mathbb{N}, \, n + 0 = n$$
A proof of $P$ is a term $p : P$ — an object, built by induction, that produces evidence for every $n$ that $n + 0 = n$. If no such term exists, $P$'s type is empty, and the proposition is false or at least unproved. This is why propositions are called "first-class": they aren't external labels attached to statements, they *are* the statements, living in the same universe as the data your program manipulates.

Worked example: take the proposition $\text{Even}(4)$, meaning "4 is divisible by 2." Proving it does not require inventing new logical machinery — it just requires exhibiting a term of the type $\text{Even}(4)$. Concretely, the term is the evidence "$4 = 2 \times 2$": a specific calculation that inhabits the type. The proposition is true precisely because that term exists and type-checks; if you could not produce such a term, $\text{Even}(4)$ would remain unproved.

For problem-solving, this framing turns proof search into type search: to prove a proposition, you don't manipulate abstract truth values — you construct a term and check that it has the right type. When stuck on a proof, ask "what type am I trying to inhabit, and what term would count as evidence for it?" This reframes logical reasoning as concrete, checkable construction, the same discipline as writing a program that must type-check before it runs.

### function_types (0.0s)

## Function Types

A function type has the form $A \to B$: it describes a transformation that consumes a term of type $A$ and produces a term of type $B$. This is the core building block of typed languages, because nearly every computation — arithmetic, string processing, control flow — is ultimately a function applied to an argument. The corresponding term is written using lambda notation, `fun x => e`, where `x` is the parameter and `e` is an expression built from `x` that produces the result. If `x : A` and `e : B`, then `fun x => e : A -> B`.

**Worked example.** Consider a function that doubles an integer:

$$
\texttt{double} : \mathbb{Z} \to \mathbb{Z} \qquad \texttt{double} = \texttt{fun } x \Rightarrow x + x
$$

The type $\mathbb{Z} \to \mathbb{Z}$ tells you, before running anything, that `double` accepts one integer and returns one integer — it cannot be applied to a string or to zero arguments. *Application* is the operation that uses this: given `double : Z -> Z` and `5 : Z`, applying `double 5` yields `10 : Z`. The type checker verifies application by matching the argument's type against the function's input type; a mismatch (e.g., `double "hi"`) is rejected before the program ever runs. This is why function types matter for problem-solving: they let you decompose a task into a pipeline of typed transformations and catch wiring errors statically, rather than as runtime crashes.

**Problem-solving application.** Suppose you need a function that checks whether an integer is even, then routes it to one of two string-producing functions. You'd type this as `isEven : Z -> Bool`, `describeEven : Z -> String`, `describeOdd : Z -> String`, and combine them with a conditional whose branches must both return `String` — the shared return type is enforced by the type system, not by convention. More generally, function types compose: given `f : A -> B` and `g : B -> C`, you can build `g ∘ f : A -> C` by feeding `f`'s output into `g`, and the types alone confirm the composition is legal without inspecting either function's implementation. This is the practical payoff of treating "function" as a type-and-term pair: the type is a contract you can check mechanically, and the term is the concrete recipe that fulfills it.

### curry_howard (0.0s)

## Curry Howard

The Curry-Howard correspondence establishes that a proposition and a type are the same object, and that a proof and a program are the same object. The core primitive that makes this concrete is the function type: proving "if $A$ then $B$" is identical to constructing a function of type $A \to B$. A proof is not a separate certificate that a program is correct — the program *is* the proof, and the type checker that accepts the program is simultaneously a proof checker. (The same correspondence extends to "and" and "or," pairing conjunction with a paired-value type and disjunction with a either-branch type, but the function type alone is enough to see how the correspondence works.)

**Worked example.** Consider the proposition "if $A$ implies $B$, and $B$ implies $C$, then $A$ implies $C$" — transitivity of implication. Its type is
$$(A \to B) \to (B \to C) \to (A \to C).$$
A term inhabiting this type is exactly a proof:
$$\lambda f.\, \lambda g.\, \lambda x.\, g\,(f\,x)$$
where $f : A \to B$, $g : B \to C$, $x : A$. Reading this as a program: given a function $f$ from $A$ to $B$ and a function $g$ from $B$ to $C$, compose them by applying $f$ to $x$ and feeding the result to $g$. Reading the exact same expression as a proof: assume $A$ (introduce $x$), apply the hypothesis $f$ to derive $B$, apply the hypothesis $g$ to derive $C$, discharge the assumption. The typechecker's verdict that this term has type $(A \to B) \to (B \to C) \to (A \to C)$ *is* the verification that the transitivity proof is valid. No separate "proof theory" layer runs — the same kernel that accepts well-typed programs accepts valid proofs.

**Problem-solving application.** The correspondence turns theorem-proving into program-writing, and vice versa, entirely through the function type. To prove "$A$ implies $A$" (reflexivity), you must produce a term of type $A \to A$; the identity function $\lambda x.\, x$ is both the program and the proof — nothing else needs to be checked, because the type system itself guarantees that whatever value of type $A$ goes in, a value of type $A$ comes out. Conversely, to prove that an implication is *unprovable* under constructive logic, one must show that no term of the corresponding function type can be built — the type is uninhabited. This is why proof assistants such as Coq, Agda, and Lean are, at the type-checking level, ordinary compilers: verifying a mathematical proof and compiling a program are literally the same act, performed by the same algorithm, one function-type check at a time.

### proof (0.0s)

## Proof

In type theory, a **proof** is not a separate kind of mathematical object sitting outside the type system — it is a term. Under the Curry-Howard correspondence, a proposition $P$ is itself a type, and to prove $P$ is to exhibit some term $p$ such that $p : P$. The type checker's kernel, the same small piece of code that verifies ordinary program terms have their declared types, verifies proofs by exactly the same mechanism: it checks that $p$ really does have type $P$. There is no separate "proof checker" — proof checking *is* type checking. This single idea — that a proof is just a term of the proposition's type — is the only new primitive this section introduces; everything below is a consequence of it.

**Worked example.** Consider proving $P \to P$, "if $P$ holds, then $P$ holds." Since implication corresponds to the function type, a proof of $P \to P$ is simply a function that takes a term of type $P$ and returns it unchanged:
$$
\lambda (p : P).\ p
$$
The kernel checks this the same way it checks any lambda: it confirms that given an argument of type $P$, the body returns a term of type $P$. No separate "logical" reasoning engine is invoked — the ordinary rule for checking function application *is* the logical inference here. Constructing a proof of a more elaborate implication $A \to B$ works identically: you write a function that consumes a term of type $A$ and, through whatever computation is needed, produces a term of type $B$; the kernel accepts the proof exactly when that function type-checks.

**Problem-solving application.** This identification lets you debug a broken proof exactly as you'd debug a program: a type error from the kernel — "expected term of type $B$, got term of type $A$" — pinpoints precisely which step of the argument is unjustified. Because a proof is nothing more than a term built by ordinary means (applying functions, substituting values, reducing expressions), the strategy for finding one is the same strategy you already use to write code that satisfies a target type: look at what type you need to produce, and work backward to what inputs and operations can produce it. The proposition tells you the type of the object you're hunting for; building the proof is the same skill as writing any other well-typed program.

### theorem_statements (0.0s)

## Theorem Statements

A theorem statement is a formal proposition — a claim about mathematical objects that has been proven true. In the Curry-Howard correspondence, a theorem statement is more than an assertion: it is a *type*. The proposition "if $A$ then $B$" corresponds to the type of functions from $A$ to $B$, written $A \to B$. To state a theorem is to specify a type signature; to prove it is to construct a term that inhabits that type. This single idea — propositions as types, proofs as terms — is the foundation on which proof assistants like Lean and Coq are built: checking a proof reduces to type-checking a program.

**Worked example.** Consider the theorem "for all natural numbers $n$, if $n$ is even then $n+2$ is even." As a type signature this becomes:

$$
\text{thm} : \forall n : \mathbb{N},\ \text{Even}(n) \to \text{Even}(n+2)
$$

Here $\text{Even}(n)$ is itself a type — a term of this type consists of a number $k$ together with the fact that $n = 2k$. The theorem says: given any $n$ and a term of type $\text{Even}(n)$, produce a term of type $\text{Even}(n+2)$. The proof is a function that does exactly this: from a given $k$ with $n = 2k$, it builds $k+1$ together with the fact that $n+2 = 2(k+1)$. In Lean-style pseudocode:

```
theorem even_add_two (n : Nat) (h : Even n) : Even (n + 2) :=
  let ⟨k, hk⟩ := h
  ⟨k + 1, by rw [hk]; ring⟩
```

The line `let ⟨k, hk⟩ := h` unpacks $h$ into its two pieces, $k$ and the fact $hk$, exactly as a function would read off the fields of an argument it was handed.

**Problem-solving application.** This correspondence changes how you *write* a proof: instead of asking "why is this true?" you ask "what function turns the given input types into the required output type?" Applied to the example above, the entire proof is nothing but: unpack the input, add one to the witness, adjust the equation. No cleverness is needed — only matching the shapes correctly. When your proof "doesn't type-check," the theorem-prover is telling you precisely where your reasoning has a gap, the same way a compiler flags a type mismatch in ordinary code. Practicing theorem statements as type signatures is the habit that makes formal proof tractable: decompose the goal type, find or build terms of the required subtypes, and assemble them — proof by construction, not by inspiration.

### tactic_mode (0.0s)

## Tactic Mode

In an interactive theorem prover such as Lean or Coq, a proof is not written as a finished paragraph — it is built one step at a time against a goal state that the system tracks for you. The goal state shows the statement still to be proved, along with the hypotheses currently available. A tactic is a command that transforms this goal state: it may split one goal into several, use a hypothesis to close a goal outright, or rewrite the goal into an equivalent, simpler form. The sequence of tactics you issue, from the original theorem statement to the empty goal list, is the proof — a transcript of the reasoning, executed and checked line by line.

Consider proving $\forall n \in \mathbb{N},\ n + 0 = n$ in Lean. The initial goal state reads `⊢ n + 0 = n`. The tactic `induction n with | zero => rfl | succ k ih => simp [ih]` transforms this single goal into two subgoals: the base case `⊢ 0 + 0 = 0`, closed immediately by `rfl` since it reduces to the same term on both sides; and the inductive case `⊢ k + 1 + 0 = k + 1` with hypothesis `ih : k + 0 = k` available, closed by `simp` rewriting using `ih`. Once both subgoals vanish, the goal list is empty and the proof is complete — Lean reports "no goals," and the tactic script itself stands as the checked proof.

This mechanism matters because it turns proof-writing into a *problem-solving* activity with immediate feedback: after every tactic, you see exactly what remains, so you can choose the next step based on the actual state rather than holding the whole argument in your head. Suppose you are stuck proving $\forall n,\ n \le n + 1$. Applying `intro n` gives goal `⊢ n ≤ n + 1`; applying `exact Nat.le_succ n` closes it directly by citing an existing lemma, no induction needed. If a mismatch appears — say the goal is `⊢ n + 1 ≤ n + 1 + 0` — a tactic like `simp` will normalize `n + 1 + 0` to `n + 1` before you decide how to finish. Because each tactic is a small, checkable transformation, mistakes surface immediately at the step that introduced them, rather than at the end of a long hand-written proof — making tactic mode as much a debugging tool for logic as it is a proof-construction language.

### core_tactics (0.0s)

## Core Tactics

A **tactic** is a command that transforms a proof goal into zero or more simpler subgoals, or closes it outright. A proof in a system like Coq, Lean, or Isabelle is not a static object you hand-assemble; it is a sequence of tactic applications that incrementally rewrite the goal state until nothing remains to prove. This section introduces the first and most fundamental tactic, `intro`; later sections build on it with `exact`, `apply`, `constructor`, and `cases`, each of which manipulates the goal state in its own characteristic way.

**`intro`** moves a hypothesis from the goal into the context. If the goal is $P \to Q$, the implication itself is not something you can act on directly — you first need `P` as an assumption you can reason from. `intro h` strips off the implication, adding `h : P` to the context and leaving `Q` as the new goal. The same tactic handles universal quantification: if the goal is $\forall x, P(x)$, `intro x` introduces a fresh variable `x` into the context and reduces the goal to `P(x)`. In both cases the effect is the same — a binder at the front of the goal disappears, and its bound object becomes something the context can name and use.

Consider proving $\forall n : \text{Nat}, n = n$ in Lean. The goal begins as a universally quantified statement, so `intro n` is the only tactic whose shape matches: it consumes the $\forall$, introduces `n : Nat` into the context, and leaves the new goal `n = n`. Nothing has been proved yet — `intro` never closes a goal on its own — but the quantifier that was blocking further progress is gone, and the goal is now stated purely in terms of an object already in scope.

The problem-solving discipline `intro` teaches is the first step of goal-directed reasoning: before choosing any other tactic, check whether the goal's outermost structure is a binder — an implication or a quantifier — because as long as it is, no other tactic can touch what lies underneath. Only once `intro` has stripped away every such binder does the goal expose the structure (a conjunction, an equality, an inductive hypothesis) that the remaining tactics are built to attack.

### equality_rfl (0.0s)

## Equality Rfl

In type theory, equality is not merely a claim checked by an outside judge — it is itself a *type*, written $a = b$ (or $\mathrm{Eq}\ a\ b$), whose inhabitants are the proofs that $a$ and $b$ are equal. To prove $a = b$, you must produce a term that lives in this type. The simplest possible such term comes from reflexivity: for any $a$, the value $a$ is trivially equal to itself. This gives the constructor `rfl`, short for "reflexivity," which builds a proof of $a = a$ for free — no argument required beyond the fact that both sides are the same term.

The subtlety, and the reason `rfl` is more powerful than it first appears, is that the equality checked here is *definitional* equality, not merely syntactic identity. Two expressions count as the same for `rfl` if they reduce — via computation, unfolding definitions, and pattern matching — to the identical normal form. This is why `2 + 2 = 4` is provable by `rfl`: the typechecker evaluates $2+2$ using the recursive definition of addition on natural numbers, reduces it step by step until it reaches the term $4$, and then observes that both sides of the equation are now syntactically identical. No algebraic manipulation, no external proof — the computation *is* the proof.

**Worked example.** Consider proving `2 * (3 + 4) = 14` in a language like Lean or Agda. Even though the two sides look nothing alike on the page, `rfl` succeeds: the typechecker first reduces the inner sum `3 + 4` to `7`, then reduces the product `2 * 7` to `14`, following the same recursive definitions of addition and multiplication used earlier. Since both sides normalize to the literal `14`, the equality holds definitionally — no matter how many nested steps of unfolding it takes to get there.

**Problem-solving application.** When you attempt a proof and are unsure how much manual work is needed, always try `rfl` first — it costs nothing and often closes goals involving concrete computations on literals. When `rfl` fails, the error itself is diagnostic: it tells you the two sides did *not* reduce to a common form, signaling that the equality depends on a variable, an unproven lemma, or a case split — meaning you need induction, rewriting, or a more general theorem beyond raw computation.

### inductive_types (0.0s)

## Inductive Types

An inductive type is a data type defined entirely by listing its constructors — the finite set of ways a value of that type can be built. There is no separate mechanism for "what counts as a `Nat`" beyond the rule that every natural number is either `zero` or `succ n` for some natural number `n` already built:

```
inductive Nat where
  | zero : Nat
  | succ : Nat → Nat
```

This is the whole definition. `zero` is a constructor taking no arguments; `succ` takes one `Nat` and produces a new one. The number 3 is not a primitive — it is `succ (succ (succ zero))`. `List` and `Bool` follow the same pattern: `Bool` has two nullary constructors (`true`, `false`), and `List α` has `nil : List α` and `cons : α → List α → List α`. None of these are compiler magic; a student could write all three in an afternoon.

**Worked example.** Define addition on `Nat` by pattern-matching on the constructors of the first argument — this is the definitional payoff of having listed the constructors explicitly:

```
def add : Nat → Nat → Nat
  | Nat.zero,   m => m
  | Nat.succ n, m => Nat.succ (add n m)
```

Every case of `add` corresponds to exactly one constructor of `Nat`, and the recursive call `add n m` is made on a strictly smaller argument (`n` instead of `succ n`). This is not a stylistic choice — the type checker requires it. Because `Nat` has no constructor that produces a "smaller-than-`zero`" value, recursion following the constructors is guaranteed to terminate, which is why inductive types double as a termination-checking discipline, not just a data layout.

**Problem-solving application.** Suppose you need a `length` function for `List α`. Since `List` has exactly two constructors, `length` needs exactly two cases:

```
def length : List α → Nat
  | List.nil       => Nat.zero
  | List.cons _ xs => Nat.succ (length xs)
```

This pattern — one function clause per constructor, recursive calls only on constructor arguments — is the general recipe for writing any function over an inductive type, and it is also how the type checker verifies that a `match` expression is *exhaustive*: it checks your clauses against the constructor list, not against your intentions. Missing a case (e.g., forgetting `List.nil`) is a compile error, not a runtime bug waiting to happen.

### rewriting_simp (0.0s)

## Rewriting Simp

Once you have proven a lemma of the form $a = b$ (or an iff $P \leftrightarrow Q$), the tactics `rw` and `simp` let you use that equation to transform the current goal, rather than re-deriving facts by hand. Both work by *substitution*: given $h : a = b$, `rw [h]` finds an occurrence of $a$ in the goal and literally replaces it with $b$, using the underlying justification that equal terms can be swapped anywhere (the `Eq.mpr`/`rfl`-based rewriting built into the kernel). This is the mechanized version of the substitution property of equality you use implicitly in ordinary algebra when you replace $x$ with $2$ after showing $x = 2$.

**Worked example.** Suppose the goal is $n + 0 + m = m + n$, and you have the library lemma `add_zero : n + 0 = n`. Writing `rw [add_zero]` scans the goal, finds the subterm $n + 0$, and rewrites it to $n$, leaving the goal $n + m = m + n$ — now closable by `add_comm` or another `rw`. If the equation instead needs to be applied right-to-left, `rw [← add_zero]` reverses the direction. Chaining several rewrites, `rw [h1, h2, h3]`, applies them in sequence, each acting on the result of the last.

`simp` automates this process at scale. Rather than naming one lemma, it applies a large, curated database of equations and iff-lemmas — tagged `@[simp]` by the community because they are simplifying (e.g., $n + 0 = n$, $P \wedge \text{True} \leftrightarrow P$, $\neg\neg P \leftrightarrow P$) — repeatedly, in whatever order closes or simplifies the goal, stopping when no further rule applies. This is powerful but less predictable than `rw`: two proofs using `simp` may take different paths through the rule set as the library evolves.

**Problem-solving strategy.** Use `rw` when you know exactly which equality is needed and want a transparent, reproducible step — good for goals with one or two specific substitutions. Reach for `simp` when the goal is cluttered with routine arithmetic or logical simplifications (zeros, double negations, trivial conjunctions) that would take many tedious `rw` calls; you can also restrict it with `simp only [h1, h2]` to combine `rw`'s precision with `simp`'s automatic repetition, or add `simp [h]` to include your own lemma `h` in the simplification set for a single goal.

### typeclasses_structures (0.0s)

## Typeclasses Structures

A `structure` in a proof assistant packages a collection of data together with the properties that data must satisfy, all as one bundled object. When mathematicians write "let $G$ be a group," they are implicitly asserting the existence of a set $G$, a binary operation $\cdot: G \times G \to G$, an identity element $e$, inverses, and proofs that these satisfy associativity, identity, and inverse laws. A `structure` formalizes this bundling: instead of carrying five separate hypotheses through every theorem, you define one type, `Group`, whose fields are exactly the carrier set, the operation, and the axiom proofs. A term of type `Group` *is* a complete group, packaged.

The bundling only becomes practical because instances of a structure can be found automatically rather than passed by hand. You register, once, that "$\mathbb{Z}$ under addition is a group" or "invertible $n \times n$ matrices form a group," and afterward the compiler silently retrieves the correct structure whenever a theorem needs it. This is why a theorem can be stated as `theorem lagrange [Group G] (H : Subgroup G) : ...` — the bracket notation `[Group G]` means "assume some group structure on $G$ exists," and the system supplies the specific one automatically instead of the author threading it through every call site.

The payoff appears when structures compose. A `Ring` is built from an `AddGroup` structure plus a multiplicative structure with distributivity; a `Field` extends a `Ring` with multiplicative inverses. Automatic instance retrieval chains through these extensions: if $G$ is known to be a field, the system also supplies its ring structure and its additive group structure without being asked twice, and any theorem proved for groups applies to $G$ for free. Concretely, this relies on the same machinery as [[inductive_types]] — a `structure` is itself an inductive type with one constructor bundling its fields — and functions between structures are ordinary [[function_types]], so proving a lemma about `Group.mul` is proving a fact about a function packaged inside a type. Solving a problem like "show $\mathbb{Z}_n^\times$ is a group" reduces to constructing the four required fields once; every subsequent theorem you invoke then finds and reuses that group's structure on its own.

### mathlib (0.0s)

## Mathlib

Mathlib is Lean's community-maintained mathematics library — over one million lines formalizing everything from basic arithmetic to schemes and measure theory. Its scale creates a distinctive skill: writing a proof in mathlib is often less about deriving new mathematics than about *finding* a lemma that already establishes what you need, then assembling existing pieces. Mathlib rewards library literacy as much as mathematical insight.

**Naming conventions as a search algorithm.** Mathlib names follow strict, predictable rules so that a lemma's statement can often be guessed from its name. A theorem of the form "$A$ implies $B$" is typically named `A_of_B` or describes the conclusion first, with hypotheses trailing; `add_comm` states $a + b = b + a$, `mul_le_mul_left` bounds a product after left-multiplication, and `Nat.succ_pos` gives $n + 1 > 0$ for naturals. Underscores separate the operation (`add`, `mul`, `le`), the object (`Nat`, `Finset`, `Continuous`), and modifiers (`left`, `iff`, `of_pos`). This is why "learning to find a lemma is learning mathlib": once you internalize the convention, you can often type a plausible name and have Lean's autocomplete or `exact?` tactic confirm it exists.

**Worked example.** Suppose you want to prove $(a+b)^2 = a^2 + 2ab + b^2$ for real numbers. Rather than expanding by hand, you search for `sq_add` or `add_sq`, and mathlib has `add_sq : (a + b) ^ 2 = a ^ 2 + 2 * a * b + b ^ 2`, closing the goal in one line: `exact add_sq a b`. The proof-writing skill here was retrieval, not derivation.

**Problem-solving application.** When no exact lemma exists, the practical workflow is: state your goal, run `exact?` or `apply?` to search the library semantically, and if that fails, use `simp` with a curated lemma set (`simp [add_comm, mul_assoc]`) to normalize both sides until they match — this is where mathlib's naming conventions and its rewriting infrastructure (simp lemmas) meet. A student proving inequalities in real analysis, for instance, will lean on `gcongr` and lemma families like `div_le_div_of_nonneg_left` located precisely because their names encode their content. Mastering mathlib means building a mental index of these families, not memorizing individual proofs.

### proof_search (0.0s)

## Proof Search

A theorem statement rarely appears in isolation — most facts a proof needs (associativity, monotonicity, a known inequality) already exist somewhere in mathlib, Lean's mathematical library of over a million lines. Proof search is the practice of querying that library rather than reproving what is already there. The core tool for this is the tactic `exact?`. Given a goal, `exact?` searches mathlib (plus your local hypotheses) for a single lemma or term that closes the goal exactly, and if it succeeds it prints the lemma name so you can paste it directly into your proof, replacing the search call with a permanent, checked citation.

Consider proving $n < n + 1$ for a natural number $n$. Typing `exact?` at that goal searches mathlib's ordered-arithmetic lemmas and returns `exact Nat.lt_succ_self n`. Without search, a novice might reach for `omega` or hand-roll an induction; the tactic instead surfaces the exact library fact, saving both effort and proof size. `exact?` only succeeds when a single lemma closes the goal outright — if no such lemma exists, it reports failure rather than offering partial matches, so it works best once the goal is already stated in precisely the form mathlib is likely to have proved.

That precision requirement is itself a skill: `exact?` searches by the syntactic shape of the current goal, so restating a goal in an equivalent but differently-shaped form (unfolding a definition, rewriting an equality, simplifying an expression) before calling `exact?` often turns a failed search into a successful one. In this sense, proof search is not a single lookup but an iterative loop — attempt `exact?`, and if it fails, adjust the goal's shape and try again — rather than a one-shot command.

The problem-solving discipline this tool teaches generalizes beyond Lean: before writing a manual proof, always search first. Roughly half of proof engineering is not deriving new arguments but locating the right existing lemma and fitting it to your goal's exact shape. Treating mathlib as a queryable database, rather than a fixed text to read cover to cover, turns proof-writing into a search-and-assemble process: state the goal precisely, query with `exact?`, reshape the goal if the search comes up empty, and let the library do the heavy lifting whenever it already contains the fact you need.

### automation_tactics (0.0s)

## Automation Tactics

A decision procedure is a tactic that automatically closes an entire family of goals by running an algorithm complete for that family, rather than searching for a proof by trial and combination the way general-purpose tactics do. In Lean's `mathlib`, five procedures cover distinct domains, and knowing which owns which goal is the practical skill: `ring` closes equalities in commutative (semi)rings by normalizing both sides to a canonical polynomial form; `linarith` closes goals in linear arithmetic over ordered fields by finding a nonnegative combination of hypotheses that contradicts the negated goal; `positivity` proves goals of the form $e > 0$, $e \geq 0$, or $e \neq 0$ by recursively decomposing the expression's syntax; `omega` decides linear arithmetic over integers and naturals, including divisibility and modular constraints that `linarith` cannot touch; and `aesop` is a general proof-search tactic that chases a configurable rule set — closer in spirit to `simp` plus backtracking than to a decision procedure, useful when no specialized tactic applies.

**Worked example.** Consider proving $(a+b)^2 = a^2 + 2ab + b^2$ for `a b : ℝ`. This is a ring identity, so `ring` normalizes both sides and checks syntactic equality — no case analysis, no search. Contrast this with proving $n \geq 3 \to n^2 \geq 2n + 1$ for `n : ℕ`: this is not a pure ring identity because it depends on the hypothesis $n \geq 3$, so `ring` fails; `omega` (or `nlinarith` for the nonlinear step combined with `linarith` for the linear closing) succeeds because the reasoning is a linear combination of the hypothesis and the squared term.

**Problem-solving application.** When a goal fails to close, diagnose it by domain before reaching for a heavier hammer. Ask: is this an *identity* (try `ring`)? A *linear inequality or equation over ℝ/ℚ* (try `linarith`)? A *linear goal over ℤ/ℕ with integer-specific structure like mod or floor division* (try `omega`)? A *positivity claim about a compound expression* (try `positivity`)? Only if none apply, and the goal still looks tractable by combining known lemmas, escalate to `aesop`, which is slower and less predictable but covers gaps the specialized procedures leave open. This triage — matching goal shape to the narrowest decision procedure that owns it — is faster and more robust than defaulting to search, since a decision procedure either succeeds deterministically or fails fast, while `aesop` can time out on goals outside its effective reach.

### formalization_gap (0.0s)

## Formalization Gap

Getting a statement to typecheck in Lean or Coq feels like proof of understanding, but the kernel only checks that a term has a given type — it has no opinion on whether that type says what you meant in English. The **formalization gap** is this residual link between the informal claim ("every continuous function on a closed interval attains a maximum") and its formal encoding ($\forall f, \text{Continuous } f \to \exists x, \forall y, f(y) \le f(x)$). A kernel guarantees the proof is valid *given* the statement; it says nothing about whether the statement is the theorem you intended.

The gap shows up in two familiar shapes. Sometimes a quantifier is flipped: writing $\exists \varepsilon > 0, \forall \delta > 0, \dots$ where the mathematics demands $\forall \varepsilon > 0, \exists \delta > 0, \dots$. Both are syntactically valid propositions, both may even be provable, but they describe different — sometimes trivially true or trivially false — mathematical facts. Other times a hypothesis is weakened so far that it can never be satisfied (e.g., requiring a function to be both strictly increasing and constant), so the implication holds vacuously and the "proof" certifies nothing about the world. In both cases the statement typechecks perfectly; the failure is entirely in the translation from English to logic, not in the proof that follows.

Consider formalizing "every bounded monotone sequence converges." If you encode "bounded" using a definition that only bounds the sequence's first term, the resulting theorem typechecks, mathlib's convergence lemmas apply cleanly, and the proof compiles — yet it proves nothing resembling the original claim, because the hypothesis is far too weak to rule out divergence. The gap is invisible from inside the proof assistant: soundness only propagates forward from axioms to conclusions, never backward to validate the English gloss.

Closing the gap is a discipline external to the proof, not a step within it. Standard techniques include: stating the theorem, then substituting concrete numeric examples into the formal statement to check they match intuition; asking whether negating a hypothesis makes the theorem provable for a trivial reason (a signal that it was never satisfiable to begin with); and cross-checking the formalized statement against an independent textbook statement, since mathlib's own definitions were themselves the product of a formalization choice. Because a formal statement is built from primitives supplied by mathlib, a subtle mismatch between a mathlib definition and the textbook's informal one — say, mathlib's `Continuous` versus a one-sided continuity notion assumed in the source text — can silently propagate the gap into every downstream proof that reuses it.

### sorry_first_workflow (0.0s)

## Sorry First Workflow

In Lean and other proof assistants, `sorry` is a placeholder tactic that closes any goal instantly, no matter how hard, by asserting it without proof. Every use of `sorry` is logged as a warning, and a theorem that compiles "successfully" while depending on one is not actually proved — it is proved *modulo* that gap. The sorry-first workflow exploits this deliberately: write the full skeleton of a formalization first — every definition and every theorem statement, each closed with `sorry` instead of a real proof — before attempting a single real proof step. This inverts the naive approach of proving lemmas one at a time as you think of them, and it is the standard way working mathematicians and formalizers actually build large developments.

The reasoning is structural. A proof development is a dependency graph: lemma $L_3$ might need $L_1$ and $L_2$, a main theorem might need all three. If you prove $L_1$ in full detail before deciding what $L_2$ and $L_3$ even say, you risk discovering — after hours of work — that $L_1$'s statement is too weak, or stated with the wrong hypotheses, to actually feed the later steps. By stating everything first with `sorry`, you fix the shape of the whole argument, and the type-checker verifies that the statements *compose* correctly (types match, hypotheses are available where needed) before you invest effort in any individual proof.

Concretely: suppose you want to formalize "every finite group of prime order is cyclic." You'd first write:

```
theorem prime_order_cyclic (G : Type) [Group G] [Fintype G]
    (p : ℕ) (hp : p.Prime) (hG : Fintype.card G = p) :
    IsCyclic G := by sorry

lemma exists_nontrivial_elt (G : Type) [Group G] [Fintype G]
    (hG : 1 < Fintype.card G) : ∃ g : G, g ≠ 1 := by sorry

lemma order_dvd_card_of_prime ... := by sorry
```

Compiling this file produces a list of warnings — one per `sorry` — which is now your literal to-do list. You then discharge them one by one, in whatever order is easiest, checking after each that the warning count drops. If a statement turns out wrong, you fix it while the cost is a one-line edit, not a discarded proof. Problem-solving practice with this workflow means learning to write statements precise enough to be *useful* to later `sorry`s — an overly weak lemma compiles just as cleanly as a correct one, so the discipline lies in choosing hypotheses that anticipate what the next proof will actually need.

### ai_assisted_proving (0.0s)

## Ai Assisted Proving

Formal verification tools like Lean have existed for decades, but they historically demanded that a human write every proof step by hand — a slow, expert-only process. AI-assisted proving changes the division of labor: a large language model proposes the mathematics, and Lean's kernel enforces the standard. This partnership is not a compromise on rigor; it is a way to get both the creative fluency of an LLM and the absolute certainty of formal checking, in a workflow Terence Tao has publicly advocated as a template for how AI should participate in mathematics.

The mechanics build on the pieces already introduced. Because Lean can accept a statement with `sorry` in place of a real proof, the LLM can work statement-first: propose a lemma, mark its proof as `sorry`, and check that the *statement* at least type-checks before investing effort in proving it. Once the shape of the argument is right, the LLM tries automation — built-in tactics that search for a proof automatically rather than requiring one written by hand — to discharge each goal. When automation fails, Lean's kernel returns a precise error: an unmet hypothesis, a mismatched type, an unsolved goal with its exact remaining state. That error becomes the next prompt. The LLM reads it, adjusts the approach or the lemma statement, and resubmits. This repair loop — propose, check, fail, refine — can iterate dozens of times per minute, far faster than a human editing cycle, because the kernel's verdict is instantaneous and unambiguous.

Consider proving that the sum of the first $n$ odd numbers is $n^2$: $\sum_{k=1}^{n}(2k-1) = n^2$. An LLM might first state this as a `theorem` with `sorry`, confirm it type-checks, then attempt automation to close the base case and inductive step. If Lean reports a leftover term, the LLM sees exactly which algebraic step failed and revises its approach — say, breaking the goal into a smaller intermediate claim — rather than guessing blindly.

The payoff is durability under scale. An LLM's raw output on a hard combinatorics or number-theory claim is often wrong in subtle ways that are hard for a human reviewer to catch by reading alone. Routing every claim through Lean means an error is caught mechanically, not by trust in the model's fluency. Practicing this loop — writing a `sorry`-riddled skeleton, running automation, reading the kernel's rejection, and repairing — is the core skill: it lets a student use an LLM as a tireless collaborator while treating Lean, not the LLM, as the final arbiter of truth.

### spl_machine_proved (24.3s)

## Spl Machine Proved

A claim is "machine proved" when a theorem prover has checked, step by step, that it follows from a fixed set of axioms and previously established results — with no gap a human reader has to fill in by trust or intuition. In SPL's verifier ladder, this is the top rung: SPL generates a candidate result (say, an algebraic identity or an inequality) and, instead of stopping at a numerical spot-check, submits it to the Lean proof assistant. Lean either builds a valid proof and accepts the claim, or it refuses — there is no partial credit. If the proof goes through, SPL labels the result "machine proved"; if Lean can't complete it automatically, SPL reports a weaker status (e.g., "numerically checked") rather than overstating what was established.

**Worked example.** Suppose SPL generates the identity $\sum_{k=1}^{n} k = \dfrac{n(n+1)}{2}$ for a textbook exercise. Checking this by plugging in $n = 1, \dots, 1000$ only tells you the formula held for those thousand values — it's sampling, not proof. Lean instead requires the argument used in real math courses: confirm the base case ($n=1$: $1 = \frac{1\cdot 2}{2}$), then show that if the formula holds for $n$, it must also hold for $n+1$. SPL translates the identity into Lean's language and lets Lean search for and verify this two-step argument; if it succeeds, the identity earns the "machine proved" label.

**Why this matters for problem-solving.** The label tells a reader how much to trust the result. A numerically checked claim might still hide an edge case the sampled range missed — an off-by-one error, a boundary at $n=0$, a denominator that vanishes for some value — exactly the kind of mistake that produces subtly wrong "proofs" in ordinary coursework. A machine-proved claim carries none of that risk within the scope of what was actually stated, because Lean will not accept an argument with a logical gap. Comparing these two outcomes side by side is a concrete way to internalize the difference between empirical confidence ("we checked a lot of cases") and formal certainty ("we proved it") — a distinction that matters well beyond this textbook, anywhere evidence is mistaken for a guarantee.
