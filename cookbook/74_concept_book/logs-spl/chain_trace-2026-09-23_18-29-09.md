### memory_cell (13.7s)

## Memory Cell

**定义**

一个存储单元（memory cell）是内存中一段大小固定、可寻址的空间，用来保存一个值。它有两个本质属性：**容量固定**（例如 8 位、32 位或 64 位）和**地址唯一**（每个单元都有一个编号，程序通过这个编号访问其内容，而不是通过内容本身）。这正是本书讨论的第一个"基本粒子"——在这个抽象层级之下，我们不再深入晶体管、电容或电荷这些物理实现细节；存储单元是软件世界能够谈论的最底层地基。

把存储单元想象成一排带编号的邮箱：邮箱的尺寸固定（只能放一张标准卡片），每个邮箱有门牌号 $a$，邮箱里此刻放着的内容就是值 $v$。你可以用地址 $a$ 打开对应的邮箱读取 $v$，也可以用同样的地址把里面的内容替换成新的值 $v'$。地址不变，但内容会随时间改变——这就是"可变状态"（mutable state）的雏形，也是后续一切数据结构（数组、链表、对象）得以构建的基础。

**实例分析**

考虑一个 8 位存储单元，地址为 $0x04$。某一时刻它保存的值是二进制 $00000101$（十进制 5）。执行一条赋值语句 `mem[4] = 9` 后，同一个地址 $0x04$ 现在保存 $00001001$（十进制 9）。注意：地址 $0x04$ 自始至终没有变化，改变的只是该地址所指向的内容。这个"地址—内容"分离的性质，是理解指针、引用、变量绑定等概念的前提。

**问题求解应用**

存储单元的固定尺寸带来一个必须正视的约束：**溢出**。若某单元只能表示 $0$ 到 $2^{8}-1=255$ 之间的整数，而计算结果是 $260$，多余的信息就会丢失或按位环绕（wrap around），例如 $260 \bmod 256 = 4$。在设计程序时，选择合适的单元大小（8 位、32 位还是 64 位）本质上是在"能表示的值域"与"占用的存储资源"之间做权衡——这也是后续学习整数类型、字长（word size）和内存对齐等主题时反复出现的核心判断。理解存储单元，就是理解一切数据表示问题的起点：值必须被安置在某个有限的容器里，容器的边界决定了值的边界。

### key (13.2s)

## Key

**定义**

在存储与检索结构（如查找表、优先队列、二叉搜索树、哈希表）中，每个被存储的条目往往由两部分组成:**键(key)**和**值(value)**。键是条目中用于标识、排序和查找该条目的部分——也就是"第二基数(second radical)":比较谓词(comparison predicate)真正作用的对象。值则是与键关联、被携带存储但本身不参与比较或排序的数据。例如在学生成绩表中，学号是键，姓名与分数是值;在哈希表中，字典的"单词"是键，"释义"是值。结构上的所有操作——插入位置的判定、排序顺序的确定、查找时的匹配——全部只检验键，而不检验值本身。

**举例说明**

设有一个按键排序的数组 $A$，其元素形如 $(k_i, v_i)$。二分查找在数组中定位目标键 $k^*$ 时，比较谓词只作用于键:

$$
k_i < k^* ,\quad k_i = k^*,\quad k_i > k^*
$$

值 $v_i$ 完全不参与这个判定过程。假设有学生记录 $(1023, \text{"Ana"}), (1045, \text{"Ben"}), (1078, \text{"Cy"})$，若查找学号 $1045$，算法比较的始终是学号本身，"Ben"这个值只在命中后才被读取和返回。这正体现了键与值职责的分离:键驱动结构的组织逻辑，值只是被动携带的载荷。

**问题求解应用**

在设计和实现这类结构时，识别"谁是键"是第一步，也是最容易出错的一步。常见陷阱:当记录本身是复合对象（如学生对象包含学号、姓名、GPA 多个字段）时，必须显式指定比较谓词依据哪个字段排序——若按 GPA 排序，则 GPA 是键，学号与姓名退化为值。在实践中，这通常通过传入一个**键提取函数**（如 Python 中 `sorted(students, key=lambda s: s.gpa)`）或自定义比较器来实现，而不是让结构自行猜测。当需要按不同标准（如先按院系、再按 GPA）多次检索同一批记录时，可以构建多个索引结构，各自采用不同字段作为键，但共享同一份值——这也是数据库中"多重索引"设计的核心思想。理解键与值的分离，是掌握后续排序算法、哈希表冲突处理及索引设计的基础。

### pointer (12.6s)

## Pointer

**定义**

在计算机内存中,数据存放在一系列被称为"存储单元"(memory cell)的位置上,每个存储单元都有唯一的地址。指针(pointer)是一种特殊的值,它本身存储的不是数据,而是另一个存储单元的地址。换句话说,指针的值"指向"内存中的另一个位置。这是计算机科学中第一个真正意义上的"根本性"(radical)抽象:它让程序能够跳出数组那种连续、线性的内存布局,构造出链表、树、图等更灵活的数据结构。没有指针,数据结构就只能是数组——元素依次紧挨着排列,顺序固定,大小固定。

**工作示例**

设内存中有一个整数变量 $x$,其值为 $42$,存放在地址 $0x1000$ 处。声明一个指针变量 $p$,并令 $p$ 指向 $x$,那么 $p$ 存储的值就是 $0x1000$ 这个地址,而不是 $42$ 本身。这种关系可以写作:

$$p = \&x, \qquad *p = x$$

这里 $\&$ 是"取地址"运算符,$*$ 是"解引用"运算符——通过 $p$ 找到它所指向的那块内存,读出其中的值。若执行 $*p = 100$,则 $x$ 的值被改为 $100$,因为 $p$ 和 $x$ 实际上指向同一块内存单元。这正是指针的核心威力:多个变量名(或数据结构中的多个字段)可以共享、引用同一份数据,而不必复制它。

**问题求解应用**

指针的真正价值体现在构建"自引用"式的数据结构上。例如,链表(linked list)中的每个节点包含两部分:数据域和一个指向"下一个节点"的指针。由于节点通过指针相连而非物理相邻存放,插入或删除一个节点只需修改相邻节点中的指针值,时间复杂度为 $O(1)$,而不像数组插入那样需要移动后续所有元素,后者代价是 $O(n)$。

指针同样是函数间"传引用"(pass by reference)的基础:将一个变量的地址传给函数,函数就能直接修改调用者内存中的原始数据,而不是操作一份拷贝。这一机制也带来风险——若指针指向的内存已被释放或从未初始化,解引用会导致"悬空指针"(dangling pointer)或未定义行为,是许多程序漏洞与崩溃的根源。理解指针,是从"数组式"思维迈向"图结构式"思维的第一步,也是理解动态内存分配、递归数据结构与操作系统内存管理的前提。

### array (11.9s)

## Array

数组（Array）是由若干个大小相同的存储单元（memory cell）在内存中连续排列而成的数据结构。每个单元通过一个整数**索引**（index）来标识，索引从 $0$ 开始编号。由于所有单元大小固定且物理上首尾相接，计算机可以直接用算术运算定位任意单元的地址，而不需要逐个遍历查找。若数组起始地址为 $\text{base}$，每个单元占用 $s$ 字节，则第 $i$ 个元素的地址为：

$$
\text{address}(i) = \text{base} + i \times s
$$

这个公式说明，访问任意位置的元素只需一次乘法和一次加法，时间复杂度为 $O(1)$，与数组长度无关——这正是数组最核心的性质：**随机访问**（random access）。

**举例说明**：假设一个整型数组从地址 $1000$ 开始，每个整数占 $4$ 字节，要访问下标为 $7$ 的元素，计算机直接计算 $1000 + 7 \times 4 = 1028$，一步到位读取该地址的内容，无需先访问下标 $0$ 到 $6$。相比之下，链表这类结构若要访问第 $7$ 个节点，必须从头依次跳转，时间复杂度为 $O(n)$。

数组的连续性还带来另一个重要优势：**缓存友好**（cache-friendly）。现代计算机的内存层次结构中，CPU 读取数据时会把相邻内存地址的数据一并加载进高速缓存（cache line）。因为数组的相邻元素在物理内存中也是相邻的，遍历数组时后续元素往往已经在缓存中，访问速度远快于需要频繁"跳转"内存地址的结构（如链表）。这也是为什么在实际工程中，即使某些操作在理论复杂度上数组不占优势（例如中间插入需要 $O(n)$ 搬移后续元素），数组在缓存命中率上的优势常常使其整体性能仍然更好。

**解题应用**：在实际编程中，判断"是否应该用数组"的关键问题是——操作模式是以**按下标随机读取**为主，还是以**频繁插入/删除**为主？若是前者（如实现哈希表的桶、图像像素矩阵、动态规划的状态表），数组几乎总是最优选择；若是后者且插入删除位置不固定，则需要权衡链表等结构。理解这一权衡，是后续学习动态数组、栈、队列等结构的基础，因为它们本质上都是数组的组合与扩展。

### binary_tree (15.0s)

## Binary Tree

**定义**

二叉树（binary tree）是一种递归的数据结构：它由若干**节点（node）**组成，每个节点存储一个值，并持有至多两个子指针——左子（left）和右子（right）——分别指向左子树和右子树，二者本身也是二叉树（或为空）。没有父节点指向的节点称为**根节点（root）**；不再有子节点的节点称为**叶节点（leaf）**。从组成上看，节点是"内存单元 + 指针"的复合体：值占据一段内存，指针字段则记录子节点的地址。

树的关键度量是**高度（height）** $h$，即从根到最深叶节点的边数。若树是**平衡的（balanced）**——每个节点左右子树的高度差不超过某个常数——则节点数 $n$ 与高度满足

$$
n \le 2^{h+1}-1 \quad\Longrightarrow\quad h = \Theta(\log n).
$$

这正是二叉树的核心价值：只要保持平衡，查找、插入、删除等操作沿单条路径下降，时间复杂度为 $O(\log n)$，而非链表式的 $O(n)$。这一性质使二叉树成为二叉搜索树（BST）、堆（heap）、字典树（trie）等结构的共同基础——它们都在"值 + 左右指针"之上叠加了各自的排列规则（有序性、优先级、前缀共享）。

**范例**

考虑插入序列 $[8, 3, 10, 1, 6, 14]$ 构造一棵二叉搜索树：8 为根；3 小于 8 挂左；10 大于 8 挂右；1 沿 3 的左侧挂入；6 大于 3、小于 8，挂在 3 的右侧；14 挂在 10 的右侧。最终树高为 2，共 6 个节点，符合 $h=\Theta(\log n)$ 的预期（若序列本身是单调排列，如 $[1,2,3,4,5,6]$，则退化为链，$h=\Theta(n)$，说明"平衡"这一前提不可省略）。

**问题求解应用**

给定一棵二叉树，判断其是否平衡，标准做法是自底向上的递归：对每个节点，先求左、右子树高度，若二者相差超过 1 则立即返回"不平衡"标记，否则返回 $1+\max(h_{\text{左}}, h_{\text{右}})$。这一算法只需一次后序遍历，时间复杂度 $O(n)$，避免了对每个节点重复计算高度导致的 $O(n^2)$。这类"计算子树属性并向上传递"的模式，是处理堆的堆化（heapify）、trie 的前缀计数等问题的通用思路。

### comparison (0.0s)

## Comparison

比较（comparison）是一个二元谓词：给定集合中的两个元素 $a$ 和 $b$，它回答"谁排在前面"这一个问题，输出结果只有三种可能——$a<b$、$a=b$、$a>b$。这是基于比较的排序算法（comparison-based sorting）与数据交互的**唯一**方式：算法不能"看见"元素的内部结构或数值大小，只能不断地问"这两个谁更小"，然后根据答案决定下一步动作。归并排序、快速排序、堆排序——几乎所有经典排序算法——都建立在这一单一操作之上。

**信息论下界**。既然算法对数据的全部认知都来自一连串的是/否式比较结果，我们可以把整个排序过程看作一棵二叉决策树：每个内部节点代表一次比较，每条边代表比较的两种结果之一，每个叶子代表一种最终排列（permutation）。对于 $n$ 个互不相同的元素，共有 $n!$ 种可能的排列，而算法必须能够区分出所有这些排列——否则就会把两种不同的正确顺序混为一谈。一棵二叉树若要拥有至少 $n!$ 个叶子，其深度（即最坏情况下的比较次数）至少为

$$
\log_2(n!)
$$

由斯特林公式（Stirling's approximation），$\log_2(n!) = \Theta(n \log n)$。这就是排序问题的信息论下界：任何仅依赖两两比较的算法，最坏情况下都无法避免做 $\Omega(n \log n)$ 次比较。归并排序和堆排序达到了这一下界，因此在比较模型下是渐近最优的；而计数排序、基数排序之所以能做到 $O(n)$，恰恰是因为它们绕开了"比较"这一原语，直接利用了数据的数值结构。

**问题求解应用**。这一下界给出的是一把判断工具：当你想优化一个排序算法时，首先要问它是否属于比较模型。如果是，$O(n \log n)$ 已是理论极限，继续压缩只是常数因子上的优化；如果你能够利用数据的额外结构（如已知范围、整数键、多关键字），就可能跳出比较模型，获得线性时间。例如，对 $0$ 到 $999$ 的整数排序，若坚持用比较排序，最坏也要 $\Omega(n\log n)$ 次比较；但改用计数排序则可在 $O(n+k)$ 时间内完成——因为它不再依赖"比较"这一原语,而是直接利用了键值的数值信息。

### binary_search_tree (13.1s)

## Binary Search Tree

**定义**

二叉搜索树（Binary Search Tree, BST）是在二叉树的基础上附加了一条排序不变量的数据结构：对树中任意一个节点，其左子树中所有键值都小于该节点的键值，右子树中所有键值都大于该节点的键值。设节点 $x$ 的键为 $\text{key}(x)$，该不变量可写作：

$$
\forall y \in \text{left}(x):\ \text{key}(y) < \text{key}(x) \quad \text{且} \quad \forall z \in \text{right}(x):\ \text{key}(z) > \text{key}(x)
$$

这条性质对每个子树递归成立，因此对整棵树做中序遍历（左—根—右）会得到一个严格递增的键值序列——这是判断一棵二叉树是否为 BST 的常用方法。

**查找、插入、删除**

查找键 $k$ 时，从根节点开始比较：若 $k$ 等于当前节点键，命中；若 $k$ 小，则进入左子树；若 $k$ 大，则进入右子树；直到命中或走到空指针（未找到）。插入沿用相同的比较路径，在第一个空位置挂上新节点。删除稍复杂：叶节点直接摘除；只有一个子节点的节点用该子节点替代自己；有两个子节点的节点则用其右子树的最小值（或左子树的最大值）替换自身键值，再递归删除那个被复制的节点。

三种操作的代价都等于从根到目标节点的路径长度，即树的高度 $h$。若树"足够平衡"，$h = O(\log n)$，三种操作平均都是对数时间。

**病态情形与它引出的问题**

BST 的效率完全取决于形状。如果按已排序顺序（如 $1,2,3,\dots,n$）依次插入键，每个新键都只能挂在前一个节点的右侧，树退化成一条链，高度变为 $h = n$，查找、插入、删除都退化为 $O(n)$——不比线性扫描数组快。

**问题求解练习**

给定插入序列 $[5, 3, 8, 1, 4, 7, 9]$，画出得到的 BST，并写出其中序遍历结果验证是否为递增序列；再给出一个长度为 7 的插入序列，使得到的 BST 恰好退化为链表，并说明其高度与平衡树高度 $\lceil \log_2 8 \rceil$ 的差距。这类练习正是引出后续**自平衡 BST**（如红黑树、AVL 树）的动机：它们通过在插入/删除时做旋转操作，强制维持 $h = O(\log n)$，从而杜绝上述最坏情形。

### hash_table (14.3s)

## Hash Table

**定义**：哈希表（hash table）是一种用键（key）直接定位存储位置的数据结构，其底层由一个容量为 $m$ 的数组和一个哈希函数 $h$ 组成。给定键 $k$，元素被放入下标为 $h(k) \bmod m$ 的桶（bucket）中。在哈希函数分布均匀、装载因子（元素数除以容量）保持较低的前提下，插入、查找、删除的**均摊**时间复杂度均为 $O(1)$。这优于数组的 $O(n)$ 线性查找和平衡二叉搜索树的 $O(\log n)$，是通用场景下最快的查找结构。

哈希表的核心矛盾是**碰撞（collision）**：不同的键可能映射到同一个下标，因为键空间通常远大于数组容量 $m$（鸽笼原理保证碰撞不可避免）。两种主流解决方案：

1. **链地址法（chaining）**：每个桶存一个链表，碰撞的元素依次挂在同一链表上。查找时先定位桶，再遍历链表比对键。
2. **开放寻址法（open addressing）**：碰撞时按探测序列（如线性探测 $h(k)+i$）寻找下一个空位，所有元素都直接存在数组内，不需要额外的链表结构。

**均摊 $O(1)$ 的来源**：设装载因子为 $\alpha = n/m$。在链地址法下，每条链的期望长度为 $\alpha$；只要通过动态扩容（如容量翻倍并重新哈希）将 $\alpha$ 维持在某个常数上限（例如 $\alpha \le 1$），单次操作的期望查找长度就是 $O(1)$。扩容操作本身是 $O(n)$，但因其发生频率随容量指数级降低，均摊到每次插入上仍是 $O(1)$——这与动态数组的扩容分析同理。

**Worked example**：实现一个整数集合的成员判断。设 $m = 8$，哈希函数 $h(k) = k \bmod 8$。插入 $3, 11, 19$：三者对 8 取模都等于 3，全部碰撞到桶 3。链地址法下桶 3 存储链表 $[3, 11, 19]$；查找 19 需要遍历三个节点比对键值，最坏退化为 $O(n)$——这说明哈希函数设计（如乘法哈希、加密哈希的低位混合）直接决定了碰撞率,进而决定了实际性能是否接近理想的 $O(1)$。

**应用**：字典/映射类型（Python `dict`、Java `HashMap`）、数据库索引、缓存（LRU cache 的 $O(1)$ 查找依赖哈希表）、去重与集合运算，几乎所有需要"以键找值"的场景都以哈希表为首选结构，只有在需要保序遍历时才让位于平衡树。

## Compiler Symbol Table

**定义**

编译器在扫描源程序时,必须记录每个标识符(变量名、函数名)的属性——类型、内存地址(或寄存器/栈偏移)、作用域层级等。**符号表**(symbol table)就是维护"标识符名 → 属性记录"这一映射的数据结构。它在语义分析阶段被写入(声明时插入),在代码生成阶段被大量查询(每次引用变量都要查表取地址和类型)。

由于插入和查询的频率极高且贯穿整个编译过程,符号表的数据结构选择直接影响编译速度。最常见的实现是**哈希表**(hash table):将标识符名通过哈希函数 $h(\text{name})$ 映射到桶(bucket)编号,平均情况下插入和查询都是 $O(1)$。但在代码生成阶段,某些优化(如栈帧布局、寄存器分配可视化、按声明顺序生成调试信息)需要**按名字有序遍历**所有符号,这时哈希表因为没有顺序而无能为力,必须借助**平衡二叉搜索树**(如红黑树)——插入、查询为 $O(\log n)$,但支持中序遍历得到有序序列。

**实例分析**

考虑一段 C 代码:

```c
int x = 5;
float y = 2.0;
int z = x + 10;
```

编译器扫描到 `int x` 时,在当前作用域的符号表中插入记录 `x → {type: int, addr: 0x00}`;扫描到 `float y` 时插入 `y → {type: float, addr: 0x04}`。当处理 `z = x + 10` 时,编译器查表得到 `x` 的类型是 `int`,从而知道应生成整数加法指令而非浮点加法指令,并取出其地址完成寻址。若使用哈希表,这次查询平均只需一次哈希计算,时间与符号表大小无关——这正是 $O(1)$ 均摊复杂度的体现。

**问题求解应用**

作用域嵌套(如函数内的局部变量遮蔽全局变量)要求符号表支持"链式作用域":每进入一个代码块就压入一张新的哈希表,退出时弹出。查询时从最内层表开始逐层向外查找,直到找到匹配项或到达全局表——这本质上是在一组哈希表构成的栈上做线性搜索,时间复杂度为 $O(d)$,其中 $d$ 是作用域嵌套深度。这种"哈希表处理频繁查询、平衡树处理有序遍历"的组合,是数据结构选择服务于具体访问模式的典型案例。
