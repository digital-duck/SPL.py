### relation (0.0s)

## Relation

A relation is a named, unordered set of tuples that all share the same schema — the same fixed sequence of attribute names, each drawn from a specified domain. Formally, given attributes $A_1, \dots, A_n$ with domains $D_1, \dots, D_n$, a relation $R$ is a subset of the Cartesian product:

$$
R \subseteq D_1 \times D_2 \times \cdots \times D_n
$$

Each element of $R$ is a tuple $t = (v_1, v_2, \dots, v_n)$ with $v_i \in D_i$. Because $R$ is a *set*, two consequences follow directly from set theory: tuples have no inherent order, and no tuple can appear twice. This is why SQL's `SELECT *` output is conceptually unordered (even though engines often return rows in a stable order for convenience) and why a table's primary key exists — to enforce the uniqueness that set membership already implies in the theoretical model.

**Worked example.** Consider a relation `Student` with schema (`id`, `name`, `gpa`):

$$
\text{Student} = \{(101, \text{"Ada"}, 3.9),\ (102, \text{"Grace"}, 3.7),\ (103, \text{"Alan"}, 3.8)\}
$$

Each tuple is a single fact: "the student with id 101 is named Ada and has GPA 3.9." The relation as a whole is the complete collection of such facts at a moment in time. Note that swapping the order in which you list the three tuples produces the identical relation — order carries no information, only the tuple's *content* does.

**Problem-solving application.** This is why relational algebra operations (selection, projection, union, difference) are defined as producing new *sets* of tuples, and why duplicate elimination is a real cost engines must manage: `SELECT DISTINCT name FROM Student` is not an optional flourish, it is restoring the mathematical guarantee that a relation cannot contain the same tuple twice. Recognizing this matters whenever you reason about whether a query result can be safely treated as a true relation for further algebraic manipulation, or whether it might instead contain repeated rows whose duplicates carry meaning — for instance, feeding into an aggregate count.

### attribute (0.0s)

## Attribute

A relation is a set of tuples, and an **attribute** is a named, typed slot within that tuple — the pairing of a column name with a domain of legal values it may hold. Formally, if a relation schema is $R(A_1, A_2, \ldots, A_n)$, each $A_i$ is an attribute, and every tuple in an instance of $R$ assigns to $A_i$ a value drawn from its domain $\text{dom}(A_i)$. The schema `Student(id: integer, name: string, gpa: decimal)` declares three attributes; a tuple like $(1042, \text{"Amara"}, 3.7)$ is only valid if each value respects its attribute's domain. Attributes are what let a relation carry meaning beyond a bare list of values — position alone is fragile, but a name like `gpa` tells you exactly what a value represents and constrains how it can be used.

This matters because the core relational operation of projection is defined entirely in terms of attributes, not row position. Projection, written $\pi_{A_1, \ldots, A_k}(R)$, selects a subset of attributes and discards the rest, producing a narrower relation. If `Student` has attributes `id, name, gpa`, then $\pi_{\text{name}, \text{gpa}}(\text{Student})$ returns only those two columns for every student. Notice that projection depends entirely on attribute names: asking for `name, gpa` means something specific because those labels, not their column positions, tell you which values you're keeping.

In problem-solving terms, most relational-algebra bugs trace back to attribute mismatches: projecting away an attribute that a later step depends on, mistaking two same-named attributes in different tables for the same thing (a `name` column in `Student` versus `Course` are unrelated despite the shared label), or assuming a projected relation still carries information that was actually discarded. For example, if you compute $\pi_{\text{name}}(\text{Student})$ and later need to filter by `gpa`, you can't — that attribute is gone, and you must go back to the original relation. This is a common trap: projection is not reversible, so the order in which you apply it relative to other operations matters.

When you design a schema, choosing precise, unambiguous attribute names — and documenting each one's domain — is what makes projection (and the operations built on it) safe to compose. A well-named attribute set lets you reason about what a relation contains just by reading its schema, without inspecting the data itself. Attributes are the vocabulary of the relational model; getting them right is what makes every later operation predictable rather than a source of silent, hard-to-debug errors.

### tuple (0.0s)

## Tuple

A **tuple** is a single, ordered list of attribute values, one value for each attribute in a relation's schema. If a relation `Student(id, name, gpa)` has schema attributes $(id, name, gpa)$, then one tuple might be $(1042, \text{"Amara Okafor"}, 3.85)$. This is the atomic unit of stored data in the relational model: you cannot decompose a tuple further and still have a meaningful row of the table. A relation itself is formally defined as a *set* of tuples — not a list, not a bag — which is why, in strict relational theory, duplicate rows are not permitted and row order carries no meaning.

Two structural rules govern every tuple. First, its length is fixed by the schema: a tuple in `Student` always has exactly three values, no more, no less. Second, each value must belong to the domain (the legal set of values) declared for that attribute's position — `gpa` cannot hold the string `"junior"`, and `id` cannot hold a negative number if the schema forbids it. A tuple that violates either rule is not a member of the relation.

**Worked example.** Consider `Enrollment(student_id, course_id, term)` with two current tuples: $(1042, \text{"CS201"}, \text{"Fall2026"})$ and $(1042, \text{"MATH210"}, \text{"Fall2026"})$. Suppose you try to insert $(1042, \text{"CS201"}, \text{"Fall2026"})$ again. Under strict set semantics, this insertion changes nothing — the "new" tuple is already an element of the set, and sets do not track multiplicity. Most production databases relax this rule for performance reasons and allow duplicate rows unless a `PRIMARY KEY` or `UNIQUE` constraint is declared; recognizing that gap between the mathematical model and real SQL engines is itself a useful piece of problem-solving intuition when you're debugging unexpected duplicate rows in a report.

**Application.** When designing a schema, ask two questions for every entity: what attributes make a single instance of it, and what combination of those attributes uniquely identifies one tuple from another? For `Enrollment` above, no single attribute is unique, but the combination $(student\_id, course\_id, term)$ is — this composite combination is precisely what should be declared as a primary key or unique constraint to make the "no duplicate tuples" rule enforceable in practice, not just in theory.

### domain (0.0s)

## Domain

In relational database theory, a **domain** is the set of permissible values that an attribute may take. Formally, for a relation schema $R(A_1, A_2, \ldots, A_n)$, each attribute $A_i$ is associated with a domain $D_i$, and every tuple $t$ in the relation must satisfy $t[A_i] \in D_i$ for all $i$. A domain specifies both a **type** (INTEGER, TEXT, DATE, BOOLEAN, DECIMAL(10,2), and so on) and, often, a **constraint** narrowing that type further — for example, $\text{Age} \in \{n \in \mathbb{Z} \mid 0 \le n \le 120\}$, or $\text{Grade} \in \{\text{'A'}, \text{'B'}, \text{'C'}, \text{'D'}, \text{'F'}\}$.

The domain is distinct from the tuple and the attribute: an attribute is a *named slot* in a schema, a tuple is a *filled-in row*, and a domain is the *rulebook* governing what may legally occupy that slot. Without domains, a database cannot enforce integrity at the cell level — nothing would stop a `date_of_birth` column from holding the string `"banana"` or an `age` column from holding $-5$.

**Worked example.** Consider a `Students` relation with schema $\text{Students}(\text{id}, \text{name}, \text{gpa}, \text{enrolled})$. We assign domains:

$$
D_{\text{id}} = \mathbb{Z}^+, \quad D_{\text{name}} = \text{TEXT}, \quad D_{\text{gpa}} = \{x \in \mathbb{R} \mid 0.0 \le x \le 4.0\}, \quad D_{\text{enrolled}} = \{\text{TRUE}, \text{FALSE}\}
$$

If a client attempts to insert $t[\text{gpa}] = 4.7$, the database management system checks $4.7 \in D_{\text{gpa}}$, finds it false, and rejects the insert. This check is domain-integrity enforcement — the database's guarantee that no value can violate its column's rulebook, regardless of which application or user submitted it.

**Problem-solving application.** Domains matter directly when designing schemas and writing queries. In SQL, a domain is declared via a column type plus optional `CHECK` constraints:

```sql
CREATE TABLE Students (
    id       INTEGER PRIMARY KEY,
    name     TEXT NOT NULL,
    gpa      DECIMAL(3,2) CHECK (gpa BETWEEN 0.0 AND 4.0),
    enrolled BOOLEAN NOT NULL
);
```

When two relations are compared or joined on an attribute (e.g. `WHERE Students.id = Enrollments.student_id`), the comparison is only meaningful if both attributes share a compatible domain — this is why join errors often trace back to a domain mismatch, such as comparing a `TEXT` id against an `INTEGER` id. Recognizing domain compatibility is therefore essential to correct query design.

### cartesian_product (0.0s)

## Cartesian Product

**Definition.** Given relations $R$ with $m$ tuples over attributes $A_1, \dots, A_k$ and $S$ with $n$ tuples over attributes $B_1, \dots, B_\ell$, the Cartesian product $R \times S$ is the relation containing every possible pairing of a tuple from $R$ with a tuple from $S$:

$$R \times S = \{\, (r, s) \mid r \in R,\ s \in S \,\}$$

The result has $|R| \times |S|$ tuples and $|R.\text{cols}| + |S.\text{cols}|$ attributes — no filtering, no matching condition, just exhaustive combination. This is the brute-force combinator underlying relational algebra: every join is built from the Cartesian product by keeping only the rows that satisfy some condition, so $R \times S$ is the operator to master before joins are introduced.

**Worked example.** Let $R$ = Students $= \{(\text{Alice}), (\text{Bob})\}$ over attribute Name, and $S$ = Courses $= \{(\text{Math}), (\text{Bio})\}$ over attribute Course. Then $R \times S$ produces $2 \times 2 = 4$ tuples:

$$(\text{Alice}, \text{Math}),\ (\text{Alice}, \text{Bio}),\ (\text{Bob}, \text{Math}),\ (\text{Bob}, \text{Bio})$$

Note the row count multiplies, not adds — this is what makes the operator dangerous at scale: two relations of 10,000 rows each produce 100 million rows, none of which may be meaningful.

**Problem-solving application.** The Cartesian product's real value is diagnostic and constructive rather than practical to run directly. First, it explains *why* an accidental join without a `WHERE` or `ON` clause silently explodes a result set — SQL's comma-separated `FROM R, S` is literally $R \times S$, and forgetting the join condition means forgetting to filter it down. Second, it is the tool for reasoning about correctness: to verify a proposed join query, you can mentally construct $R \times S$ and check that your `WHERE` condition selects exactly the tuples you intend, no more and no less. Third, it is genuinely useful when you *want* every combination — generating all possible pairings for a schedule, all (student, exam-slot) assignments to feed into a constraint solver, or a full factorial design for an experiment. In those cases, $R \times S$ isn't a wasteful intermediate step; it's the complete solution space you then narrow down with additional constraints.

### projection (0.0s)

## Projection

Projection is the relational-algebra operation that selects a specified set of columns (attributes) from a relation, discarding the rest, and returns the result as a new relation. Formally, if $R$ is a relation with attribute set $\{A_1, A_2, \ldots, A_n\}$, projection onto a subset $X \subseteq \{A_1, \ldots, A_n\}$ is written $\pi_X(R)$, and produces a relation whose schema is exactly $X$. Because a relation is a *set* of tuples, projection also removes duplicate rows that result from discarding columns — two tuples that differ only in the dropped attributes collapse into one. This duplicate elimination is what makes projection more than simple column slicing: it enforces the set semantics that define a relation in the first place.

**Worked example.** Consider a relation `Enrollment(StudentID, CourseID, Semester, Grade)`. The query
$$\pi_{\text{CourseID}}(\text{Enrollment})$$
returns the set of distinct courses that have at least one enrollment — if 200 students took CS101 in different semesters, the result still contains a single row `CS101`. In SQL this is `SELECT DISTINCT CourseID FROM Enrollment`. Note that plain SQL's `SELECT CourseID FROM Enrollment` does *not* remove duplicates by default, so it is technically not a pure relational-algebra projection unless `DISTINCT` is added — a common point of confusion for students moving between the algebra and the language.

**Problem-solving application.** Projection matters for query planning because it reduces the width of intermediate results, which reduces the memory and I/O cost of subsequent operations. A key optimization rule, *projection pushdown*, says that a query optimizer should apply $\pi$ as early as possible — before joins or expensive filters — since projecting down to only the attributes a later step actually needs shrinks every row that has to be carried through that step. Suppose you need only `StudentID` and `Grade` from a query that joins `Enrollment` with a large `CourseCatalog` table on `CourseID`: projecting `Enrollment` down to `{StudentID, CourseID, Grade}` before the join, rather than joining full rows and projecting afterward, avoids carrying unused columns like `Semester` and every catalog attribute through the expensive join step. Practicing this reordering — recognizing which attributes a downstream operation actually needs and pushing $\pi$ toward the base relations — is a core skill in writing efficient queries and in reading query execution plans.

### selection (0.0s)

## Selection

Selection is relational algebra's row filter: given a relation $R$ and a predicate $P$, the selection $\sigma_P(R)$ returns exactly those tuples of $R$ for which $P$ evaluates to true. Formally,

$$
\sigma_P(R) = \{\, t \in R \mid P(t) \text{ is true} \,\}
$$

The predicate $P$ can reference any attribute of $R$ (comparing it to a literal or to another attribute) and can combine multiple conditions with $\land$, $\lor$, and $\neg$. Selection never adds or removes columns and never invents new tuples — it only decides, tuple by tuple, whether to keep it. Consequently $\sigma_P(R)$ has the same schema as $R$, and its cardinality satisfies $|\sigma_P(R)| \le |R|$.

**Worked example.** Suppose relation `Employees(id, name, dept, salary)` holds 10,000 rows. The query "employees in the Engineering department earning over \$120,000" is

$$
\sigma_{\,dept = \text{'Engineering'} \,\land\, salary > 120000}(\text{Employees})
$$

In SQL this is exactly `SELECT * FROM Employees WHERE dept = 'Engineering' AND salary > 120000`. Each of the 10,000 tuples is tested against the compound predicate independently; the output relation retains all four columns but only the rows that pass both conditions.

**Problem-solving application.** Selection is where query *selectivity* — the fraction of tuples that survive the predicate — matters for performance. If a predicate is highly selective (few tuples pass), a database engine will prefer an index lookup over a full scan; if it's not selective (most tuples pass), a full scan is often cheaper because the index overhead isn't justified. This also motivates "push selection down" as a query-optimization rewrite rule: an optimizer applies the cheaper or more selective sub-condition of a compound predicate first, filtering out rows early so downstream operations (joins, aggregations) process less data, rather than evaluating the full conjunction in one pass. As an exercise, consider $\sigma_{age \ge 18 \,\lor\, guardian\_signed = \text{true}}(\text{Applicants})$ and predict which of the two sub-conditions is likely more selective in a dataset of mostly adult applicants.

### index (0.0s)

## Index

An **index** is an auxiliary data structure — built on one or more attributes of a relation — that lets the query engine locate rows satisfying a predicate without scanning every tuple. The dominant implementation is the **B-tree**: a balanced, ordered tree that maintains sorted keys with fanout $b$, giving search, insert, and delete cost $O(\log_b n)$ for a relation of $n$ rows — far better than the $O(n)$ cost of a full table scan. Because keys are kept in sorted order, a B-tree index also supports range predicates ($A > v$) and sorted output directly, which is why it is the default index type in most relational database systems.

**Worked example.** Consider a table `Orders(order_id, customer_id, order_date, amount)` with one million rows, and a query `SELECT * FROM Orders WHERE customer_id = 42`. Without an index, the engine performs a sequential scan, examining all $10^6$ rows — cost proportional to $n$. With a B-tree index on `customer_id`, the engine descends the tree in $O(\log_b n)$ steps; with $b = 100$, that is about $\lceil \log_{100} 10^6 \rceil = 3$ node accesses to find the first matching entry, followed by retrieving only the matching rows via row pointers. The command `CREATE INDEX idx_cust ON Orders(customer_id);` builds this structure once, at a cost of $O(n \log n)$ to sort and insert all existing rows, and thereafter every `INSERT` or `UPDATE` on `Orders` must also update the index, adding $O(\log n)$ write overhead per modification and consuming additional storage.

**Problem-solving application.** Indexing decisions are a cost-benefit trade-off between read and write workloads. A table with heavy `SELECT` traffic and infrequent writes (e.g., a reporting table) benefits from indexing every attribute used in `WHERE`, `JOIN`, or `ORDER BY` clauses. A table with heavy `INSERT`/`UPDATE` traffic (e.g., a logging table) should be indexed sparingly, since each additional index multiplies the per-write cost. For join predicates specifically, indexing the foreign-key attribute converts a nested-loop join's $O(n \cdot m)$ cost into an index-nested-loop join's $O(n \log m)$ cost — often the single largest performance improvement available to a database administrator without rewriting application logic.

### join (0.0s)

## Join

A **join** combines tuples from two relations that share related values, producing a result set that would be impossible to obtain from either table alone. Formally, the most general form — an **inner join** — is defined as a cartesian product followed by a selection:

$$
R \bowtie_{\theta} S \;=\; \sigma_{\theta}(R \times S)
$$

where $R \times S$ pairs every tuple of $R$ with every tuple of $S$, and the selection predicate $\theta$ (the join condition, e.g. $R.id = S.id$) filters that product down to only the pairs that actually correspond. A projection often follows to drop redundant or unwanted columns. This decomposition explains why joins are the most expensive relational operation: naively, $|R \times S| = |R| \cdot |S|$ tuples must be generated before filtering, though real database engines use indexes and hash-based algorithms to avoid materializing the full product.

**Worked example.** Suppose `Students(sid, name)` has rows $(1, \text{Amy})$, $(2, \text{Ben})$, and `Enrollments(sid, course)` has $(1, \text{Bio})$, $(1, \text{Chem})$, $(3, \text{Art})$. An inner join on `sid` produces only rows where the id matches on both sides: $(1, \text{Amy}, \text{Bio})$ and $(1, \text{Amy}, \text{Chem})$. Ben (no enrollments) and the Art row (sid 3, no matching student) both vanish — inner join keeps only agreement.

**Outer joins** solve the problem of wanting to preserve the "orphan" rows. A **LEFT OUTER JOIN** keeps every row of $R$ even when no match exists in $S$, padding the missing $S$-columns with NULL — so Ben would appear as $(2, \text{Ben}, \text{NULL})$. **RIGHT OUTER JOIN** does the symmetric thing for $S$, and **FULL OUTER JOIN** preserves unmatched rows from both sides simultaneously.

**Problem-solving application.** When writing a query, first decide what you cannot afford to lose: if the question is "which students have taken a course?", inner join suffices; if it's "list all students and their courses, if any," you need a left outer join, since inner join would silently drop non-enrolled students — a common source of incorrect reports. Always identify the join condition explicitly (mismatched or missing predicates silently degrade a join back into a full cartesian product) and push selective filters as early as possible, since join cost scales with the size of the inputs being combined.

### schema (26.6s)

## Schema

A relation's **schema** is the ordered list of (attribute, domain) pairs that defines what every tuple stored in that relation must look like. If a relation instance is the current *set of rows*, the schema is the *template* those rows are drawn from — it says how many columns exist, what each is named, and what type of value each may hold. Formally, a schema for relation $R$ is written

$$
R(A_1: D_1,\ A_2: D_2,\ \dots,\ A_n: D_n)
$$

where each $A_i$ is an attribute name and $D_i$ is its domain — the set of legal values. A tuple $t$ belongs to $R$ only if $t.A_i \in D_i$ for every $i$. This is why schema is a *contract*: it is checked, not suggested. A row that tries to store text in an integer domain, or that omits a required attribute, is rejected outright.

**Worked example.** Consider a relation for university enrollment:

$$
\text{Enrollment}(\text{student\_id}: \mathbb{Z}^+,\ \text{course\_code}: \text{VARCHAR}(8),\ \text{term}: \{\text{"Fall","Spring","Summer"}\},\ \text{grade}: \{0.0,\dots,4.0\})
$$

In SQL, this schema *is* the `CREATE TABLE` statement — there is no separate design artifact:

```sql
CREATE TABLE Enrollment (
    student_id  INT PRIMARY KEY,
    course_code VARCHAR(8),
    term        VARCHAR(6) CHECK (term IN ('Fall','Spring','Summer')),
    grade       DECIMAL(2,1) CHECK (grade BETWEEN 0.0 AND 4.0)
);
```

Each column declaration names an attribute and constrains it to a domain; the `CHECK` clauses enforce domains SQL's base types can't express on their own.

**Problem-solving application.** Schema design is where most real database bugs originate, so the practical skill is auditing a proposed schema *before* data arrives. Given a request to store "student contact info," ask three questions grounded in the schema definition above. First, is each attribute truly a single value, or does it silently pack several together — a `full_name` field, for instance, hides a first name and a last name inside one domain, making them impossible to query or sort independently. Second, is the domain $D_i$ chosen tight enough to be correct: should `phone` be a string domain rather than a numeric one, since leading zeros and dashes are meaningful even though the value looks numeric? Third, which attributes can legitimately have no value, and should their domain include `NULL`, or should a default apply instead? Answering these before writing `CREATE TABLE` prevents a downstream cascade: malformed inserts, ambiguous queries, and costly `ALTER TABLE` migrations once the relation already holds live data.

### aggregate (0.0s)

## Aggregate

A relational query often needs a summary rather than a list of rows: the total revenue, the average score, the number of customers per region. **Aggregation** is the mechanism that produces such summaries. It works in two steps. First, `GROUP BY` partitions the tuples of a relation into disjoint groups, where every tuple in a group shares the same value(s) for the specified group-key attribute(s). Second, an **aggregate function** — `COUNT`, `SUM`, `AVG`, `MIN`, or `MAX` — reduces each group to a single scalar value, so the entire query collapses to one output tuple per group. Formally, if a relation $R$ is partitioned into groups $G_1, G_2, \dots, G_k$ by key value, then for aggregate function $f$ and attribute $A$, the query output is the set $\{(k_i, f(\pi_A(G_i))) : i = 1, \dots, k\}$ — one row of (group key, aggregated value) per partition.

**Worked example.** Consider a table `orders(order_id, customer_id, amount)`. To find each customer's total spending and order count:

```sql
SELECT customer_id, SUM(amount) AS total_spent, COUNT(*) AS num_orders
FROM orders
GROUP BY customer_id;
```

The engine first buckets rows by `customer_id`, then applies `SUM` and `COUNT` independently within each bucket, emitting one summary row per customer — regardless of how many orders that customer placed.

**Problem-solving application: filtering groups with HAVING.** `GROUP BY` and its aggregate functions are the core primitive of this section; `HAVING` is simply the clause that lets you filter on the *result* of that aggregation, so it belongs in the same lesson rather than as a separate topic. The key distinction is *when* filtering happens relative to grouping. `WHERE` filters individual tuples *before* grouping occurs, so it can only reference raw columns like `amount`, not aggregated results. `HAVING` filters *after* aggregation, so it can reference the computed aggregate values themselves. Suppose you want only customers who have spent more than \$500 total, but you also want to exclude any single order under \$10 from counting toward that total:

```sql
SELECT customer_id, SUM(amount) AS total_spent
FROM orders
WHERE amount >= 10
GROUP BY customer_id
HAVING SUM(amount) > 500;
```

Here `WHERE` prunes tuples first (row-level condition on `amount`), then grouping and `SUM` execute, and finally `HAVING` prunes entire groups based on the aggregated `total_spent`. Confusing the two — for instance, writing `WHERE SUM(amount) > 500` — is a common error, since `SUM` does not exist yet at the point `WHERE` is evaluated; the query planner rejects it, because aggregation hasn't happened.

### normalization (9.8s)

## Normalization

A relational schema is well-designed when each fact is stored in exactly one place. Normalization is the process of decomposing a relation $R$ into a set of smaller relations $R_1, R_2, \dots, R_n$ so that the original data can be reconstructed by joining them, while redundancy and the update anomalies it causes — insertion, deletion, and modification anomalies — are eliminated. The theory proceeds through a sequence of increasingly strict conditions, called normal forms, each defined in terms of functional dependencies: a dependency $X \rightarrow Y$ means that the value of attribute set $X$ determines the value of $Y$.

**1NF** requires every attribute to hold a single, atomic value — no repeating groups or lists in a cell. **2NF** requires 1NF plus no partial dependency: for a relation with a composite primary key, every non-key attribute must depend on the *entire* key, not just part of it. **3NF** requires 2NF plus no transitive dependency: a non-key attribute must not depend on another non-key attribute. **BCNF** (Boyce-Codd Normal Form) tightens this further — every determinant (the left side of a functional dependency) must be a candidate key.

**Worked example.** Consider `Enrollment(StudentID, CourseID, StudentName, CourseName, Grade)` with dependencies $StudentID \rightarrow StudentName$ and $CourseID \rightarrow CourseName$. The key is $\{StudentID, CourseID\}$, but $StudentName$ depends only on $StudentID$ — a partial dependency, violating 2NF. Every time a student enrolls in a new course, their name is redundantly re-entered, and if it's misspelled once, the two rows disagree. Decomposing into `Student(StudentID, StudentName)`, `Course(CourseID, CourseName)`, and `Enrollment(StudentID, CourseID, Grade)` removes the redundancy: each name and course title is stored exactly once.

**Problem-solving application.** Given a set of attributes and a set of functional dependencies, the practical task is to find a *minimal cover* of dependencies, group attributes so each relation's non-key attributes depend on the whole key and nothing but the key, and verify the decomposition is lossless — the natural join of the pieces reconstructs the original relation exactly, with no spurious rows. This systematic check-and-decompose procedure is what database designers apply directly to real schemas before deployment.

### query_plan (11.7s)

## Query Plan

A query plan is the sequence of relational operators — scans, joins, sorts, aggregations — that a database's query optimizer selects to execute a SQL statement. SQL itself is declarative: it states *what* result is wanted, not *how* to compute it. The optimizer's job is to translate that declaration into an executable procedure and, critically, to choose the *cheapest* such procedure among many logically equivalent ones.

Consider `SELECT * FROM orders o JOIN customers c ON o.cust_id = c.id WHERE c.region = 'EU'`. One plan scans `customers`, filters by region, then probes an index on `orders.cust_id` for each matching row (index nested-loop join). Another plan scans both tables fully and builds a hash table on the smaller filtered set (hash join). If `region = 'EU'` is highly selective, the first plan touches few rows and wins; if EU customers are most of the table, the hash join's linear scan cost beats repeated index probes. Running `EXPLAIN` (or `EXPLAIN ANALYZE`) on the query reveals which plan was chosen, along with estimated row counts and costs at each step — this is the primary tool for diagnosing slow queries.

The combinatorics behind this choice are what make optimization hard. For a query joining $n$ tables, there are $(n-1)!$ distinct left-deep join orderings (fixing one table as the outer-most relation and permuting the rest), since join is associative and commutative but not cost-equivalent under reordering — joining small filtered tables first minimizes intermediate result sizes. With $n=5$ tables, that's $4! = 24$ orderings; at $n=10$, it's $362{,}880$. Exhaustive search becomes infeasible, so real optimizers use dynamic programming (build optimal plans for subsets of tables, combine them — the classic System R algorithm) for small $n$, and switch to greedy or randomized heuristics (genetic algorithms, simulated annealing) beyond a threshold, trading provable optimality for tractable search time.

Problem-solving application: given a plan from `EXPLAIN` showing a sequential scan feeding a sort-merge join where you expected an index-nested-loop, check three things — does an index exist on the join column, are statistics on the table stale (causing the optimizer to misestimate selectivity), and is the filtered row count actually large enough that a full scan is cheaper. Query tuning is largely the practice of giving the optimizer accurate cost inputs — indexes, up-to-date statistics — rather than second-guessing its search.

### data_warehouse (10.5s)

## Data Warehouse

A data warehouse is a database engineered for analytical queries — aggregations over large historical datasets — rather than for the fast, single-row reads and writes that support day-to-day transactions. Operational systems (OLTP: online transaction processing) store data in **normalized** form, splitting it across many tables to eliminate redundancy and keep updates cheap and consistent. Analytics has the opposite priority: a single query typically needs to summarize millions of rows across many dimensions, so warehouses **denormalize** data into a **star schema** — one large *fact table* (e.g., every sale, with foreign keys and numeric measures) surrounded by smaller *dimension tables* (customer, product, date, store) that describe those measures. This trades storage redundancy for fewer joins and simpler, faster queries.

**Worked example.** Suppose a retailer's OLTP database normalizes orders across `orders`, `order_items`, `customers`, and `products` tables to avoid duplicating customer or product data. In the warehouse, an ETL (extract-transform-load) pipeline flattens this into a `fact_sales` table with columns like `date_id`, `product_id`, `store_id`, `quantity`, `revenue`, joined to dimension tables. A query like "total revenue by product category by month" now touches one fact table and two small dimensions instead of four normalized tables — a query planner can execute it with far fewer joins.

**Problem-solving application.** Two engineering choices make aggregation over billions of rows tractable. First, **columnar storage**: instead of storing each row contiguously, the warehouse stores each column contiguously on disk. A `GROUP BY category, SUM(revenue)` query only reads the `category` and `revenue` columns, skipping the rest — drastically reducing I/O compared to row storage, which would read every column of every row. Second, **vectorized execution**: rather than processing one row at a time (with per-row function-call overhead), the engine operates on batches ("vectors") of values using CPU SIMD instructions, amortizing overhead across thousands of rows per operation.

Given a query, the planner also chooses among **parallel scan strategies** — splitting a table's column chunks across worker threads or nodes, scanning them concurrently, and merging partial aggregates (a pattern analogous to MapReduce: local `SUM`/`COUNT` per partition, then a final combine step). The planner estimates cost based on data statistics (row counts, partition pruning by date range, etc.) to decide how many workers to allocate and whether to prune irrelevant partitions entirely before scanning.
