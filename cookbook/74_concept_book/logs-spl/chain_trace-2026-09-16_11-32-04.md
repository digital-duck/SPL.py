## Memory Cell

A memory cell is a fixed-size, addressable unit of storage: it holds a value, and that value can be read or written by referring to the cell's address rather than to the value itself. This indirection — name the location, not the content — is the foundational abstraction of computing. Every data structure, from an array to a hash table to a linked list, is ultimately a pattern for organizing addresses of memory cells. In this domain, the memory cell is the floor: below it lie transistors, capacitors, and voltage levels, which belong to hardware design, not to the logic of programs.

A memory cell has two defining properties: a fixed width (commonly 8 bits, one byte, though some architectures use different widths) and a unique address, typically a non-negative integer. If a machine has $n$ bits of address space, it can distinguish $2^n$ distinct cells. A 32-bit address space, for instance, addresses $2^{32} \approx 4.3$ billion cells — the historical ceiling behind the "4 GB limit" of 32-bit systems.

**Worked example.** Suppose memory is modeled as a function $M: \text{Address} \to \text{Value}$, where $\text{Address} = \{0, 1, \dots, 2^n - 1\}$ and each value is an 8-bit byte, so $\text{Value} = \{0, 1, \dots, 255\}$. Writing 65 (the ASCII code for 'A') to address 1000 updates the function so that $M(1000) = 65$; reading address 1000 later retrieves that value regardless of what produced it. This is exactly how a C array works under the hood: declaring `char buf[10]` reserves ten consecutive addresses, and `buf[i]` compiles to $M(\text{base} + i)$ — address arithmetic on top of memory cells.

**Problem-solving application.** Suppose a sensor logs one byte per second and you're given 1 MB ($2^{20}$ bytes) of memory. How many seconds of data can you store, and what is the largest address you'll need? The capacity is $2^{20} = 1{,}048{,}576$ cells, so you can log that many seconds (about 12.1 days), and addresses run from $0$ to $2^{20}-1 = 1{,}048{,}575$ — requiring at least 20 bits to represent. This kind of address-space accounting is the first step in any buffer-sizing or memory-budgeting problem you'll encounter in systems programming.

### key (10.4s)

## Key

A **key** is the field (or combination of fields) within a stored record that a data structure or algorithm uses to compare, order, and locate elements. It is distinct from the **value** — the payload of information the record carries, which is typically just moved along wherever the key goes but never inspected by the comparison logic itself. When you sort a list of student records by GPA, the GPA is the key; the student's name, ID, and transcript are the value. The comparison predicate — whether it is `<`, `>`, or a custom `compare(a, b)` function — acts exclusively on the key.

This separation matters because it determines *what* an algorithm is allowed to do. A sorting algorithm that compares full records instead of extracting keys first is doing unnecessary work — and if the value is large (an image, a document, a nested object), that waste compounds badly. The standard technique is **key extraction**: given a record $r$, define a function $k(r)$ that maps it to its key, and have every comparison call $k(r_1)$ versus $k(r_2)$ rather than comparing $r_1$ and $r_2$ directly.

**Worked example.** Suppose you have employee records `(id, name, salary)` and want to sort them by salary, highest first. In Python:

```python
employees = [
    (101, "Ana", 72000),
    (102, "Ben", 95000),
    (103, "Cy",  81000),
]
employees.sort(key=lambda r: r[2], reverse=True)
```

Here `key=lambda r: r[2]` is exactly the extraction function $k(r)$: it tells the sort routine to compare salaries, not tuples. Without it, Python would compare `id` first (since tuple comparison is lexicographic), giving the wrong order entirely.

**Problem-solving application.** Keys generalize beyond sorting. In a hash table, the key is what gets hashed to determine bucket placement; the value is stored alongside but plays no role in the hash function. In a binary search tree, every node's key must satisfy the ordering invariant relative to its subtree, while the value is inert cargo. When designing a lookup system — a database index, a cache, a priority queue — the first design question is always: *what is the key?* Choosing it well (unique, cheap to compare, stable) is often the difference between an efficient structure and a subtly broken one, since duplicate or mutable keys can silently corrupt ordering or retrieval guarantees.

### pointer (11.3s)

## Pointer

A pointer is a value whose contents are interpreted as an address — the location of a memory cell rather than data to be used directly. If an ordinary variable is a box holding a number or a character, a pointer is a box holding the *location* of another box. This single idea is the first genuine departure from the array: an array packs elements into contiguous memory in a fixed layout, so its structure is entirely determined by arithmetic on indices. A pointer breaks that constraint. Once a cell can store the address of another cell, memory need not be laid out in one block at all — cells can live anywhere and still be connected, because the connection is data (an address) rather than physical adjacency.

Formally, let memory be modeled as a function $M: \text{Addr} \to \text{Value}$, mapping addresses to the values stored there. A normal variable $x$ at address $a$ satisfies $M(a) = v$ for some value $v$. A pointer variable $p$ at address $b$ satisfies $M(b) = a$, where $a$ is itself an address — so *dereferencing* $p$, written $*p$, means evaluating $M(M(b))$. This two-step lookup — one to fetch the address, one to fetch the value at that address — is the entire mechanism. Nothing else is added.

Consider linking two integers manually. In C:

```c
int x = 42;
int *p = &x;      // p holds the address of x
printf("%d\n", *p); // dereference: prints 42
*p = 99;             // writes through the pointer
printf("%d\n", x);   // prints 99
```

Here `&x` produces the address of `x`, and `*p` reverses that operation.

The problem-solving payoff appears once pointers connect cells that are *not* adjacent in memory. Suppose you need a list that grows and shrinks arbitrarily, with cheap insertion anywhere — something an array cannot do without shifting every subsequent element, an $O(n)$ operation. Define a cell as a pair $(\text{value}, \text{next})$, where $\text{next}$ is a pointer to another cell or a special null address meaning "no cell." Insertion after a given cell becomes a constant-time rewiring of two pointers, regardless of list size, because nothing physically moves. This is the linked list, and it exists only because a memory cell can hold something other than data — it can hold a reference to where the next piece of the structure lives.

### array (12.1s)

## Array

An array is a data structure that stores a sequence of elements of the same type in a contiguous block of memory. Because every element occupies the same fixed number of bytes, the address of any element can be computed directly from its index — no traversal required. If an array begins at memory address $\text{base}$ and each element occupies $s$ bytes, the address of the element at index $i$ is:

$$\text{address}(i) = \text{base} + i \cdot s$$

This arithmetic gives arrays their defining property: $O(1)$ random access. Reading `arr[5000]` costs the same as reading `arr[0]`, regardless of the array's size.

**Worked example.** Suppose an array of 64-bit integers (8 bytes each) starts at address 1000. To find the address of index 12: $\text{address}(12) = 1000 + 12 \cdot 8 = 1096$. The CPU performs this calculation directly — it never "walks" through the intervening elements the way it would with a linked list. This is also why arrays are cache-friendly: when the processor loads element $i$, it typically pulls a whole cache line containing several neighboring elements into fast memory at once, so accessing $i+1$ right after $i$ is nearly free.

**Problem-solving application.** The contiguity that makes access fast also makes structural change expensive. Inserting an element at index $k$ in an array of length $n$ requires shifting all elements from $k$ to $n-1$ one slot to the right, an $O(n)$ operation in the worst case; deletion is symmetric. This is the central trade-off to reason about when choosing a structure: if your workload is dominated by lookups by position (e.g., accessing pixel data, evaluating a polynomial by coefficient index, or table lookups), an array is close to optimal. If your workload is dominated by frequent insertions or deletions in the middle of the sequence, the $O(n)$ shift cost may dominate, and a different structure — one that sacrifices $O(1)$ access for cheaper restructuring — is usually the better choice. Recognizing this tension between access pattern and mutation pattern is the first real design decision in data structure selection, and nearly every structure built "on top of" arrays (dynamic arrays, hash tables, heaps) exists specifically to push back against one side of this trade-off while preserving the other.

### binary_tree (9.8s)

## Binary Tree

A **binary tree** is a recursive data structure built from a node containing a value and two pointers, `left` and `right`, each either `null` or a reference to another binary tree. Formally, a binary tree $T$ is either empty or a triple $(v, T_L, T_R)$, where $v$ is a value and $T_L, T_R$ are themselves binary trees. This recursive definition is why nearly every operation on trees — search, insertion, traversal — is naturally written as a recursive function that handles the base case (empty tree) and combines results from the left and right subtrees.

The key structural property is **height** $h$, the length of the longest root-to-leaf path. A tree with $n$ nodes has $h \geq \lfloor \log_2 n \rfloor$, because a tree of height $h$ can hold at most $2^{h+1} - 1$ nodes (each level $i$ holds at most $2^i$ nodes). This bound is the reason binary trees matter: if a tree stays **balanced** — height kept near $\log_2 n$ — operations that walk a single root-to-leaf path run in $O(\log n)$ time. If the tree degenerates into a chain (e.g., inserting sorted data into an unbalanced BST), $h$ approaches $n$ and those same operations become $O(n)$, no better than a linked list.

**Worked example.** Consider inserting the values 5, 3, 8, 1, 4 into a binary search tree, where every node's left subtree holds smaller values and its right subtree holds larger ones. Insertion recurses: compare the new value to the current node, descend left or right, and place the new node when a null pointer is reached. Inserting 5, then 3 (left of 5), 8 (right of 5), 1 (left of 3), 4 (right of 3) produces a tree of height 2 for 5 nodes — matching the $O(\log n)$ bound closely, since $\log_2 5 \approx 2.32$.

**Problem-solving application.** Recognizing a binary tree's shape tells you which algorithm to reach for. A **heap** enforces a parent-child ordering (not left/right ordering) to guarantee $O(\log n)$ insertion and extraction of the minimum or maximum — the basis of priority queues and heapsort. A **trie** repurposes the child-pointer idea, using one pointer per possible character rather than just two, to achieve $O(k)$ lookup for a string of length $k$, independent of how many other strings are stored. In each case, the core skill is the same: given an operation, trace which path from root to leaf it must follow, and confirm the tree's balancing invariant keeps that path length at $O(\log n)$.

### comparison (0.0s)

## Comparison

A comparison is a binary predicate: given two elements $a$ and $b$ from a totally ordered set, it returns one of three outcomes — $a < b$, $a = b$, or $a > b$. This is deliberately the *only* operation a comparison-based algorithm is allowed to perform on the data. The algorithm never inspects bits, computes a hash, or indexes into an array by value — it only ever asks "which of these two is smaller?" and branches on the answer. Every sorting algorithm you have likely met — bubble sort, insertion sort, mergesort, quicksort, heapsort — is built entirely out of sequences of these yes/no questions.

Restricting an algorithm to comparisons might look like it weakens it, but it actually makes something powerful provable: a hard lower bound on how fast *any* comparison-based sort can possibly be, regardless of cleverness.

**Worked example.** Suppose you want to sort 3 distinct elements $a, b, c$. There are $3! = 6$ possible orderings. Each comparison you make splits the remaining possibilities roughly in half — a comparison is a yes/no question, so a sequence of $k$ comparisons can distinguish at most $2^k$ outcomes. To distinguish all 6 orderings you need $2^k \geq 6$, so $k \geq 3$ comparisons in the worst case — no algorithm can guarantee sorting 3 elements in 2 comparisons, no matter how it is designed.

**Problem-solving application — the general bound.** For $n$ elements there are $n!$ possible orderings, and a comparison-based algorithm can be modeled as a binary decision tree with one leaf per ordering. A binary tree with $n!$ leaves has depth at least $\log_2(n!)$:

$$
\log_2(n!) = \Omega(n \log n)
$$

by Stirling's approximation. This is why mergesort's and heapsort's $O(n \log n)$ running time is not an accident to be improved upon — it is asymptotically optimal for any algorithm restricted to comparisons. To break the barrier, you must abandon comparison as the sole primitive, which is exactly what non-comparison sorts like counting sort or radix sort do: they exploit structure in the values themselves (e.g., bounded integer range) rather than only asking "which is bigger?"

### binary_search_tree (10.0s)

## Binary Search Tree

A binary search tree (BST) is a binary tree that satisfies one additional invariant at every node: every key in the left subtree is less than the node's key, and every key in the right subtree is greater. Formally, for any node $x$ with key $k(x)$, if $y$ lies in $x$'s left subtree then $k(y) < k(x)$, and if $z$ lies in $x$'s right subtree then $k(z) > k(x)$. This invariant holds recursively at every node, not just the root, so any subtree of a BST is itself a valid BST.

The invariant turns the tree into a physical embodiment of comparison-based search: at each node, comparing the target key to $k(x)$ tells you which of the two subtrees can possibly contain it, and the other subtree is eliminated entirely. Starting from the root, this comparison-and-descend step repeats until the key is found or a null child is reached.

**Worked example.** Insert the keys $15, 6, 18, 3, 7, 17, 20$ in that order into an empty BST. Each insertion walks from the root comparing the new key to existing nodes until it finds an empty spot: $15$ becomes the root; $6 < 15$ goes left; $18 > 15$ goes right; $3 < 15, 3 < 6$ goes to $6$'s left; $7 < 15, 7 > 6$ goes to $6$'s right; $17 < 18$ goes to $18$'s left; $20 > 18$ goes to $18$'s right. Searching for $17$ now takes three comparisons ($15 \to 18 \to 17$) instead of scanning all seven keys.

**Complexity.** If a BST has height $h$, search, insert, and delete each run in $O(h)$ time, since each step descends one level. For a tree built from keys inserted in random order, the expected height is $O(\log n)$, giving expected $O(\log n)$ operations — the same asymptotic behavior as binary search on a sorted array, but with $O(\log n)$ insertion instead of $O(n)$ array shifting.

This bound is not guaranteed, however. Inserting keys already in sorted order — $1, 2, 3, \dots, n$ — produces a tree that is really a linked list: each new key is larger than all previous ones, so it always attaches as a right child, giving height $h = n - 1$ and $O(n)$ operations. This worst case is exactly what motivates self-balancing BSTs (AVL trees, red-black trees), which add rebalancing rules to guarantee $O(\log n)$ height regardless of insertion order.

### hash_table (11.0s)

## Hash Table

A hash table stores key-value pairs in an array of $m$ buckets, using a hash function $h(k)$ to compute an index for key $k$. Insert, lookup, and delete all follow the same pattern: compute $i = h(k) \bmod m$, then operate on bucket $i$. When the hash function distributes keys roughly uniformly, each bucket holds only a constant number of entries on average, so these operations run in amortized $O(1)$ time — dramatically faster than the $O(n)$ scan a plain array requires or the $O(\log n)$ a balanced tree offers.

The catch is collisions: two distinct keys $k_1 \neq k_2$ can hash to the same index, $h(k_1) \bmod m = h(k_2) \bmod m$. Two standard strategies resolve this. **Chaining** stores a linked list at each bucket; a collision just appends to that bucket's list, so lookup degrades to scanning a short list rather than failing. **Open addressing** instead searches for another empty slot in the array itself, following a probe sequence (e.g., linear probing: try $i, i+1, i+2, \dots \pmod m$) until a free slot is found — no auxiliary structure needed, but deletions require care (a "tombstone" marker, not an empty slot, or later lookups will stop searching too early).

**Worked example.** Suppose $m = 7$ and $h(k) = k \bmod 7$. Inserting keys $10, 3, 17$ gives indices $3, 3, 3$ — all three collide. With chaining, bucket 3 becomes a list `[10, 3, 17]`; looking up $17$ means scanning that list. With linear probing, $10$ takes slot 3, $3$ probes to slot 4, $17$ probes to slot 5.

**Why $O(1)$ is "amortized," not guaranteed.** The load factor $\alpha = n/m$ (entries per bucket) governs performance: as $\alpha$ grows, chains lengthen and lookup cost rises toward $O(\alpha)$. Practical implementations resize the array — typically doubling $m$ — once $\alpha$ exceeds a threshold (often $0.7$–$1.0$), rehashing all entries. This resize costs $O(n)$ but happens rarely enough that its cost, spread across all the cheap operations between resizes, averages out to $O(1)$ per operation — the same amortized-cost argument used for dynamic array growth. A poor hash function, or an adversary who chooses keys to collide, can degrade every operation to $O(n)$ regardless of load factor, which is why cryptographically robust or randomized hash functions matter in security-sensitive code.

### compiler_symbol_table (17.1s)

## Compiler Symbol Table

A compiler's symbol table is a dictionary mapping each identifier in a program — a variable, function, or type name — to the attributes the compiler needs to generate correct code: its data type, memory address (or stack offset), scope level, and sometimes size or mutability. Every phase after parsing consults this table: type checking uses it to verify operations are legal, and code generation uses it to emit correct load and store instructions.

The dominant implementation is a hash table, because identifier lookup — "what is the type of `x`?" — happens constantly during compilation, and a hash table gives expected $O(1)$ lookup, insertion, and deletion. The compiler hashes the identifier string to an index and stores the attribute record there, resolving collisions with chaining or open addressing. Since compilers process millions of identifier references in large source files, the difference between $O(1)$ and $O(\log n)$ lookup is measurable in build time.

But hashing destroys order: iterating a hash table yields identifiers in an arbitrary sequence unrelated to how they appear in the source. Some compiler tasks need ordered traversal — for example, allocating stack offsets to local variables in declaration order, or emitting debug symbol tables sorted by address for a debugger. For these tasks, compilers use a balanced BST (red-black tree or AVL tree), which keeps keys in sorted order while still guaranteeing $O(\log n)$ lookup, insertion, and deletion, avoiding the $O(n)$ worst case of an unbalanced tree.

**Worked example.** Consider compiling:
```
int a = 1;
int b = 2;
int c = a + b;
```
The compiler inserts `a`, `b`, `c` into the symbol table as it parses each declaration, recording type `int` and a stack offset (e.g., `a` at `-4`, `b` at `-8`, `c` at `-12`). When it later parses `a + b`, it looks up `a` and `b` in the hash table in $O(1)$ each to confirm both are `int` and to retrieve their addresses for the generated instructions (e.g., `LOAD a`, `LOAD b`, `ADD`, `STORE c`).

**Problem-solving application.** Real compilers combine both structures: a hash table per scope for fast lookup, linked into a scope chain (or stack of tables) to implement nested block scoping — when a name isn't found in the innermost scope's table, the compiler searches outward. A balanced BST is layered on top only when a pass genuinely needs sorted iteration, such as generating a sorted symbol dump for linking or debugging. Choosing between these structures is a direct trade-off between average-case speed and the need for deterministic order — a recurring decision in systems programming beyond compilers alone.
