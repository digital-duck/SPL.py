### proposition (0.0s)

## Proposition

A proposition is a mathematical claim treated as a first-class object — something you can name, store in a variable, pass to a function, and combine with logical connectives, before you ever decide whether it is true. In classical logic, a proposition is just a statement with a truth value: true or false, and nothing else. But in the type-theoretic view used by proof assistants like Lean and Coq, a proposition is a *type*, and a proof of that proposition is a *term* — a piece of evidence — that belongs to that type. This identification is the Curry–Howard correspondence: propositions correspond to types, and proofs correspond to terms inhabiting them. "$P$ is true" becomes "the type $P$ is inhabited" — you can exhibit some object of type $P$.

Concretely, consider the proposition $P : \text{“for all naturals } n, \, n + 0 = n\text{”}$. In a proof assistant this is written as a type:
$$P : \forall n : \mathbb{N}, \, n + 0 = n$$
A proof of $P$ is a term $p : P$ — an object, built by induction, that produces evidence for every $n$ that $n + 0 = n$. If no such term exists, $P$'s type is empty, and the proposition is false or at least unproved. This is why propositions are called "first-class": they aren't external labels attached to statements, they *are* the statements, living in the same universe as the data your program manipulates.

Worked example: take the proposition $\text{Even}(4)$, meaning "4 is divisible by 2." Proving it does not require inventing new logical machinery — it just requires exhibiting a term of the type $\text{Even}(4)$. Concretely, the term is the evidence "$4 = 2 \times 2$": a specific calculation that inhabits the type. The proposition is true precisely because that term exists and type-checks; if you could not produce such a term, $\text{Even}(4)$ would remain unproved.

For problem-solving, this framing turns proof search into type search: to prove a proposition, you don't manipulate abstract truth values — you construct a term and check that it has the right type. When stuck on a proof, ask "what type am I trying to inhabit, and what term would count as evidence for it?" This reframes logical reasoning as concrete, checkable construction, the same discipline as writing a program that must type-check before it runs.

### term (0.0s)

## Term

A **term** is any expression that inhabits a type — a concrete piece of data, a computation, or (in dependently typed systems) a proof, all classified by what kind of thing it is. Writing $t : T$ means "term $t$ has type $T$." Under this reading, $3 : \mathbb{N}$, $\lambda x.\,x+1 : \mathbb{N} \to \mathbb{N}$, and, in a system rich enough to express propositions as types, a proof $p : (n = n)$ are all terms — they differ wildly in what they *are*, but each is judged well-formed and slots into its type the same way a value slots into a variable. Naming a term with `def`, as in `def three := 3`, does not create a new kind of object; it just gives the term `3` (already of type $\mathbb{N}$) a handle you can reuse.

**Worked example.** Take `def add1 := λx. x + 1`. To check this term, a type checker assumes $x$ has type $\mathbb{N}$, then checks the body `x + 1` under that assumption; since addition of naturals returns a natural, `x + 1` has type $\mathbb{N}$, so the whole function $\lambda x.\,x+1$ has type $\mathbb{N} \to \mathbb{N}$. The `def` merely names this term `add1`; every later use of `add1` is definitionally the same term as $\lambda x.\,x+1$, and the checker may freely unfold one into the other.

**Problem-solving application.** This uniform treatment — everything is a term, checked against a type — is what makes the Curry–Howard correspondence work: a proposition is a type, and a proof is a term of that type, checked by the *same* process used for programs. Proving $A \to A$ true is literally the same act as writing a term of type $A \to A$ — namely $\lambda x.\,x$ — and checking that term *is* checking the proof. Practically, this means a proof assistant that rejects your proof is rejecting a term for failing to match the goal type, exactly as it would reject `def bad : ℕ := "hello"` for producing a string where a natural number was expected. So debugging a rejected proof uses the same skill as debugging rejected code: identify what type is expected, identify what type your term actually has, and find where the mismatch enters.

### type (0.0s)

## Type

Every expression in Lean has a type, and the type tells Lean — and you — exactly what the expression is and what you're allowed to do with it. Write `#check 5` and Lean answers `5 : Nat`; write `#check "hello"` and it answers `"hello" : String`. The colon reads "has type": the object on the left belongs to the category on the right. This isn't a comment or a suggestion — it's a guarantee Lean checks mechanically before it will accept anything you write. If you claim `5 : String`, Lean rejects it outright, because `5` genuinely is not a member of the string type.

Types matter because they determine which operations make sense. `Nat` (natural numbers), `Int`, `Bool`, and `String` are the basic types you'll meet first, and every value you construct in Lean belongs to exactly one of them. `#check` is your tool for asking, at any point, which type a given expression has — you don't need to guess or read documentation, you just ask Lean directly.

Types become essential once you try to combine pieces. Suppose Lean has a built-in operation that expects a `Nat` — say, doubling a number — and you hand it a `String` instead, like `"three"`. Lean immediately reports a type mismatch: the operation expects a `Nat`, but you supplied a `String`. This is the payoff of a typed language — the error surfaces the moment you write the mistake, not later when the program runs on bad data. Compare this to writing the same logic in an untyped language, where doubling `"three"` might silently produce `"threethree"` or crash deep inside unrelated code far from where the bad value originated.

This same checking is what makes Lean trustworthy as a proof assistant, not just a programming language: it can verify that a mathematical claim is built correctly for exactly the reason it can verify that a number is used where a number is expected. You'll see how that works once you learn how Lean represents statements and proofs — for now, the idea to hold onto is simpler: everything in Lean has a type, and `#check` is how you ask what it is.

### curry_howard (0.0s)

## Curry Howard

The Curry-Howard correspondence establishes that a proposition and a type are the same object, and that a proof and a program are the same object. The core primitive that makes this concrete is the function type: proving "if $A$ then $B$" is identical to constructing a function of type $A \to B$. A proof is not a separate certificate that a program is correct — the program *is* the proof, and the type checker that accepts the program is simultaneously a proof checker. (The same correspondence extends to "and" and "or," pairing conjunction with a paired-value type and disjunction with a either-branch type, but the function type alone is enough to see how the correspondence works.)

**Worked example.** Consider the proposition "if $A$ implies $B$, and $B$ implies $C$, then $A$ implies $C$" — transitivity of implication. Its type is
$$(A \to B) \to (B \to C) \to (A \to C).$$
A term inhabiting this type is exactly a proof:
$$\lambda f.\, \lambda g.\, \lambda x.\, g\,(f\,x)$$
where $f : A \to B$, $g : B \to C$, $x : A$. Reading this as a program: given a function $f$ from $A$ to $B$ and a function $g$ from $B$ to $C$, compose them by applying $f$ to $x$ and feeding the result to $g$. Reading the exact same expression as a proof: assume $A$ (introduce $x$), apply the hypothesis $f$ to derive $B$, apply the hypothesis $g$ to derive $C$, discharge the assumption. The typechecker's verdict that this term has type $(A \to B) \to (B \to C) \to (A \to C)$ *is* the verification that the transitivity proof is valid. No separate "proof theory" layer runs — the same kernel that accepts well-typed programs accepts valid proofs.

**Problem-solving application.** The correspondence turns theorem-proving into program-writing, and vice versa, entirely through the function type. To prove "$A$ implies $A$" (reflexivity), you must produce a term of type $A \to A$; the identity function $\lambda x.\, x$ is both the program and the proof — nothing else needs to be checked, because the type system itself guarantees that whatever value of type $A$ goes in, a value of type $A$ comes out. Conversely, to prove that an implication is *unprovable* under constructive logic, one must show that no term of the corresponding function type can be built — the type is uninhabited. This is why proof assistants such as Coq, Agda, and Lean are, at the type-checking level, ordinary compilers: verifying a mathematical proof and compiling a program are literally the same act, performed by the same algorithm, one function-type check at a time.

### function_types (0.0s)

## Function Types

A function type has the form $A \to B$: it describes a transformation that consumes a term of type $A$ and produces a term of type $B$. This is the core building block of typed languages, because nearly every computation — arithmetic, string processing, control flow — is ultimately a function applied to an argument. The corresponding term is written using lambda notation, `fun x => e`, where `x` is the parameter and `e` is an expression built from `x` that produces the result. If `x : A` and `e : B`, then `fun x => e : A -> B`.

**Worked example.** Consider a function that doubles an integer:

$$
\texttt{double} : \mathbb{Z} \to \mathbb{Z} \qquad \texttt{double} = \texttt{fun } x \Rightarrow x + x
$$

The type $\mathbb{Z} \to \mathbb{Z}$ tells you, before running anything, that `double` accepts one integer and returns one integer — it cannot be applied to a string or to zero arguments. *Application* is the operation that uses this: given `double : Z -> Z` and `5 : Z`, applying `double 5` yields `10 : Z`. The type checker verifies application by matching the argument's type against the function's input type; a mismatch (e.g., `double "hi"`) is rejected before the program ever runs. This is why function types matter for problem-solving: they let you decompose a task into a pipeline of typed transformations and catch wiring errors statically, rather than as runtime crashes.

**Problem-solving application.** Suppose you need a function that checks whether an integer is even, then routes it to one of two string-producing functions. You'd type this as `isEven : Z -> Bool`, `describeEven : Z -> String`, `describeOdd : Z -> String`, and combine them with a conditional whose branches must both return `String` — the shared return type is enforced by the type system, not by convention. More generally, function types compose: given `f : A -> B` and `g : B -> C`, you can build `g ∘ f : A -> C` by feeding `f`'s output into `g`, and the types alone confirm the composition is legal without inspecting either function's implementation. This is the practical payoff of treating "function" as a type-and-term pair: the type is a contract you can check mechanically, and the term is the concrete recipe that fulfills it.

### proof (0.0s)

## Proof

In type theory, a **proof** is not a separate kind of mathematical object sitting outside the type system — it is a term. Under the Curry-Howard correspondence, a proposition $P$ is itself a type, and to prove $P$ is to exhibit some term $p$ such that $p : P$. The type checker's kernel, the same small piece of code that verifies ordinary program terms have their declared types, verifies proofs by exactly the same mechanism: it checks that $p$ really does have type $P$. There is no separate "proof checker" — proof checking *is* type checking. This single idea — that a proof is just a term of the proposition's type — is the only new primitive this section introduces; everything below is a consequence of it.

**Worked example.** Consider proving $P \to P$, "if $P$ holds, then $P$ holds." Since implication corresponds to the function type, a proof of $P \to P$ is simply a function that takes a term of type $P$ and returns it unchanged:
$$
\lambda (p : P).\ p
$$
The kernel checks this the same way it checks any lambda: it confirms that given an argument of type $P$, the body returns a term of type $P$. No separate "logical" reasoning engine is invoked — the ordinary rule for checking function application *is* the logical inference here. Constructing a proof of a more elaborate implication $A \to B$ works identically: you write a function that consumes a term of type $A$ and, through whatever computation is needed, produces a term of type $B$; the kernel accepts the proof exactly when that function type-checks.

**Problem-solving application.** This identification lets you debug a broken proof exactly as you'd debug a program: a type error from the kernel — "expected term of type $B$, got term of type $A$" — pinpoints precisely which step of the argument is unjustified. Because a proof is nothing more than a term built by ordinary means (applying functions, substituting values, reducing expressions), the strategy for finding one is the same strategy you already use to write code that satisfies a target type: look at what type you need to produce, and work backward to what inputs and operations can produce it. The proposition tells you the type of the object you're hunting for; building the proof is the same skill as writing any other well-typed program.

### theorem_statements (0.0s)

## Theorem Statements

A theorem statement is a formal proposition — a claim about mathematical objects that has been proven true. In the Curry-Howard correspondence, a theorem statement is more than an assertion: it is a *type*. The proposition "if $A$ then $B$" corresponds to the type of functions from $A$ to $B$, written $A \to B$. To state a theorem is to specify a type signature; to prove it is to construct a term that inhabits that type. This single idea — propositions as types, proofs as terms — is the foundation on which proof assistants like Lean and Coq are built: checking a proof reduces to type-checking a program.

**Worked example.** Consider the theorem "for all natural numbers $n$, if $n$ is even then $n+2$ is even." As a type signature this becomes:

$$
\text{thm} : \forall n : \mathbb{N},\ \text{Even}(n) \to \text{Even}(n+2)
$$

Here $\text{Even}(n)$ is itself a type — a term of this type consists of a number $k$ together with the fact that $n = 2k$. The theorem says: given any $n$ and a term of type $\text{Even}(n)$, produce a term of type $\text{Even}(n+2)$. The proof is a function that does exactly this: from a given $k$ with $n = 2k$, it builds $k+1$ together with the fact that $n+2 = 2(k+1)$. In Lean-style pseudocode:

```
theorem even_add_two (n : Nat) (h : Even n) : Even (n + 2) :=
  let ⟨k, hk⟩ := h
  ⟨k + 1, by rw [hk]; ring⟩
```

The line `let ⟨k, hk⟩ := h` unpacks $h$ into its two pieces, $k$ and the fact $hk$, exactly as a function would read off the fields of an argument it was handed.

**Problem-solving application.** This correspondence changes how you *write* a proof: instead of asking "why is this true?" you ask "what function turns the given input types into the required output type?" Applied to the example above, the entire proof is nothing but: unpack the input, add one to the witness, adjust the equation. No cleverness is needed — only matching the shapes correctly. When your proof "doesn't type-check," the theorem-prover is telling you precisely where your reasoning has a gap, the same way a compiler flags a type mismatch in ordinary code. Practicing theorem statements as type signatures is the habit that makes formal proof tractable: decompose the goal type, find or build terms of the required subtypes, and assemble them — proof by construction, not by inspiration.

### tactic_mode (0.0s)

## Tactic Mode

In an interactive theorem prover such as Lean or Coq, a proof is not written as a finished paragraph — it is built one step at a time against a goal state that the system tracks for you. The goal state shows the statement still to be proved, along with the hypotheses currently available. A tactic is a command that transforms this goal state: it may split one goal into several, use a hypothesis to close a goal outright, or rewrite the goal into an equivalent, simpler form. The sequence of tactics you issue, from the original theorem statement to the empty goal list, is the proof — a transcript of the reasoning, executed and checked line by line.

Consider proving $\forall n \in \mathbb{N},\ n + 0 = n$ in Lean. The initial goal state reads `⊢ n + 0 = n`. The tactic `induction n with | zero => rfl | succ k ih => simp [ih]` transforms this single goal into two subgoals: the base case `⊢ 0 + 0 = 0`, closed immediately by `rfl` since it reduces to the same term on both sides; and the inductive case `⊢ k + 1 + 0 = k + 1` with hypothesis `ih : k + 0 = k` available, closed by `simp` rewriting using `ih`. Once both subgoals vanish, the goal list is empty and the proof is complete — Lean reports "no goals," and the tactic script itself stands as the checked proof.

This mechanism matters because it turns proof-writing into a *problem-solving* activity with immediate feedback: after every tactic, you see exactly what remains, so you can choose the next step based on the actual state rather than holding the whole argument in your head. Suppose you are stuck proving $\forall n,\ n \le n + 1$. Applying `intro n` gives goal `⊢ n ≤ n + 1`; applying `exact Nat.le_succ n` closes it directly by citing an existing lemma, no induction needed. If a mismatch appears — say the goal is `⊢ n + 1 ≤ n + 1 + 0` — a tactic like `simp` will normalize `n + 1 + 0` to `n + 1` before you decide how to finish. Because each tactic is a small, checkable transformation, mistakes surface immediately at the step that introduced them, rather than at the end of a long hand-written proof — making tactic mode as much a debugging tool for logic as it is a proof-construction language.

### core_tactics (0.0s)

## Core Tactics

A **tactic** is a command that transforms a proof goal into zero or more simpler subgoals, or closes it outright. A proof in a system like Coq, Lean, or Isabelle is not a static object you hand-assemble; it is a sequence of tactic applications that incrementally rewrite the goal state until nothing remains to prove. This section introduces the first and most fundamental tactic, `intro`; later sections build on it with `exact`, `apply`, `constructor`, and `cases`, each of which manipulates the goal state in its own characteristic way.

**`intro`** moves a hypothesis from the goal into the context. If the goal is $P \to Q$, the implication itself is not something you can act on directly — you first need `P` as an assumption you can reason from. `intro h` strips off the implication, adding `h : P` to the context and leaving `Q` as the new goal. The same tactic handles universal quantification: if the goal is $\forall x, P(x)$, `intro x` introduces a fresh variable `x` into the context and reduces the goal to `P(x)`. In both cases the effect is the same — a binder at the front of the goal disappears, and its bound object becomes something the context can name and use.

Consider proving $\forall n : \text{Nat}, n = n$ in Lean. The goal begins as a universally quantified statement, so `intro n` is the only tactic whose shape matches: it consumes the $\forall$, introduces `n : Nat` into the context, and leaves the new goal `n = n`. Nothing has been proved yet — `intro` never closes a goal on its own — but the quantifier that was blocking further progress is gone, and the goal is now stated purely in terms of an object already in scope.

The problem-solving discipline `intro` teaches is the first step of goal-directed reasoning: before choosing any other tactic, check whether the goal's outermost structure is a binder — an implication or a quantifier — because as long as it is, no other tactic can touch what lies underneath. Only once `intro` has stripped away every such binder does the goal expose the structure (a conjunction, an equality, an inductive hypothesis) that the remaining tactics are built to attack.

### equality_rfl (0.0s)

## Equality Rfl

In type theory, equality is not merely a claim checked by an outside judge — it is itself a *type*, written $a = b$ (or $\mathrm{Eq}\ a\ b$), whose inhabitants are the proofs that $a$ and $b$ are equal. To prove $a = b$, you must produce a term that lives in this type. The simplest possible such term comes from reflexivity: for any $a$, the value $a$ is trivially equal to itself. This gives the constructor `rfl`, short for "reflexivity," which builds a proof of $a = a$ for free — no argument required beyond the fact that both sides are the same term.

The subtlety, and the reason `rfl` is more powerful than it first appears, is that the equality checked here is *definitional* equality, not merely syntactic identity. Two expressions count as the same for `rfl` if they reduce — via computation, unfolding definitions, and pattern matching — to the identical normal form. This is why `2 + 2 = 4` is provable by `rfl`: the typechecker evaluates $2+2$ using the recursive definition of addition on natural numbers, reduces it step by step until it reaches the term $4$, and then observes that both sides of the equation are now syntactically identical. No algebraic manipulation, no external proof — the computation *is* the proof.

**Worked example.** Consider proving `2 * (3 + 4) = 14` in a language like Lean or Agda. Even though the two sides look nothing alike on the page, `rfl` succeeds: the typechecker first reduces the inner sum `3 + 4` to `7`, then reduces the product `2 * 7` to `14`, following the same recursive definitions of addition and multiplication used earlier. Since both sides normalize to the literal `14`, the equality holds definitionally — no matter how many nested steps of unfolding it takes to get there.

**Problem-solving application.** When you attempt a proof and are unsure how much manual work is needed, always try `rfl` first — it costs nothing and often closes goals involving concrete computations on literals. When `rfl` fails, the error itself is diagnostic: it tells you the two sides did *not* reduce to a common form, signaling that the equality depends on a variable, an unproven lemma, or a case split — meaning you need induction, rewriting, or a more general theorem beyond raw computation.

## Math Education Games

Since Kurt Gödel and Alan Turing, mathematicians have known that proof is mechanical: a valid argument is a finite sequence of steps, each licensed by a rule, checkable without judgment or intuition. A *proof assistant* — software like Lean, Coq, or Isabelle — exploits this fact. You state a goal, apply tactics (small commands like "induction on $n$" or "rewrite using this lemma"), and the kernel either accepts the step or rejects it instantly, with no partial credit and no ambiguity. The Natural Number Game, built on Lean, turns this loop into a game: each level is a theorem about $\mathbb{N}$, each tactic is a move, and the "win" condition is a closed proof.

Consider the first real hurdle beginners face: proving $\forall n \in \mathbb{N},\ n + 0 = n$. This looks trivial until you notice that addition on the natural numbers is *defined* by recursion — $n + 0 = n$ by definition, but $0 + n = n$ requires induction, since $0$ sits on the wrong side of the recursive definition. A player who has only read about induction in a textbook often cannot see why one direction is free and the other is not. Typing `induction n with n ih` and watching Lean split the goal into a base case ($0 + 0 = 0$) and a step case (assume $0 + n = n$, prove $0 + (n+1) = n+1$) makes the logical skeleton of induction physically visible: you cannot fake the inductive hypothesis `ih`, because the kernel checks whether it was actually used correctly in the successor case.

This is the pedagogical payoff of instant kernel feedback: it separates "I think this proof works" from "this proof works," collapsing the usual delay between submitting a proof set and getting it graded from days to milliseconds. That immediacy rewards experimentation — a player can try `rw [add_zero]`, watch it fail or succeed, and adjust, the same way a student learns a video game's mechanics through repeated trial rather than a rulebook.

For problem-solving practice, try proving $\forall n\, m \in \mathbb{N},\ n + m = m + n$ (commutativity) using only `induction`, `rw`, and previously proved lemmas like `add_zero` and `succ_add` — the natural next level after `add_zero` and `zero_add`, and the one where most players discover why lemma order matters.
