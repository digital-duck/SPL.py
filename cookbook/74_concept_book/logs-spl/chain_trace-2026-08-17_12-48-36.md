## Connected Graph

A **connected graph** is a graph in which every pair of vertices is linked by at least one path. In other words, you can travel from any vertex to any other vertex by following edges — no vertex is stranded in isolation. If even one pair of vertices has no path between them, the graph is **disconnected**, and the isolated pieces are called **connected components**.

Connectivity is one of the most fundamental properties in graph theory because it determines whether a network can actually function as a single unit. A social network is connected if every person can reach every other person through some chain of mutual friends. A power grid is connected if every substation is reachable from every other. A road network is connected if every city can be reached from every other city.

**Worked Example.** Consider a graph with five vertices: $A, B, C, D, E$ and edges $\{A\text{-}B,\ B\text{-}C,\ C\text{-}D,\ D\text{-}A,\ D\text{-}E\}$. Starting from $A$: you can reach $B$ directly, $C$ via $B$, $D$ directly, and $E$ via $D$. Since every vertex is reachable from $A$ (and by symmetry, from any vertex), this graph is connected. Now remove edge $D\text{-}E$. Vertex $E$ has no remaining edges, so it becomes isolated. The graph splits into two components — $\{A, B, C, D\}$ and $\{E\}$ — and is now disconnected.

**Problem-Solving Application.** To check connectivity in code, use a depth-first search (DFS) or breadth-first search (BFS) starting from any vertex and count how many vertices you visit. If the count equals the total number of vertices, the graph is connected.

```python
def is_connected(graph: dict[str, list[str]]) -> bool:
    if not graph:
        return True
    start = next(iter(graph))
    visited = set()
    stack = [start]
    while stack:
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            stack.extend(graph[node])
    return len(visited) == len(graph)
```

Here `graph` is an adjacency list mapping each vertex to its neighbors. This runs in $O(V + E)$ time — linear in the number of vertices $V$ and edges $E$ — making it practical even for large networks. A natural follow-up question: how many edges must you add to make a disconnected graph connected? The answer is the number of connected components minus one, since each added edge can merge exactly two components into one.

## Walk

A **walk** in a graph is any sequence of vertices where each consecutive pair is connected by an edge. Formally, a walk from vertex $v_0$ to vertex $v_k$ is written $v_0, e_1, v_1, e_2, v_2, \ldots, e_k, v_k$, where each $e_i$ is an edge joining $v_{i-1}$ to $v_i$. Crucially, a walk places no restriction on repetition — you may revisit vertices and reuse edges as many times as you like. The **length** of a walk is the number of edges traversed, counted with repetition.

This permissiveness is what distinguishes a walk from a path (no repeated vertices) or a trail (no repeated edges). Think of a walk as a literal stroll through a city where backtracking and looping are perfectly allowed.

**Worked example.** Consider the graph below with five vertices:

$$A - B - C - D, \quad B - D, \quad C - E$$

The sequence $A, B, D, B, C, E$ is a valid walk of length 5: it starts at $A$, crosses to $B$, jumps to $D$, backtracks to $B$, continues to $C$, then reaches $E$. The edge $\{A,B\}$ appears once, but $\{B,D\}$ and $\{B,C\}$ are each used once — no rule is broken even though vertex $B$ appears twice.

**Problem-solving application.** Walks become practically important when you model repetitive processes — web crawlers following links, random walks in probability, or Markov chains in statistics. A key result connects walks to matrix algebra: if $A$ is the **adjacency matrix** of a graph, then the entry $(A^k)_{ij}$ counts the number of distinct walks of length exactly $k$ from vertex $i$ to vertex $j$. This gives an efficient way to answer questions like "how many 3-step paths connect two users in a social network?" without enumerating every route manually.

For example, if $A^3$ evaluated at position $(i,j)$ returns 4, then there are exactly 4 walks of length 3 between those two users, including any that double back on themselves.

When you need to guarantee efficiency — no wasted steps — you restrict the walk to a trail or path. But when you need to count all possible routes or model a process that can loop, the unrestricted walk is the right tool.

## Hamilton Path

A **Hamiltonian path** in a graph is a path that visits every vertex exactly once. Unlike an Eulerian path — which requires traversing every *edge* once — a Hamiltonian path is concerned with covering every *node*. If the path starts and ends at the same vertex, it becomes a **Hamiltonian cycle**. The concept is named after William Rowan Hamilton, who sold a puzzle in 1857 asking players to find such a route along the edges of a dodecahedron.

Formally, given a graph $G = (V, E)$, a Hamiltonian path is a sequence of vertices $v_1, v_2, \ldots, v_n$ such that every vertex in $V$ appears exactly once and each consecutive pair $(v_i, v_{i+1})$ is connected by an edge in $E$.

**Worked Example.** Consider this undirected graph with five vertices:

```
A — B — C
|       |
D — — — E
```

Edges: $\{A$-$B,\ B$-$C,\ C$-$E,\ E$-$D,\ D$-$A,\ B$-$E\}$

Is there a Hamiltonian path from $A$ to $C$? Try: $A \to B \to E \to D$ — that misses $C$. Try: $A \to D \to E \to B \to C$ — all five vertices, each once, connected by valid edges. Yes, this is a Hamiltonian path. Notice there is no guaranteed algorithm to find one quickly; you reason by systematic trial and backtracking.

**Problem-Solving Application.** Hamiltonian path problems appear constantly in scheduling and logistics. Suppose a delivery driver must visit six warehouses, each connected by specific road links, without revisiting any location. Modeling warehouses as vertices and roads as edges, finding a Hamiltonian path gives a valid route.

In code, a standard backtracking approach works for small graphs:

```python
def hamiltonian_path(graph, path, visited):
    if len(path) == len(graph):
        return path
    current = path[-1]
    for neighbor in graph[current]:
        if neighbor not in visited:
            visited.add(neighbor)
            result = hamiltonian_path(graph, path + [neighbor], visited)
            if result:
                return result
            visited.remove(neighbor)
    return None
```

This runs in $O(n!)$ in the worst case — Hamiltonian path is NP-complete, meaning no known polynomial-time algorithm exists for arbitrary graphs. For large instances, heuristics or approximation algorithms replace exact search.

### hamilton_cycle (14.3s)

## Hamilton Cycle

A **Hamilton cycle** (also called a Hamiltonian cycle) is a closed path through a graph that visits every vertex exactly once before returning to the starting vertex. Unlike an Euler circuit — which traverses every *edge* exactly once — a Hamilton cycle cares about vertices. The distinction matters in practice: planning a delivery route that hits every city once is a Hamilton cycle problem; inspecting every road segment once is an Euler circuit problem.

Not every graph has a Hamilton cycle, and no simple necessary-and-sufficient condition is known for general graphs. This is partly why the problem sits at the heart of theoretical computer science: determining whether a Hamilton cycle exists in an arbitrary graph is NP-complete. For small or structured graphs, however, we can find one (or rule one out) systematically.

**Worked example.** Consider a graph with five cities — A, B, C, D, E — and edges AB, BC, CD, DE, EA, AC, CE. Does a Hamilton cycle exist?

Start at A. A connects to B, C, and E. Try A → B → C → D → E → A. Check: every vertex appears exactly once, and the final edge EA exists. This is a valid Hamilton cycle. The route visits all five cities and returns home without repetition.

Now remove edge EA. Can we still find a Hamilton cycle? A's only connections are B and C. Any cycle through A must use both. Try A → B → C → D → E — but E now connects only to D (we just came from there) and no edge back to A exists. Try A → C → B — but B connects only to A and C, both visited. Every path dead-ends. No Hamilton cycle exists in this modified graph.

**Problem-solving application.** Hamilton cycle problems appear directly in logistics (the Travelling Salesman Problem is the weighted version — minimize total distance of a Hamilton cycle), circuit board design, and DNA sequencing. When you tackle one: (1) identify vertices with degree 2 — both their edges are forced into any cycle; (2) prune edges that would create a premature subcycle; (3) use backtracking if the forced edges don't close a full cycle. For large instances, exact solutions are computationally expensive, so heuristics like nearest-neighbor or genetic algorithms are used in practice. Understanding the structure of forced edges is what separates efficient search from blind trial-and-error.

### hamiltonian_graph (15.5s)

## Hamiltonian Graph

A **Hamiltonian graph** is a graph that contains a *Hamiltonian cycle* — a closed path that visits every vertex exactly once before returning to the starting vertex. Named after the Irish mathematician William Rowan Hamilton, who popularized the idea through a puzzle played on a dodecahedron in 1857, the concept sits at the heart of combinatorial optimization and has direct applications in routing, scheduling, and circuit design.

The distinction from an Eulerian circuit is worth locking in: an Eulerian circuit traverses every **edge** exactly once; a Hamiltonian cycle visits every **vertex** exactly once. A graph can have one, both, or neither.

**Worked example.** Consider a graph with five cities — A, B, C, D, E — and edges connecting: A–B, B–C, C–D, D–E, E–A, and A–C. Does a Hamiltonian cycle exist?

Start at A. Try the path A → B → C → D → E → A. Check the edges:
- A–B ✓, B–C ✓, C–D ✓, D–E ✓, E–A ✓

Every vertex appears exactly once, and we return to A. This is a Hamiltonian cycle, so the graph is Hamiltonian.

Now remove the edge E–A. The graph is no longer Hamiltonian, because any cycle must close back to A, and the only path from E leads back through D–C–B, revisiting vertices.

**Problem-solving application.** Hamiltonian cycle detection is famously NP-complete — no known efficient algorithm solves it for arbitrary graphs. In practice, you either exploit structure or use heuristics.

One useful sufficient condition is **Dirac's Theorem**: if every vertex in a simple graph with $n \geq 3$ vertices has degree at least $n/2$, the graph is guaranteed to be Hamiltonian. This gives you a fast screening check — compute degrees, compare to $n/2$, and if all qualify, you can assert a Hamiltonian cycle exists without searching for it explicitly.

```python
def dirac_check(adj: dict[str, list[str]]) -> bool:
    n = len(adj)
    return all(len(neighbors) >= n / 2 for neighbors in adj.values())
```

For small graphs, backtracking search with pruning is practical. For large real-world instances — think the Traveling Salesman Problem, which asks for the *shortest* Hamiltonian cycle — approximation algorithms and dynamic programming (Held–Karp, $O(2^n n^2)$) are the standard tools. Recognizing the Hamiltonian structure in a problem is often the first and most important step.

## Weighted Graph

A **weighted graph** is a graph $G = (V, E, w)$ where each edge $e \in E$ carries a numerical label called a **weight**, given by a function $w: E \to \mathbb{R}$. Weights typically represent cost, distance, time, or capacity — whatever quantity governs the relationship between two nodes. Without weights, a graph only tells you whether a connection exists; with weights, it tells you how much that connection "costs."

Formally, for an edge between vertices $u$ and $v$, we write $w(u, v)$ for its weight. A path from a source to a destination accumulates weight by summing the weights of every edge it traverses:

$$\text{path cost} = \sum_{i=1}^{k} w(v_{i-1},\, v_i)$$

The central problem in most weighted-graph applications is finding the **shortest path** — the one with minimum total weight.

**Worked example.** Consider four cities: A, B, C, D. The road network (with travel times in minutes) looks like this:

```
A --10-- B
|        |
6        3
|        |
C --15-- D
 \      /
   --4--
```

To get from A to D, two candidate paths are:
- $A \to B \to D$: cost $10 + 3 = 13$
- $A \to C \to D$: cost $6 + 4 = 10$

The shortest path is $A \to C \to D$ with total weight 10.

**Problem-solving application.** Dijkstra's algorithm finds shortest paths efficiently. It maintains a priority queue of (cost, node) pairs, always expanding the cheapest unvisited node next.

```python
import heapq

def dijkstra(graph, start):
    dist = {node: float('inf') for node in graph}
    dist[start] = 0
    pq = [(0, start)]          # (cost, node)

    while pq:
        cost, u = heapq.heappop(pq)
        if cost > dist[u]:
            continue           # stale entry
        for v, w in graph[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                heapq.heappush(pq, (dist[v], v))
    return dist

graph = {
    'A': [('B', 10), ('C', 6)],
    'B': [('D', 3)],
    'C': [('D', 4)],
    'D': []
}
print(dijkstra(graph, 'A'))
# {'A': 0, 'B': 10, 'C': 6, 'D': 10}
```

The result confirms that the shortest distance from A to D is 10. Weighted graphs appear everywhere real decisions involve trade-offs: network routing minimizes latency, logistics networks minimize shipping cost, and GPS navigation minimizes travel time — all using the same underlying structure.

## Directed Hamiltonian Transformation

**Definition.** A *directed Hamiltonian transformation* converts a graph or computational problem into an equivalent directed graph in which finding a Hamiltonian path (a path that visits every vertex exactly once) solves the original problem. The two moves most commonly called by this name are (1) *edge duplication*, which replaces each undirected edge $\{u, v\}$ with the two directed arcs $u \to v$ and $v \to u$, and (2) *vertex splitting*, which replaces each vertex $v$ with a pair $v^{\text{in}}$ and $v^{\text{out}}$ connected by a single arc $v^{\text{in}} \to v^{\text{out}}$, forcing any Hamiltonian path to pass through $v$ exactly once. These transformations appear constantly in NP-completeness reductions and in algorithm design wherever a path constraint must be encoded as a graph structure.

**Worked example.** Suppose you have an undirected graph with vertices $\{A, B, C\}$ and edges $\{A{-}B, B{-}C, A{-}C\}$. Apply vertex splitting so the goal becomes finding a directed Hamiltonian path from $A^{\text{in}}$ to $C^{\text{out}}$:

1. Replace $A$ with $A^{\text{in}} \to A^{\text{out}}$, similarly for $B$ and $C$.
2. Replace each undirected edge $\{u, v\}$ with arcs $u^{\text{out}} \to v^{\text{in}}$ and $v^{\text{out}} \to u^{\text{in}}$.

The resulting directed graph has six vertices. A Hamiltonian path from $A^{\text{in}}$ to $C^{\text{out}}$ in the new graph corresponds to a Hamiltonian path from $A$ to $C$ in the original — the splitting gadget enforces the "visit once" constraint mechanically.

**Problem-solving application.** In practice, this transformation lets you reduce one graph problem to another so you can reuse known algorithms or solvers. Consider a scheduling problem: $n$ tasks must each be completed exactly once, and task $i$ must precede task $j$ (a directed dependency). Model each task as a vertex with a split $i^{\text{in}} \to i^{\text{out}}$, and add arc $i^{\text{out}} \to j^{\text{in}}$ for each dependency. A Hamiltonian path through this directed graph is a valid execution order that honours every dependency and visits every task once.

When attacking such a problem:
- Draw the original dependency graph.
- Apply vertex splitting to enforce the "exactly once" constraint.
- Add arcs only for valid transitions.
- Feed the resulting digraph to a Hamiltonian-path solver or backtracking search.

The key insight is that the transformation relocates the constraint — "visit each node once" — from the search algorithm into the graph structure itself, making the structure do the bookkeeping instead of the code.

## Optimal Hamilton Cycle

A **Hamilton cycle** in a graph is a closed path that visits every vertex exactly once before returning to the starting point. When the graph is weighted — meaning each edge carries a cost such as distance, time, or price — an **optimal Hamilton cycle** is the one with the smallest possible total weight. Finding it is the core of the famous **Traveling Salesman Problem (TSP)**: given a set of cities and the cost of traveling between each pair, find the cheapest round trip that visits every city exactly once.

The challenge is scale. A graph with $n$ cities has $(n-1)!/2$ distinct Hamilton cycles. For $n = 10$ that is 181,440 cycles; for $n = 20$ it exceeds $10^{17}$. Checking all of them is computationally infeasible for large inputs, so practitioners rely on exact algorithms for small instances and heuristics or approximations for large ones.

**Worked example.** Suppose four cities — A, B, C, D — have travel costs given by a symmetric matrix:

$$\begin{pmatrix} 0 & 10 & 15 & 20 \\ 10 & 0 & 35 & 25 \\ 15 & 35 & 0 & 30 \\ 20 & 25 & 30 & 0 \end{pmatrix}$$

There are three distinct cycles to evaluate:

| Cycle | Total cost |
|---|---|
| A → B → C → D → A | $10 + 35 + 30 + 20 = 95$ |
| A → B → D → C → A | $10 + 25 + 30 + 15 = 80$ |
| A → C → B → D → A | $15 + 35 + 25 + 20 = 95$ |

The optimal Hamilton cycle is **A → B → D → C → A** with total cost **80**.

**Problem-solving application.** When exact enumeration is too slow, the **nearest-neighbor heuristic** provides a fast approximation: start at any city, always travel next to the closest unvisited city, and return home at the end. Applied to the example above starting at A: A → B (cost 10) → D (cost 25) → C (cost 30) → A (cost 15) = 80, which happens to be optimal here. In general the heuristic can miss the true optimum, but it runs in $O(n^2)$ time versus the exponential cost of brute force. For guaranteed optimality on larger instances, algorithms like branch-and-bound or integer linear programming are used in practice.

## Traveling Salesman Problem

A salesperson needs to visit a set of cities exactly once and return home — what is the shortest possible route? This deceptively simple question defines the **Traveling Salesman Problem (TSP)**: given $n$ cities and the distances between every pair, find the minimum-cost Hamiltonian cycle (a closed tour that visits each city exactly once).

TSP is famous not just as a puzzle but as a canonical **NP-hard** problem. For $n$ cities, the number of distinct tours is $(n-1)!/2$, which grows faster than any polynomial. For 20 cities that is already over $10^{16}$ tours — exhaustive search is hopeless in practice, so real solutions rely on smart heuristics and approximation algorithms.

**Nearest-neighbor heuristic — worked example.** Suppose you have four cities: A, B, C, D with distances:

|   | A | B | C | D |
|---|---|---|---|---|
| A | — | 2 | 9 | 6 |
| B | 2 | — | 5 | 4 |
| C | 9 | 5 | — | 3 |
| D | 6 | 4 | 3 | — |

Start at A. Nearest unvisited city: B (distance 2). From B, nearest unvisited: D (distance 4). From D, nearest unvisited: C (distance 3). Return home: C → A (distance 9). Tour: A → B → D → C → A, total cost $2 + 4 + 3 + 9 = 18$.

Is this optimal? The tour A → B → C → D → A costs $2 + 5 + 3 + 6 = 16$. The greedy heuristic missed it — a reminder that "always pick the closest next city" does not guarantee a globally optimal solution.

**Problem-solving with code.** For small instances you can try all permutations; for larger ones, use established libraries:

```python
from itertools import permutations

distances = {
    ('A','B'):2, ('A','C'):9, ('A','D'):6,
    ('B','C'):5, ('B','D'):4, ('C','D'):3
}

def dist(a, b):
    return distances.get((a,b), distances.get((b,a)))

cities = ['A','B','C','D']
best = float('inf')
best_tour = None

for perm in permutations(cities[1:]):   # fix A as start
    tour = ['A'] + list(perm) + ['A']
    cost = sum(dist(tour[i], tour[i+1]) for i in range(len(tour)-1))
    if cost < best:
        best, best_tour = cost, tour

print(best_tour, best)   # ['A', 'B', 'C', 'D', 'A'] 16
```

For real-world scale — logistics routing, circuit board drilling, genome sequencing — practitioners use **OR-Tools**, **LKH**, or metaheuristics like simulated annealing, which trade provable optimality for tractable runtime. Understanding TSP teaches you when to seek exact solutions versus when to settle for "good enough, fast."
