### exact_integer (13.0s)

## Exact Integer

Every integer in mathematics is exact: $7$, $-42$, and $2^{100}$ are each a single, definite value with no ambiguity. Most programming languages betray this idea. A 32-bit or 64-bit integer type stores numbers in a fixed number of bits, so once a computation exceeds that range, the result silently wraps around or overflows — the computer starts lying about arithmetic. Sage refuses to do this. Every Sage `Integer` is arbitrary-precision: it grows however many digits are needed to represent the value exactly, with no upper bound tied to hardware word size. Computing $2^{100}$ in Sage does not overflow and does not round to a nearby floating-point approximation — it returns the one true 31-digit integer, stored digit by digit, just as a mathematician would write it.

**Worked example.** In Sage,
```
sage: 2^100
1267650600228229401496703205376
```
This is not an estimate; it is the exact value, and Sage will use it in further computation without loss. Contrast this with a language using fixed 64-bit integers, where $2^{100}$ cannot be represented at all and the computation either overflows to a meaningless bit pattern or is silently truncated. Sage's `Integer` type instead allocates memory dynamically, so the representable range is limited only by available memory, not by a hardware register.

**Problem-solving application.** Exact integers matter whenever a computation must be trusted, not merely approximated — factoring large numbers, computing exact binomial coefficients for combinatorics, or verifying number-theoretic identities like Fermat's Little Theorem. Consider $100!$, which has 158 digits:
```
sage: factorial(100)
93326215443944152681699238856266700490715968264381621468592963895217599993229915608941463976156518286253697920827223758251185210916864000000000000000000000000
```
A floating-point computation of $100!$ would lose all precision beyond about 15–17 significant digits, making it useless for checking, say, whether $100!$ is divisible by $99^3$. With exact integers, `factorial(100) % 99^3 == 0` returns a provably correct `True` or `False`, because every digit above is exact. This is the floor of exactness that the rest of Sage's number system — rationals, exact reals, symbolic expressions — is built on top of: integers are where "exact" begins.

### parent_structure (10.4s)

## Parent Structure

Every object you construct in Sage lives inside a mathematical structure called its **parent** — a ring, field, or other algebraic set that governs how the object behaves under arithmetic. Where Python asks `type(x)`, Sage asks `x.parent()`, and the answer is not a data type but a piece of mathematics: the integers $\mathbb{Z}$, the rationals $\mathbb{Q}$, the finite field $\mathrm{GF}(7)$, or the symbolic ring $\mathrm{SR}$. This matters because the *same* numeral, say $3$, means something different depending on where it lives. As an element of $\mathbb{Z}$, $3$ has no multiplicative inverse; as an element of $\mathbb{Q}$, it does ($1/3$); as an element of $\mathrm{GF}(7)$, its inverse is $5$, since $3 \cdot 5 \equiv 1 \pmod 7$.

**Worked example.** Consider the following:

```python
a = 3
print(a.parent())              # Integer Ring
b = QQ(3)
print(b.parent())              # Rational Field
c = GF(7)(3)
print(c.parent())              # Finite Field of size 7
print(1/c)                     # 5
print(1/a)                     # 1/3  (Sage promotes to QQ automatically)
```

Sage's default integer `3` already prints `1/3` under division because Sage silently *coerces* it into $\mathbb{Q}$ when needed — but that coercion is only possible because Sage knows both parents ($\mathbb{Z}$ and $\mathbb{Q}$) and knows there is a structure-preserving map $\mathbb{Z} \hookrightarrow \mathbb{Q}$ between them. In $\mathrm{GF}(7)$, no such map to $\mathbb{Q}$ exists — division is intrinsic to the field itself, computed via modular inverses, not by leaving the structure.

**Problem-solving application.** Whenever an operation between two Sage objects fails with a `TypeError: no common canonical parent`, the fix is to inspect `.parent()` on each operand and decide, explicitly, which structure the computation should happen in — then coerce with `QQ(x)`, `GF(p)(x)`, or `SR(x)` before combining them. For instance, mixing a matrix over $\mathbb{Z}$ with one over $\mathrm{GF}(7)$ will raise an error unless you coerce both into a common parent first, since matrix rank, invertibility, and even equality depend on which ring the entries are drawn from. Treating `.parent()` as your first diagnostic — before checking values — is the habit that prevents a large class of Sage errors.

### polynomial_rings (9.9s)

## Polynomial Rings

A polynomial ring $R[x]$ is the set of all polynomials in the variable $x$ with coefficients drawn from a ring $R$, together with the usual operations of addition and multiplication. The choice of $R$ is not cosmetic — it determines what questions about a polynomial can even be answered. Over $\mathbb{Z}[x]$, the polynomial $2x - 1$ has no root, because $\tfrac{1}{2} \notin \mathbb{Z}$. Over $\mathbb{Q}[x]$, it does. Sage makes this dependency explicit: rather than treating a polynomial as a free-floating expression, it requires you to declare the ring first, via `PolynomialRing(QQ, 'x')`, and every polynomial you build lives inside that declared structure as a first-class object with a known *parent*.

This matters because operations like `factor()`, `gcd()`, and `roots()` are not universal algorithms — their correct behavior depends on the ring. Factoring $x^2 - 2$ over $\mathbb{Q}[x]$ gives an irreducible polynomial, since $\sqrt{2}$ is irrational; the same polynomial factors as $(x - \sqrt{2})(x + \sqrt{2})$ over $\mathbb{R}[x]$. A system that doesn't track the ring cannot distinguish these answers — it would have to guess or default to floating-point approximation, silently trading exactness for convenience.

```python
R.<x> = PolynomialRing(QQ, 'x')
f = x^4 - 5*x^2 + 6
print(f.factor())        # (x^2 - 3) * (x^2 - 2) -- irreducible over QQ
print(f.roots())          # [] -- no rational roots

S.<x> = PolynomialRing(QQbar, 'x')  # algebraic closure of QQ
g = S(f)
print(g.roots())          # four exact algebraic-number roots
```

The practical payoff is exact computation with certified correctness. Suppose you need the greatest common divisor of $f(x) = x^3 - x$ and $g(x) = x^2 - 1$ to simplify a rational function $\tfrac{f(x)}{g(x)}$ before integrating it symbolically. Working in $\mathbb{Q}[x]$, `gcd(f, g)` runs the Euclidean algorithm for polynomials — repeated division with remainder, exactly analogous to integer gcd — and returns $x - 1$ (up to a unit), letting you cancel the shared factor and reduce $\tfrac{f(x)}{g(x)}$ to $x(x+1)$ with no rounding error anywhere in the pipeline.

### number_theory_sage (10.8s)

## Number Theory Sage

Number theory concerns the arithmetic structure of integers — divisibility, primality, and congruences — but its computations quickly outgrow pencil and paper. Factoring a 40-digit number or testing primality of a 300-digit one is infeasible by trial division, yet these operations sit at the core of modern cryptography (RSA, Diffie–Hellman) and algorithm design. Sage wraps the PARI/GP library, a C library purpose-built for number theory, so these industrial-strength computations run at interactive speed inside a readable Python-like syntax.

Four operations anchor this toolkit. `factor(n)` returns the prime factorization of $n$, guaranteed correct by the Fundamental Theorem of Arithmetic: every integer $n > 1$ has a unique expression $n = p_1^{e_1} p_2^{e_2} \cdots p_k^{e_k}$ as a product of primes. `is_prime(n)` certifies primality using a combination of fast probabilistic tests (Miller–Rabin) and deterministic proofs (APR-CL), sidestepping the need to trust a merely "probable" answer. `euler_phi(n)` computes Euler's totient function, $\varphi(n) = \#\{k : 1 \le k \le n,\ \gcd(k,n)=1\}$, which for a factorization $n = \prod p_i^{e_i}$ satisfies

$$
\varphi(n) = n \prod_{p_i \mid n} \left(1 - \frac{1}{p_i}\right).
$$

Finally, `crt(a, b, m, n)` solves the Chinese Remainder Theorem system $x \equiv a \pmod{m}$, $x \equiv b \pmod{n}$ for coprime $m, n$, returning the unique solution modulo $mn$.

These are not independent tricks — they compose. RSA key generation, for instance, needs `is_prime` to find two large primes $p, q$, `euler_phi` to compute $\varphi(pq) = (p-1)(q-1)$ for the private exponent, and `crt` to accelerate decryption via the CRT-optimized RSA algorithm:

```python
p, q = random_prime(2^512), random_prime(2^512)
n = p * q
phi = euler_phi(n)          # = (p-1)*(q-1)
e = 65537
d = inverse_mod(e, phi)
factor(n)                   # infeasible for an attacker without p, q
```

The problem-solving payoff is that Sage lets you verify cryptographic parameters, explore conjectures (e.g., checking Goldbach's conjecture across a range), or prototype an attack on toy-sized keys — all without reimplementing decades of optimized number-theoretic algorithms yourself.

### finite_fields (12.4s)

## Finite Fields

A field is a set with addition and multiplication where every nonzero element has a multiplicative inverse. Finite fields (Galois fields) are fields with finitely many elements. Two facts govern them completely: a finite field of order $q$ exists if and only if $q = p^n$ for a prime $p$ and positive integer $n$, and any two finite fields of the same order are isomorphic. So "the" field of order $q$ is written $GF(q)$, or $\mathbb{F}_q$.

The simplest case, $GF(p)$ for prime $p$, is arithmetic modulo $p$: the elements are $\{0, 1, \dots, p-1\}$, and addition/multiplication wrap around via reduction mod $p$. Every nonzero element has an inverse precisely because $p$ is prime — for any $a \not\equiv 0$, $\gcd(a,p)=1$, so Bézout's identity gives integers $x, y$ with $ax + py = 1$, meaning $x$ is $a^{-1} \pmod p$. This is why $GF(p)$ fails if $p$ isn't prime: in $\mathbb{Z}/6\mathbb{Z}$, the element $2$ has no inverse since $\gcd(2,6)=2$.

Extension fields $GF(p^n)$ for $n > 1$ can't be built from integers mod $p^n$ — that ring has zero divisors. Instead, take the polynomial ring $\mathbb{F}_p[x]$ and quotient by an irreducible polynomial $f(x)$ of degree $n$:
$$GF(p^n) = \mathbb{F}_p[x] / \langle f(x) \rangle.$$
Elements are polynomials of degree less than $n$ with coefficients in $\mathbb{F}_p$; multiplication reduces modulo $f(x)$. For example, $GF(4) = \mathbb{F}_2[x]/\langle x^2+x+1\rangle$ has elements $\{0, 1, x, x+1\}$; here $x \cdot x = x^2 \equiv x+1$ (since $x^2+x+1 \equiv 0$), and one checks $x \cdot (x+1) = x^2+x \equiv 1$, so $x$ and $x+1$ are mutual inverses.

This construction is the engine behind AES, which operates on $GF(2^8) = \mathbb{F}_2[x]/\langle x^8+x^4+x^3+x+1\rangle$, and behind Reed–Solomon error-correcting codes. In Sage, verify irreducibility and build the field directly:

```python
R.<x> = GF(2)[]
f = x^8 + x^4 + x^3 + x + 1
f.is_irreducible()          # True
F = GF(2^8, name='a', modulus=f)
F.multiplicative_generator()
```

Problem-solving application: to invert an element $a(x) \in GF(p^n)$, run the extended Euclidean algorithm on $a(x)$ and $f(x)$ in $\mathbb{F}_p[x]$, exactly as ordinary integer inversion mod $p$ uses extended Euclid on integers — the polynomial and integer cases are the same algorithm over different rings.

## Cryptography

Cryptography is the mathematics of transforming information so that only intended parties can recover it, using operations that are easy to compute in one direction but computationally infeasible to reverse without a secret key. Modern public-key cryptography rests on number-theoretic problems in finite structures — the integers modulo $n$, finite fields, and elliptic curves — where "hard" has a precise complexity-theoretic meaning: no known algorithm solves the problem in time polynomial in the size of the input.

**RSA** exploits the difficulty of integer factorization. Choose two large primes $p, q$, compute $n = pq$ and $\phi(n) = (p-1)(q-1)$. Pick a public exponent $e$ coprime to $\phi(n)$, and compute the private exponent $d$ satisfying
$$
ed \equiv 1 \pmod{\phi(n)}.
$$
Encryption is $c \equiv m^e \pmod n$; decryption is $m \equiv c^d \pmod n$. This works by Euler's theorem: since $ed \equiv 1 \pmod{\phi(n)}$, we have $ed = 1 + k\phi(n)$, so $c^d \equiv m^{ed} \equiv m \cdot (m^{\phi(n)})^k \equiv m \pmod n$. Security requires factoring $n$ to be infeasible — true for $n$ with hundreds of digits, false for small $n$, which is exactly why you should experiment with small values before trusting the scheme.

**Discrete logarithms** underlie Diffie–Hellman key exchange: in a cyclic group (e.g. $(\mathbb{Z}/p\mathbb{Z})^*$) with generator $g$, computing $g^a \bmod p$ is fast, but recovering $a$ from $g^a \bmod p$ is hard. Two parties publish $g^a \bmod p$ and $g^b \bmod p$, then each raises the other's value to their own secret, both arriving at $g^{ab} \bmod p$ without ever transmitting $a$ or $b$.

**Elliptic-curve cryptography** replaces $(\mathbb{Z}/p\mathbb{Z})^*$ with the group of points on a curve $y^2 = x^3 + ax + b \pmod p$, where point addition plays the role of multiplication. The elliptic-curve discrete log problem is believed harder per bit than its integer counterpart, so ECC achieves RSA-level security with much shorter keys — the reason it dominates mobile and embedded systems.

**Worked application:** With $p=61, q=53$, $n=3233$, $\phi(n)=3120$, choosing $e=17$ gives $d=2753$ (via the extended Euclidean algorithm). Encrypting $m=65$: $c = 65^{17} \bmod 3233 = 2790$; decrypting recovers $m = 2790^{2753} \bmod 3233 = 65$. Implementing this by hand in a language with modular exponentiation (Python's `pow(m, e, n)`) is the fastest way to internalize why key size, not obscurity, is what makes cryptography trustworthy.
