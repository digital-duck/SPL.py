## Binary Search Tree

**Definition.** A *binary search tree* (BST) is a rooted binary tree in which every node $v$ stores a key $k(v)$ drawn from a totally ordered set, subject to the *BST invariant*: for every node $v$, all keys in the left subtree of $v$ are strictly less than $k(v)$, and all keys in the right subtree of $v$ are strictly greater than $k(v)$. Formally, if $L(v)$ and $R(v)$ denote the left and right subtrees,

$$\forall u \in L(v):\ k(u) < k(v), \qquad \forall u \in R(v):\ k(u) > k(v).$$

This invariant holds recursively at every node, not merely at the root.

**Worked Example.** Insert the sequence $\langle 5, 3, 7, 1, 4 \rangle$ into an initially empty BST. The first key, $5$, becomes the root. Key $3 < 5$ goes left; $7 > 5$ goes right. Key $1 < 5$, then $1 < 3$, so it becomes the left child of $3$. Key $4 < 5$, then $4 > 3$, so it becomes the right child of $3$. The resulting tree has height $h = 2$ and satisfies the BST invariant at every node. An in-order traversal (left $\to$ root $\to$ right) yields $\langle 1, 3, 4, 5, 7 \rangle$—the keys in sorted order, which is a direct consequence of the invariant.

**Key Theorem (Search Complexity).** A search, insertion, or deletion in a BST containing $n$ nodes requires $O(h)$ comparisons, where $h$ is the height of the tree. For a *balanced* BST, $h = \Theta(\log n)$, giving $O(\log n)$ worst-case operations. In the degenerate case—keys inserted in sorted order—the tree degenerates to a linked list with $h = n - 1$ and $O(n)$ operations. Self-balancing variants (AVL trees, red–black trees) maintain $h = O(\log n)$ unconditionally.

**Lab Cell (SymPy/Python).**

```python
# Minimal BST node; insert and in-order traversal
class Node:
    def __init__(self, key):
        self.key, self.left, self.right = key, None, None

def insert(root, key):
    if root is None:
        return Node(key)
    if key < root.key:
        root.left = insert(root.left, key)
    else:
        root.right = insert(root.right, key)
    return root

def inorder(root):
    return [] if root is None else inorder(root.left) + [root.key] + inorder(root.right)

root = None
for k in [5, 3, 7, 1, 4]:
    root = insert(root, k)

print(inorder(root))   # → [1, 3, 4, 5, 7]
```

## Block Store

### Definition

A **block store** is an abstract data structure that partitions a finite sequence of elements into contiguous, fixed-size segments called *blocks*, and provides indexed access to each block as an atomic unit. Formally, let $S = (s_0, s_1, \ldots, s_{n-1})$ be a sequence of $n$ elements drawn from a universe $\mathcal{U}$. Given a block size $b \in \mathbb{Z}^+$, the block store $\mathcal{B}(S, b)$ is the ordered collection

$$\mathcal{B}(S, b) = \bigl(B_0,\, B_1,\, \ldots,\, B_{k-1}\bigr), \qquad k = \lceil n / b \rceil,$$

where the $i$-th block is defined by

$$B_i = \bigl(s_{ib},\, s_{ib+1},\, \ldots,\, s_{\min((i+1)b,\, n) - 1}\bigr).$$

The final block $B_{k-1}$ may be a *partial block*, containing $n - (k-1)b \leq b$ elements. The two primitive operations are **read** $\texttt{get}(i)$, returning $B_i$ in $O(1)$ index time, and **write** $\texttt{put}(i, B)$, replacing $B_i$ with a new block $B$ of the same capacity.

### Worked Example

Let $S = (3, 1, 4, 1, 5, 9, 2, 6, 5)$, so $n = 9$, and let $b = 4$. Then $k = \lceil 9/4 \rceil = 3$ and

$$B_0 = (3, 1, 4, 1), \quad B_1 = (5, 9, 2, 6), \quad B_2 = (5).$$

The element at flat index $j = 6$ lives in block $i = \lfloor 6/4 \rfloor = 1$ at local offset $r = 6 \bmod 4 = 2$, so $s_6 = B_1[2] = 2$. This two-level addressing — block index followed by intra-block offset — is the structural basis for page-based memory systems and external-memory algorithms.

### Key Theorem

**Theorem (Block-Transfer Complexity).** Scanning all $n$ elements of $\mathcal{B}(S, b)$ requires exactly $k = \lceil n/b \rceil$ block reads. Consequently, any algorithm that accesses elements solely through sequential block reads has I/O complexity $\Theta(n/b)$, a factor of $b$ better than element-wise access.

*Proof sketch.* Each $\texttt{get}(i)$ retrieves exactly $b$ elements (or fewer for the last block). Since the blocks partition $S$ without overlap, the total number of reads equals the number of blocks $k$. $\square$

## External Memory Model

**Definition.** The *external memory model* (also called the I/O model or disk-access model) is a formal computational framework introduced by Aggarwal and Vitter (1988) to analyze algorithms whose data sets exceed the capacity of main memory. The model is parameterized by three quantities:

- $N$ — the number of data elements in the problem instance,
- $M$ — the number of elements that fit in internal (main) memory, $M < N$,
- $B$ — the number of elements transferred in a single block between external storage and internal memory, $1 \le B \le M$.

Computation proceeds in two alternating phases: *internal computation*, which is free, and *I/O operations*, each of which moves exactly one block of $B$ contiguous elements between external and internal memory. The cost of an algorithm is measured exclusively by the number of I/O operations, denoted $\mathrm{IO}(N, M, B)$.

**Worked Example.** Consider scanning an array of $N$ integers stored on disk. Reading every element requires loading $\lceil N/B \rceil$ blocks sequentially. For $N = 10^8$ records, $B = 10^4$ records per disk page, and $M = 10^6$, the scan costs $\lceil 10^8 / 10^4 \rceil = 10^4$ I/O operations — four orders of magnitude fewer than $N$, illustrating why $B$ is the central amplification factor.

**Key Theorem (Sorting Lower Bound).** Any comparison-based sorting algorithm in the external memory model requires

$$\Omega\!\left(\frac{N}{B}\log_{M/B}\frac{N}{B}\right)$$

I/O operations in the worst case. The algorithm *merge sort* adapted to external memory achieves this bound: it reads and writes $O(N/B)$ blocks per merge pass and requires $O(\log_{M/B}(N/B))$ passes, giving total I/O cost

$$O\!\left(\frac{N}{B}\log_{M/B}\frac{N}{B}\right).$$

The logarithm base $M/B \gg 2$ explains why external merge sort vastly outperforms naive in-memory sort applied to disk-resident data.

**Lab Cell (SymPy).**

```python
from sympy import symbols, ceiling, log, simplify

N, M, B = symbols('N M B', positive=True)

scan_cost   = ceiling(N / B)
sort_cost   = (N / B) * log(N / B) / log(M / B)   # O-notation form

# Evaluate for concrete parameters

```

## B Tree

A **B tree** of order $m$ is a rooted, balanced search tree satisfying four invariants: (1) every node holds between $\lceil m/2 \rceil - 1$ and $m - 1$ keys; (2) the root holds between $1$ and $m - 1$ keys; (3) all leaves reside at the same depth; and (4) a node with $k$ keys has exactly $k + 1$ children. Keys within each node are stored in sorted order, and the subtree rooted at child pointer $i$ contains only keys in the open interval $(k_{i-1}, k_i)$, where $k_0 = -\infty$ and $k_{k+1} = +\infty$.

**Worked example.** Consider a B tree of order $m = 3$ (commonly called a **2–3 tree**), so each internal node holds 1 or 2 keys and has 2 or 3 children. Begin with the empty tree and insert the sequence $10, 20, 5, 6, 12, 30, 7$.

- Insert $10, 20$: root becomes $[10 \mid 20]$.
- Insert $5$: root would require 3 keys, exceeding $m - 1 = 2$. Split at median $10$; promote $10$ to a new root with children $[5]$ and $[20]$.
- Continue inserting $6, 12, 30, 7$. Each insertion places the key in the appropriate leaf; whenever a node overflows, the median key is promoted to the parent, and splits cascade upward as needed.

After all insertions the tree has height 2, with the root holding the promoted medians and all original keys residing in leaves at uniform depth.

**Key theorem (height bound).** For a B tree of order $m$ storing $n$ keys, the height $h$ satisfies
$$h \leq \log_{\lceil m/2 \rceil} \frac{n + 1}{2}.$$
Because $m$ is typically chosen so that a node fits in one disk block (e.g., $m \approx 100$–$1000$), $h$ rarely exceeds 3 or 4 in practice, making both search and insertion $O(\log n)$ in the number of disk accesses — the primary motivation for B trees in database and file-system design.

**Lab cell.**

```python
from sympy import floor, log, ceiling

def btree_max_height(n: int, m: int) -> int:
    """Upper bound on B-tree height."""
    return int(floor(log((n + 1) / 2, ceiling(m / 2))))

# Example: order-100 B tree with one million keys
print(btree_max_height(10**6, 100))   # expected: 3
```

Running this cell confirms that even at $n = 10^6$ and $m = 100$, the theoretical height bound is 3, illustrating why B trees dominate storage-backed index structures.

## B Plus Tree

**Definition.** A *B+ tree* of order $m$ is a rooted, balanced search tree satisfying four invariants: (1) every internal node has between $\lceil m/2 \rceil$ and $m$ children; (2) the root has between $2$ and $m$ children (unless it is a leaf); (3) all data records are stored exclusively in the leaf nodes; and (4) the leaf nodes are linked in a doubly-linked list sorted by key. Internal nodes store only *separator keys* that route searches downward, while leaves store key–value pairs. Because every path from root to leaf has identical length $h = \lceil \log_{\lceil m/2 \rceil} n \rceil$, the tree is height-balanced by construction.

Formally, let $T$ be a B+ tree of order $m$ containing $n$ keys. The height satisfies

$$h \leq \log_{\lceil m/2 \rceil} n,$$

and every search, insertion, and deletion runs in $O(\log n)$ time with respect to key comparisons, while requiring at most $O(h)$ disk I/O operations — the primary motivation for large $m$ in database systems.

**Worked Example.** Consider a B+ tree of order $m = 4$ (each internal node holds up to 3 separator keys and 4 child pointers). Insert keys $\{10, 20, 30, 40, 50\}$ in order. After inserting 10, 20, 30, the root leaf is full. Inserting 40 triggers a *leaf split*: the leaf $[10,20,30,40]$ splits into $L_1 = [10,20]$ and $L_2 = [30,40]$, and the separator key $30$ is *promoted* to the new internal root. Inserting 50 places it in $L_2 = [30,40,50]$ without overflow. The resulting tree has internal root containing separator $30$, with $L_1$ and $L_2$ linked sequentially — enabling a range query $[20,45]$ to scan $L_1 \to L_2$ without revisiting the root.

**Theorem (Range Query Efficiency).** A range query $[a, b]$ on a B+ tree of order $m$ with $n$ keys runs in $O(\log n + k/m)$ I/O operations, where $k$ is the number of records in $[a, b]$.

*Proof sketch.* The search for $a$ costs $O(\log n)$ comparisons descending to a leaf. Because leaves are linked and each node holds $\Theta(m)$ records, scanning $k$ results requires $O(k/m)$ additional node accesses. $\square$

**Lab Cell (SymPy).**

```python
import sympy as sp

m, n, k = sp.symbols('m n k', positive=True, integer=True)

height_bound = sp.ceiling(sp.log(n, sp.ceiling(m / 2)))
range_io     = sp.ceiling(sp.log(n, sp.ceiling(m / 2))) + sp.ceiling(k / m)

print("Height bound h ≤", height_bound)
print("Range query I/O:", range_io)
print("Evaluate (m=4, n=1000, k=50):",
      range_io.subs({m: 4, n: 1000, k: 50}))
```

## Btree Filesystems Databases

### Definition

A **B-tree of order $m$** is a self-balancing search tree satisfying four invariants: (1) every node holds between $\lceil m/2 \rceil - 1$ and $m - 1$ keys; (2) all leaf nodes reside at the same depth $h$; (3) each internal node with $k$ keys has exactly $k + 1$ children; and (4) keys within a node are stored in sorted order, partitioning the subtrees below them. For a tree containing $n$ keys, the height satisfies

$$h \leq \log_{\lceil m/2 \rceil} \frac{n+1}{2},$$

guaranteeing that search, insertion, and deletion each require $O(\log n)$ disk accesses — a critical bound because secondary storage I/O dominates runtime in filesystem and database workloads.

### Worked Example

Consider a B-tree of order $m = 4$ (at most 3 keys per node). Suppose we insert the key sequence $\{10, 20, 5, 6, 12, 30, 7, 17\}$. After inserting 10, 20, 5 the root holds $[5, 10, 20]$. Inserting 6 overflows the root; the median key 10 is **promoted** and two children $[5, 6]$ and $[20]$ are created. Continuing, each overflow triggers a split and, if necessary, propagates a promoted key upward. The final tree has height 2, with the root $[10, 17]$ separating three leaf nodes. Any search traverses at most 2 nodes regardless of $n$, compared with $O(n)$ comparisons in an unbalanced structure.

### Key Theorem

**Theorem (Disk-Access Bound).** Let a B-tree of order $m$ index $n$ records. The number of node reads to satisfy any point query is at most

$$\left\lfloor \log_{\lceil m/2 \rceil}(n) \right\rfloor + 1.$$

*Proof sketch.* Each level of the tree partitions the key space by a factor of at least $\lceil m/2 \rceil$. After $d$ levels, at most $\lceil m/2 \rceil^d$ distinct subtrees remain. Setting $\lceil m/2 \rceil^d \geq n$ and solving yields $d \geq \log_{\lceil m/2 \rceil} n$, so the search reaches a leaf within $\lfloor \log_{\lceil m/2 \rceil} n \rfloor + 1$ reads. $\blacksquare$

Filesystems such as HFS+ and NTFS use B-tree variants to index directory entries, while database engines (InnoDB, PostgreSQL) use B$^+$-trees — a refinement storing all records at leaf level and chaining leaves — to support efficient range scans.
