## Comparison

A comparison is a binary predicate: given two elements $a$ and $b$ from a totally ordered set, it returns one of three outcomes — $a < b$, $a = b$, or $a > b$. This is deliberately the *only* operation a comparison-based algorithm is allowed to perform on the data. The algorithm never inspects bits, computes a hash, or indexes into an array by value — it only ever asks "which of these two is smaller?" and branches on the answer. Every sorting algorithm you have likely met — bubble sort, insertion sort, mergesort, quicksort, heapsort — is built entirely out of sequences of these yes/no questions.

Restricting an algorithm to comparisons might look like it weakens it, but it actually makes something powerful provable: a hard lower bound on how fast *any* comparison-based sort can possibly be, regardless of cleverness.

**Worked example.** Suppose you want to sort 3 distinct elements $a, b, c$. There are $3! = 6$ possible orderings. Each comparison you make splits the remaining possibilities roughly in half — a comparison is a yes/no question, so a sequence of $k$ comparisons can distinguish at most $2^k$ outcomes. To distinguish all 6 orderings you need $2^k \geq 6$, so $k \geq 3$ comparisons in the worst case — no algorithm can guarantee sorting 3 elements in 2 comparisons, no matter how it is designed.

**Problem-solving application — the general bound.** For $n$ elements there are $n!$ possible orderings, and a comparison-based algorithm can be modeled as a binary decision tree with one leaf per ordering. A binary tree with $n!$ leaves has depth at least $\log_2(n!)$:

$$
\log_2(n!) = \Omega(n \log n)
$$

by Stirling's approximation. This is why mergesort's and heapsort's $O(n \log n)$ running time is not an accident to be improved upon — it is asymptotically optimal for any algorithm restricted to comparisons. To break the barrier, you must abandon comparison as the sole primitive, which is exactly what non-comparison sorts like counting sort or radix sort do: they exploit structure in the values themselves (e.g., bounded integer range) rather than only asking "which is bigger?"

### memory_access (0.0s)

## Memory Access

Random-access memory (RAM) lets a program read or write the value stored at any address in constant time, $O(1)$, regardless of how large the memory is or how far the address sits from the last one accessed. This is the second computational radical: a primitive so basic it is usually invisible, yet it is what makes arrays, hash tables, and index arithmetic possible. Contrast this with a tape-based or purely comparison-based model, where reaching position $k$ costs $O(k)$ steps. The $O(1)$ guarantee is what lets an array `A` support `A[i]` in constant time no matter what `i` is — the hardware computes the physical address as `base + i * element_size` and jumps there directly.

**Worked example.** Suppose you need to count how many times each grade (A–F) appears in a class of $n$ students. A comparison-based approach — sorting the grades, then scanning for runs — costs $\Theta(n \log n)$. But because grades map to a small, known set of indices ($0$ through $4$), you can allocate a counts array of size 5 and, for each student, directly increment `counts[grade_to_index(g)]`. Each increment is $O(1)$ random access, so the whole tally runs in $\Theta(n)$ — no comparisons, no sorting, just direct addressing.

**Problem-solving application.** This is the mechanism behind every algorithm that beats the $\Omega(n \log n)$ comparison-sorting lower bound: radix sort and counting sort exploit random access to place each element directly into its correct bucket using its value (or a digit of its value) as an index, rather than comparing it against other elements. Hash tables use the same idea one layer removed — a hash function converts an arbitrary key into an array index, so lookup, insertion, and deletion are $O(1)$ on average, again by using computed addresses instead of comparisons. The pattern to recognize: whenever a problem lets you convert a value into a bounded index — a digit, a character, a remainder mod $n$ — random access lets you replace searching or comparing with direct placement, often dropping the complexity class entirely. The tradeoff is space: these techniques typically require memory proportional to the range of possible index values, not just to $n$.

### recursion (0.0s)

## Recursion

Recursion is a special case of reduction in which a problem is solved by reducing it to one or more smaller instances of *itself*, until the instances become trivial to solve directly. The trick to designing a recursive solution is to imagine a "Recursion Fairy" — an oracle that will correctly solve any smaller instance of your problem for you. Your only job is to (1) define a **base case** simple enough to solve without help, and (2) show how to combine the fairy's answer(s) on smaller inputs into a correct answer for your input.

**Worked example: factorial.** Define $n! = n \cdot (n-1)!$ for $n > 0$, with base case $0! = 1$. If the fairy hands you $(n-1)!$, you multiply by $n$ and you're done. In code:

```python
def factorial(n):
    if n == 0:
        return 1                 # base case
    return n * factorial(n - 1)  # trust the fairy on n-1
```

**Why this works — the formal justification.** Trusting the fairy is not hand-waving; it is mathematical induction in disguise. The base case is the induction basis. The recursive step assumes the fairy's answer is correct for all smaller inputs (the induction hypothesis) and shows the combining step preserves correctness (the inductive step). Since every recursive call strictly decreases $n$ toward the base case, the recursion terminates, and induction guarantees the result is correct for every $n$.

**Problem-solving application: Fibonacci and efficiency.** Define $F(n) = F(n-1) + F(n-2)$, $F(0)=0, F(1)=1$. A direct translation of this recurrence into code is correct but wasteful: it recomputes $F(k)$ exponentially many times, giving time complexity $T(n) = T(n-1) + T(n-2) + O(1)$, which solves to $O(\phi^n)$ where $\phi \approx 1.618$. Recognizing this inefficiency is itself a problem-solving skill: by having the fairy remember answers she's already computed (memoization) or by building answers bottom-up (dynamic programming), the same recursive structure runs in $O(n)$ time. This pattern — trust the fairy, verify by induction, then analyze and optimize the resulting recurrence — is the core discipline for applying recursion to real algorithmic problems, from tree traversal to divide-and-conquer sorting.

### dynamic_programming (0.0s)

## Dynamic Programming

Dynamic programming (DP) solves a problem by breaking it into overlapping subproblems, solving each one exactly once, and storing the result so it never has to be recomputed. It applies whenever a problem has two properties: **optimal substructure** (an optimal solution to the whole problem is built from optimal solutions to its subproblems) and **overlapping subproblems** (the same subproblem recurs many times during recursion, rather than each subproblem being distinct). When both hold, DP converts an exponential-time recursive algorithm into a polynomial-time one by trading recursion's repeated computation for memory access to a stored answer.

**Worked example.** Consider the Fibonacci sequence, defined by $F(n) = F(n-1) + F(n-2)$ with $F(0)=0$, $F(1)=1$. A naive recursive implementation recomputes $F(n-2)$ once for every call to $F(n-1)$ and $F(n)$, so the number of calls grows as $O(2^n)$ — specifically, the recursion tree has $T(n) = T(n-1) + T(n-2) + O(1)$, whose solution grows exponentially (proportional to $\phi^n$ where $\phi$ is the golden ratio). DP fixes this two ways:

- **Memoization (top-down):** keep a cache (array or hash map) of already-computed values; before recursing, check the cache. Each of the $n$ distinct subproblems is now computed once, giving $O(n)$ time and $O(n)$ space.
- **Tabulation (bottom-up):** build an array iteratively, computing $F(0), F(1), \dots, F(n)$ in order, so each value is read directly rather than recursed into. This also runs in $O(n)$ time and can be reduced to $O(1)$ space since only the last two values are ever needed.

**Problem-solving application.** The general recipe for applying DP to a new problem is: (1) define the subproblem precisely, usually as a function of one or more indices (e.g., $dp[i]$ = best answer using the first $i$ items); (2) write a recurrence expressing $dp[i]$ in terms of smaller subproblems; (3) identify the base case(s); (4) decide an evaluation order (recursion with memoization, or iteration) that guarantees each subproblem's dependencies are solved before it is. For example, in the classic 0/1 knapsack problem, $dp[i][w]$ = maximum value achievable using the first $i$ items with capacity $w$, with recurrence $dp[i][w] = \max(dp[i-1][w],\ v_i + dp[i-1][w-w_i])$ when item $i$ fits. Filling this table takes $O(n \cdot W)$ time, replacing an otherwise exponential search over item subsets. Recognizing this pattern — recursive structure plus repeated subcalls — is the key skill: whenever brute-force recursion revisits the same state, DP is the tool that makes it tractable.

### greedy (0.0s)

## Greedy

A greedy algorithm builds a solution by making the choice that looks best *right now*, at every step, and never revisits that choice. This is what distinguishes greedy from dynamic programming: DP considers subproblems and combines their optimal solutions, while greedy commits immediately and moves forward. The catch is that "always take the locally best option" is only guaranteed to produce a globally optimal solution for problems that have the **greedy-choice property** — a proof obligation, not an assumption. Formally, a problem exhibits this property if a globally optimal solution can be reached by making a locally optimal (greedy) choice first, then optimally solving the remaining subproblem. Many problems also require **optimal substructure** (an optimal solution contains optimal solutions to subproblems), which greedy shares with DP, but greedy additionally needs that no later choice can ever force you to undo an earlier one.

**Worked example — activity selection.** Given $n$ activities with start and finish times $(s_i, f_i)$, select the maximum number that don't overlap. The greedy strategy: sort by finish time, then repeatedly pick the activity with the earliest finish time compatible with what's already chosen. Proof sketch of correctness: let $a_1$ be the activity with earliest finish time. Suppose an optimal solution $O$ doesn't include $a_1$; let $a_j \in O$ be its earliest-finishing activity. Since $f_1 \le f_j$, swapping $a_j$ for $a_1$ in $O$ yields another optimal solution that does include $a_1$. This exchange argument shows the greedy choice is always safe — the hallmark of the greedy-choice property.

**Where it fails and where it must be proven.** Huffman coding (merging the two least-frequent nodes at each step) and Dijkstra's algorithm (finalizing the closest unvisited vertex, restricted to non-negative edge weights) are correct for the same reason: an exchange argument shows the locally cheapest choice never blocks a global optimum. But 0/1 knapsack — greedily taking items by best value-to-weight ratio — fails, because taking a high-ratio item can leave unusable leftover capacity, and only a full DP over subsets recovers the optimum. General combinatorial optimization has no such guarantee at all, which is why "try greedy first, then prove or disprove the exchange argument" is the standard practical workflow.

### compression (12.0s)

## Compression

Compression removes redundancy from data so it occupies fewer bits, while preserving the ability to reconstruct the original (lossless) or an acceptably close approximation (lossy). The theoretical floor for lossless compression is set by Shannon's source coding theorem: a symbol source with entropy $H$ (in bits per symbol) cannot be compressed, on average, below $H$ bits per symbol without loss of information. Two classical algorithms approach this floor from different angles and together underlie nearly every modern codec.

**Huffman coding** assigns variable-length binary codes to symbols based on frequency, giving common symbols shorter codes. It is a greedy algorithm: repeatedly merge the two least-frequent symbols (or subtrees) into a new node whose weight is their sum, until one tree remains; the depth of each leaf becomes its code length. Because more frequent symbols end up shallower, the algorithm provably produces an optimal *prefix-free* code — no code is a prefix of another, so a stream of concatenated codes can be decoded unambiguously without delimiters. The resulting average code length is within one bit of the entropy $H$, i.e. $H \le L_{\text{avg}} < H + 1$.

**Worked example.** Given symbols with frequencies A:5, B:9, C:12, D:13, E:16, E:45, Huffman's algorithm merges the two smallest weights repeatedly (5+9=14, 12+13=25, 14+16=30, 25+30=55, 55+45=100), producing codes where the most frequent symbol gets 1 bit and rarer symbols get 3–4 bits — beating a fixed 3-bit code for 6 symbols.

**LZ77/LZ78** attack a different redundancy: repeated substrings rather than skewed symbol frequencies. LZ77 slides a window over previously seen data and replaces a repeated substring with a (distance, length) back-reference, found via a dynamic-programming-style search for the longest match ending at each position. LZ78 instead builds a dictionary of previously seen phrases incrementally, referencing dictionary indices.

**Application.** Real-world codecs layer both ideas: DEFLATE (used in gzip, zip, PNG) runs LZ77 to eliminate repeated sequences, then Huffman-codes the resulting literals and match lengths to squeeze out remaining statistical redundancy. Zstandard extends this with Finite State Entropy coding for faster, near-entropy-optimal symbol coding at scale.
