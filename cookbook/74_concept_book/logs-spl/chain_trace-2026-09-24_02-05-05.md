### term (0.0s)

## Term

You've already met terms without naming them: `3`, `x + 1`, `fun n -> n * 2` — every one of these is a *term*, and every term has a *type*, the category of thing it produces when evaluated. A number like `3` has type $\mathbb{N}$ or $\mathbb{Z}$; a function like the doubler has a function type, written with an arrow: $\mathbb{N} \to \mathbb{N}$ means "takes a natural number in, gives a natural number back." The relationship between a term and its type is written with a colon: $3 : \mathbb{N}$ means "the term $3$ inhabits the type $\mathbb{N}$," or more casually, "$3$ is a $\mathbb{N}$."

This colon notation is the one new idea here, but it's worth sitting with, because it applies to *everything* — not just numbers. Once you know a term's type, you know what you're allowed to do with it: a term of type $\mathbb{N} \to \mathbb{N}$ can be applied to a number to get another number; a term of type $\mathbb{N}$ cannot be applied to anything.

When you write `def double n = n * 2`, you're not just naming a computation — you're giving a term a handle so you can refer to it later, and that handle inherits the term's type:

$$
3 : \mathbb{N} \qquad \text{double} : \mathbb{N} \to \mathbb{N}
$$

Later on, you'll see this same colon notation used for something surprising: proofs. For now, just get comfortable reading $\text{term} : \text{type}$.

**Practice:** For each of the following, write down what type you think the term has, using the $\text{term} : \text{type}$ notation: (a) `true`, (b) `fun x -> x > 0` (a function testing positivity), (c) the number $-5$.

### type (0.0s)

## Type

You already know that in Lean, every object has a type — `#check 3` tells you it's `ℕ`, and `#check True` tells you it's `Prop`. But what *is* a type, structurally? A type is a classification: a rule that decides which objects count as members of it, and which don't. Writing $n : \mathbb{N}$ means "$n$ is a term of type $\mathbb{N}$" — a specific instance, built by specific rules, belonging to that category and no other.

Here's the structural piece: types themselves have types. $\mathbb{N}$, $\mathbb{Z}$, $\text{Bool}$, and even $\text{Prop}$ are all terms of type $\text{Type}$. So there's a hierarchy — objects live in types, types live in `Type`, and `Type` lives in an even bigger type called `Type 1`, and so on upward. This stack of "types of types" is called the **type universe hierarchy**, written $\text{Type}_0, \text{Type}_1, \text{Type}_2, \dots$ It exists so Lean never has to answer the paradoxical question "what is the type of everything, including itself?" — each level only classifies the level below it.

The simple rule: every term has exactly one type, and that type determines what you're allowed to do with the term. You can add two `ℕ`s but not a `ℕ` and a `Prop` — their types don't match, so the operation isn't even well-formed. This is why `#check` is your first move when confused: it tells you which universe of meaning you're working in.

**Practice problem:** Run `#check (5 : ℤ)` and `#check (5 : ℤ) = 5`. What type does each expression have, and why are they different kinds of objects?

### proposition (0.0s)

## Proposition

You already know a proposition as a statement that's true or false: "7 is prime," "this triangle has a right angle." In type theory, we upgrade that idea. A proposition $P$ becomes a *type* — a collection of objects — and those objects are the *proofs* of $P$. To say $P$ is true is to produce a specific object $p$ that counts as evidence for it. We write this as $p : P$, meaning "$p$ is a proof of $P$."

This is the shift: instead of asking "is $P$ true or false?", you ask "what would a proof of $P$ look like, and can I build one?" A proof isn't a yes/no label sitting outside the statement — it's data that lives *inside* it. If $P$ is "there exists an $n$ such that $n^2 = 4$," a proof isn't a checkmark; it's literally the pair $(2, \text{evidence that } 2^2=4)$. Two different proofs can both satisfy $p : P$ for the same $P$, the way two different arguments can both prove the same theorem.

The rule that makes this useful: finding some $p$ with $p : P$ *is* proving $P$, and if no such $p$ can be found, $P$ is false (or at least unproven) — there's nothing else to check. This is why proof assistants like Lean or Coq can verify proofs mechanically: checking "does $p : P$ hold?" is the same kind of check a compiler does when it confirms a value has the right type.

**Practice:** Let $P$ be the proposition "$3 + 4 = 7$." Write down, informally, what an object $p$ with $p : P$ would need to contain for this to count as evidence. Then state one proposition $Q$ for which you cannot yet find such a $p$ — what would it need to look like?

### function_types (0.0s)

## Function Types

Every function you write is really two things at once: a *type*, which describes the shape of the transformation, and a *term*, which describes the actual recipe. The type is the promise; the term is the delivery.

We write a function's type as $A \to B$, read "a function from $A$ to $B$." It says: give me any value of type $A$, and I will produce a value of type $B$. Nothing more is promised — not how, just that it happens.

The term is the recipe itself, written with a lambda:

$$\text{fun } x \Rightarrow e$$

Here $x$ is the input variable, and $e$ is an expression built from $x$ that produces the output. For example, $\text{fun } x \Rightarrow x + 1$ has type $\mathbb{Z} \to \mathbb{Z}$: it promises an integer in, an integer out, and the recipe is "add one."

The core rule connecting type and term is **application**: if $f$ has type $A \to B$, and $a$ has type $A$, then $f\,a$ (applying $f$ to $a$) has type $B$. This is the only way anything actually *happens* in a typed language — you don't just describe transformations, you apply them. Type-checking application is simple: the input's type must match the function's domain, or the program is rejected before it ever runs.

Notice the asymmetry: a function's type is fixed and finite to state, but the term can be arbitrarily complex — nested calls, recursion, other functions passed in. That's the payoff of separating type from term: the type gives you a guarantee you can check instantly, while the term does the real work.

**Practice:** Write the type and a term for a function that takes a real number and returns its square. Then apply it to $3.0$ — what type does the result have, and what is its value?

### curry_howard (0.0s)

## Curry Howard

You've already met the idea that a proof and a type-checked program are somehow the same thing. Now let's see the actual correspondence — not a metaphor, an exact dictionary.

Every proposition $P$ corresponds to a type, also written $P$. Every proof of $P$ corresponds to a term $t$ of that type, written $t : P$. "Checking a proof" and "type-checking a program" become literally the same computation, run by the same kernel.

The one new idea to hold onto here is what implication becomes. $P \Rightarrow Q$ turns into a function type $P \to Q$: a proof that "$P$ implies $Q$" is nothing but a function that eats any proof of $P$ and hands back a proof of $Q$. That's it — no separate machinery for "logical implication" versus "computable function." They're the same object, read two ways.

$$
\underbrace{P \Rightarrow Q}_{\text{proposition}} \quad \Longleftrightarrow \quad \underbrace{P \to Q}_{\text{type}}
$$

The rule: to prove $P \Rightarrow Q$, you build a term of type $P \to Q$. If it type-checks, the proof is valid. (The same dictionary extends to "and," "or," and quantifiers too — you'll meet those correspondences one at a time.)

**Practice:** Suppose you have a term $f : P \to Q$ (a proof that $P$ implies $Q$) and a term $p : P$ (a proof of $P$). Write, in plain pseudocode, the expression that combines $f$ and $p$ to produce a term of type $Q$. What familiar logical rule does this computation correspond to?

### proof (0.0s)

## Proof

You already have the intuition: a proof is a chain of logical steps that forces a conclusion to be true, no matter what. Now let's see what a proof actually *is* inside the type-theoretic world of the SPL/Lean approach — because here, "proof" isn't just an argument in prose. It's a **term**.

Recall that a proposition $P$ is itself a type — a "recipe" for what would count as evidence that $P$ holds. A proof of $P$ is any term $p$ that satisfies $p : P$. That's the whole idea: proving $P$ means *constructing* a term whose type is $P$. The kernel doesn't read your proof and judge whether it's "convincing" — it just checks, mechanically, that $p$'s type really is $P$, the same way it checks that $3$ has type $\mathbb{N}$.

This is why proofs are terms and not paragraphs: they're built the same way any value in the language is built. For example, a proof of $P \Rightarrow Q$ is a function that takes any proof of $P$ and hands back a proof of $Q$:

$$
f : P \to Q
$$

Feed $f$ a term of type $P$, and out comes a term of type $Q$ — applying a function to an argument, nothing more exotic than that.

**Rule of thumb:** to prove something, figure out what *type* it corresponds to, then build a term of that type.

**Practice:** Suppose $\text{Even}(n)$ is a type whose terms are proofs that $n$ is even. If $h : \text{Even}(n)$ is a proof, and you know a function $\text{double\_ok} : \text{Even}(n) \to \text{Even}(2n)$, write down the term that proves $\text{Even}(2n)$.

### theorem_statements (0.0s)

## Theorem Statements

You already know that in Curry-Howard, a proposition is a type and a proof is a program. A **theorem statement** is where that idea takes on real weight: it's the exact sentence "if you give me this, I'll produce that," written as a type. The theorem's *name* labels the claim, the *statement* is its type signature, and the *proof* is a program inhabiting that type — a term you can actually run.

Consider a familiar claim: "every natural number equals itself." As a theorem statement:

$$\texttt{refl\_nat} : \forall\, n : \mathbb{N},\ n = n$$

Read this like a function type: for any $n$ you hand it, `refl_nat` returns a proof of $n = n$. The one new piece here is the $\forall$: it isn't decoration, it's a *dependent* function type, because the output type ($n = n$) depends on which $n$ you passed in. This is the real structural jump from plain function types — instead of `int -> int`, you get types that change shape based on their input.

That's the whole trick. Once you can write $\forall\, x : T,\ P(x)$, you can state any "for all inputs, this property holds" claim — the statement alone already tells you *what shape* any valid proof must have: a term of exactly that dependent type, nothing looser. No proof yet — that comes next.

**Practice:** Write the theorem statement (not the proof) claiming "every natural number $n$ satisfies $n + 0 = n$." Give it a name and a $\forall$ type signature in the style above.

### tactic_mode (0.0s)

## Tactic Mode

Once you can state a theorem, how do you actually build its proof? In *tactic mode*, you don't write a finished proof all at once — you work interactively. You start with a **goal**: the statement you still need to establish. You apply a **tactic**, a command that transforms the goal into a new, hopefully simpler one. You keep applying tactics until no goal remains — at that point, the proof is complete.

Think of the goal state as a to-do list that shrinks (or occasionally grows) with each step. If your goal is $\forall n \in \mathbb{N},\ n + 0 = n$, a tactic like `intro n` turns it into $n + 0 = n$ for a fixed, arbitrary $n$. A tactic like `induction n` splits that into two new goals: a base case, $0 + 0 = 0$, and an inductive case, assuming $k + 0 = k$, show $(k+1) + 0 = k+1$. Each tactic is a small, checkable move — but stacking them produces something rigorous.

The proof itself is the transcript: the ordered sequence of tactics applied. Nothing is "hidden" — every step is recorded, and the proof checker can replay it to confirm the goal state really does close. This is different from a textbook proof, which shows only the final polished argument. Tactic mode shows the *process*, which is exactly why it composes so naturally with theorem statements (what you're proving) and proofs (the record of how).

**Practice:** Suppose your goal is $\forall n \in \mathbb{N},\ n + 1 = 1 + n$, and you're given tactics `intro`, `induction`, and `rewrite`. Write, in order, which tactics you'd apply and what goal remains after each one, until the goal list is empty.

### core_tactics (0.0s)

## Core Tactics

You already know the feeling: staring at a goal in Coq or Lean and thinking, "I know what's true here, I just need to say it." That's exactly what tactics let you do — instead of writing out a full proof term (a rigid, explicit construction), you issue commands that build the proof *for* you, step by step, guided by logic.

Today, focus on just one move: **`apply`**. It's the workhorse for implications. Suppose you have a hypothesis $h : P \to Q$ and your goal is $Q$. Since $h$ already tells you that $P$ gives you $Q$, all that's left to prove is $P$ itself. Running `apply h` does exactly that: it replaces your goal $Q$ with the smaller goal $P$.

Here's the useful trick: `apply` doesn't stop there. If the thing you apply *already matches the goal exactly* — no leftover hypothesis needed — it closes the goal completely instead of leaving something new to prove. So the same tactic that shrinks a goal can also finish it, depending on what you feed it.

Notice the pattern: `apply` reads the *shape* of a hypothesis — is it an arrow pointing at your goal? — and uses that arrow to work backward from what you want to what you'd need. Later, you'll meet tactics for other shapes: goals built from "and," "or," "exists," or "for all." For now, one tool, used twice, can already carry you further than you'd expect.

**Practice problem:** Given `h1 : A -> B` and `h2 : A`, with goal `B`, write the two-step proof using `apply` alone. (Hint: the first `apply` shrinks the goal; think about what the second `apply` matches exactly.)

### equality_rfl (0.0s)

## Equality Rfl

You already know equality intuitively: $2 + 2 = 4$ feels obviously true. But in a formal proof system, "true" isn't a feeling — it's something you have to *construct*. For any two terms $a$ and $b$ of the same type, $a = b$ is a proposition, and proving it means building a witness that convinces the checker.

The one new tool this section introduces is `rfl`, the proof you use when $a$ and $b$ are actually the *same term after computation*. Here's the key structural idea: `rfl` doesn't compare $a$ and $b$ symbolically — it works because the type checker unfolds both sides step by step until they land on an identical result. When you write:

$$2 + 2 = 4$$

the checker expands the definition of addition: $2 + 2 \rightsquigarrow 2 + (1+1) \rightsquigarrow \dots \rightsquigarrow 4$. Once both sides collapse to the identical term $4$, `rfl` closes the proof — there's nothing left to argue.

This gives you a simple rule: **`rfl` proves $a = b$ exactly when $a$ and $b$ unfold to the same final value.** If they don't — even if they're "true" for some other reason — `rfl` alone will fail, and you'll need a more powerful proof strategy (rewriting, induction, etc.) that you'll meet later.

**Practice problem:** Using the same reasoning, explain in one or two sentences why `rfl` can prove $3 \times 3 = 9$, but would *not* work directly to prove $x + 0 = x$ for an arbitrary variable $x$ (think about whether both sides unfold to the same value when $x$ isn't a specific number).

### inductive_types (0.0s)

## Inductive Types

You already know that `Nat` — the type of natural numbers — can be built by starting at `zero` and repeatedly applying `succ` (successor). What you might not realize yet is that this *is* the entire definition. There's no hidden machinery. In Lean, it looks like this:

$$
\texttt{inductive Nat} \mid \texttt{zero} \mid \texttt{succ (n : Nat)}
$$

That's it — two lines. `zero` is a `Nat`, and if `n` is a `Nat`, so is `succ n`. Every natural number — 0, 1, 2, 3, ... — is really just nested applications: $1 = \texttt{succ zero}$, $2 = \texttt{succ (succ zero)}$, and so on.

This pattern — listing the *constructors* that build a type, and nothing else — is called an **inductive type**. A constructor is a rule that says "here's a new way to make a value of this type." `Bool` has two constructors with no arguments: `true` and `false`. `List` has two constructors: `nil` (the empty list) and `cons (head) (tail)`, which builds a longer list from an element and a shorter list. In every case, the type is defined *only* by these rules — nothing is builtin.

The payoff is that any function on an inductive type can be defined by **pattern matching** on its constructors — covering the base case(s) and the recursive case(s) — and any proof about it can proceed by **induction**, mirroring the same structure. This is why the type's definition and its proof technique share a name.

**Practice:** Using the definitions above, write out what `succ (succ (succ zero))` represents as an ordinary number, and then define, in words, a constructor-based rule for building the list `[1, 2, 3]` using only `nil` and `cons`.

### rewriting_simp (0.0s)

## Rewriting Simp

You already know `rfl` closes goals that are *definitionally* equal — the two sides compute to the same thing. But most goals aren't that lucky. Suppose you have a hypothesis $h : a = b$, and your goal mentions $a$ somewhere inside a bigger expression. You need to *replace* $a$ with $b$ inside the goal. That's what `rw [h]` does: it rewrites every occurrence of $a$ in the goal to $b$, using $h$ as the substitution rule, then checks if the result closes by `rfl`.

Formally, `rw` uses the substitution property of equality: if $a = b$, then any statement $P(a)$ becomes $P(b)$. You can chain several rewrites at once: `rw [h1, h2, h3]` applies them left to right, each one transforming the goal before the next fires.

`simp` is `rw`'s bigger sibling. Instead of one equality, it draws on a large library of rewrite rules — lemmas tagged `@[simp]` by the community because they simplify expressions in an obviously "smaller is better" direction, like $n + 0 = n$ or $x * 1 = x$. `simp` applies these rules repeatedly, in whatever order works, until nothing more simplifies. You can supply extra lemmas too: `simp [h1, h2]` adds your own facts to the simp set for that call.

**Rule of thumb:** use `rw` when you know exactly which equality to apply and where. Use `simp` when you expect the goal to reduce to something trivial after a cascade of "obvious" simplifications, but you don't want to name every step.

**Practice:** Given `h : x = 5` and goal `x + 3 = 8`, what single tactic call closes the goal? Try writing it, then check: does `rw [h]` leave you needing `rfl` too, or does it finish alone?

### typeclasses_structures (0.0s)

## Typeclasses Structures

You've seen inductive types (data with cases) and function types (maps between types). Now combine them: a **structure** bundles data with the rules it must obey.

Take a group. A group isn't just a set — it's a set $G$ equipped with an operation $\cdot$, an identity $e$, and inverses, satisfying:

$$(a \cdot b) \cdot c = a \cdot (b \cdot c), \quad e \cdot a = a \cdot e = a, \quad a \cdot a^{-1} = e$$

In a proof assistant, we package this as a structure:

$$\texttt{Group} := \{\, G : \texttt{Type},\ \cdot : G \to G \to G,\ e : G,\ \text{inv} : G \to G,\ \text{proofs of the axioms} \,\}$$

Notice the later fields depend on the earlier ones: the axioms only make sense once $G$ and $\cdot$ are already fixed. But it's still built from pieces you already know — a type, some functions, and proof terms, gathered into one bundle.

Here's the payoff. Once $(\mathbb{Z}, +)$, permutations, and matrices are each packaged as a $\texttt{Group}$, a theorem like "every group has a unique identity" can be stated once and reused for all of them, because the system can search for the matching $\texttt{Group}$ bundle and plug it in automatically. When you write $a \cdot b$ for elements of some type $G$, it finds the right $\texttt{Group}\ G$ and inserts it silently — you never re-specify which operation or identity you mean, so the theorem stays clean: $\forall\, a\, b : G,\ a \cdot b = b \cdot a$, with no extra bookkeeping arguments.

**Rule of thumb**: a structure is a type-level "bundle of data + proofs," and the automatic search that finds the right bundle for a given type is what makes structures reusable across many examples at once.

**Practice**: Write out the four fields a $\texttt{Monoid}$ structure needs (a group without inverses). Which group axiom did you drop, and why does dropping it still leave something useful?

### mathlib (0.0s)

## Mathlib

You already know that mathlib defines things like groups and rings, and that `simp` can rewrite an expression using known equalities. Mathlib is the actual library where this happens at scale — over a million lines of Lean code, formalizing calculus, algebra, topology, number theory, and more, all built from the same handful of foundational definitions.

The library's real challenge isn't writing proofs — it's finding what's already there. Mathlib follows a strict naming convention so a lemma's name encodes its statement. A lemma proving $a + b = b + a$ is named `add_comm`. One proving $(a+b)+c = a+(b+c)$ is `add_assoc`. A lemma that turns a hypothesis $h : a < b$ into $a \le b$ is `le_of_lt`. Once you know the pattern — operation names (`add`, `mul`, `le`), joined by connector words (`comm`, `assoc`, `of`, `iff`) — you can often *guess* a lemma's name before searching for it, the way a chemist guesses a compound's formula from its name.

$$\texttt{add\_comm} : \forall\, a\, b, \quad a + b = b + a$$

This matters because a proof in mathlib is rarely built from scratch. It's assembled by finding the right existing lemmas and chaining them — often automatically, via `simp` or `rw`. Learning mathlib means learning to read its naming grammar well enough to search it, using tools like `exact?` or the online Loogle/Moogle search engines that match a goal's *shape* to a lemma's statement.

**Practice:** Given the naming convention above, guess the name of the mathlib lemma stating $a \cdot b = b \cdot a$ for a commutative operation, without looking it up.

### proof_search (0.0s)

## Proof Search

You've been proving things by writing every step yourself — apply this lemma, then that one, then rewrite with a third. But mathlib already contains over 100,000 theorems. Odds are, the exact fact you need — or something close enough to finish the job — is already sitting in the library. The hard part isn't proving it from scratch; it's *finding* it.

That's what `exact?` is for. It asks a precise question: "does some single known lemma close my current goal exactly, possibly after unification?" Under the hood, it takes your goal as a query, searches mathlib's lemma database for candidates whose conclusion matches your goal's shape, tries each one, and — if one fits — hands you back the exact term to write in its place. You run it, and either get a finished proof step or a report that nothing matched, in which case you're back to proving it yourself (or breaking the goal into pieces and searching again on each).

Lean's ecosystem has other search tools built on the same idea — some search by natural-language description, others by the type signature of the theorem you imagine — but the pattern to internalize now is simpler: before proving a fact, search for it. A library the size of mathlib turns "prove this" into "look this up" for a surprising fraction of goals. Knowing when to reach for `exact?` instead of writing the proof by hand is half the skill of working efficiently in Lean.

**Practice:** Suppose your goal is `n + 0 = n` for a natural number `n`. Before writing the proof yourself, run `exact?` on it. What do you expect it to find, and why is this exactly the kind of goal `exact?` is built to close?

### automation_tactics (0.0s)

## Automation Tactics

You've been closing goals one step at a time — rewrite here, apply a lemma there. But some goals belong to entire *families* that share a common shape, and for those families, Lean has decision procedures: tactics that don't just take one step, they solve the whole family at once.

Think of it like this: `ring` proves any true equation built purely from $+, -, \times$ in a commutative ring — it doesn't search for a proof, it normalizes both sides into a canonical polynomial form and checks they match. `linarith` handles linear arithmetic over ordered fields: goals like $2x + 3y \le 5x - y + 7$ built from linear combinations of hypotheses. `positivity` proves goals of the form $0 < e$ or $0 \le e$ by recursively analyzing the structure of $e$. `omega` is the specialist for linear arithmetic over integers and naturals, including divisibility and modular facts that `linarith` can't touch. And `aesop` is different in kind — a configurable proof-search engine that tries chains of rules (including simp lemmas) until something closes the goal, useful when no single decision procedure applies.

The pattern to internalize: each tactic *owns a domain*. Picking the right one is a classification problem — "is this equation purely algebraic, purely linear, purely about positivity, or does it need genuine search?" Guessing wrong just fails fast, so try them cheaply.

**Practice:** Given `x y : ℤ`, `h : x = y + 1`, prove `x^2 - y^2 = 2*y + 1`. Which single tactic closes it — and why does it belong to that domain rather than `linarith`'s?

### formalization_gap (0.0s)

## Formalization Gap

You've seen that a proof assistant checks a proof line by line, and that theorems live in vast libraries like mathlib. But there's a step the kernel never touches: turning a claim written in English into a formal statement in the first place. That translation is the *formalization gap*, and it's the one link in the whole chain that no machine verifies for you.

Here's the structure of the problem. Suppose you want to formalize "every prime greater than 2 is odd." You might write:

$$\forall p \in \mathbb{P},\ p > 2 \implies \text{Odd}(p)$$

That's correct. But small slips turn a true theorem into something else entirely — provable, yet not what you meant. Flip a quantifier: $\exists p \in \mathbb{P},\ p > 2 \implies \text{Odd}(p)$ says only *some* prime works, trivially true and useless. Or write a hypothesis that nothing ever satisfies — like assuming $x^2 < 0$ for a real number $x$ — and the implication is *vacuously* true no matter what conclusion follows, because there are no real cases to check.

The proof assistant will happily accept all of these. It checks that the logic inside the box is valid; it has no idea what the box was supposed to say. The rule to carry forward: **a checked proof only guarantees the statement is true — never that the statement is the right one.** Reading the formal statement back into plain English, sentence by sentence, is a human job every time.

**Practice:** Here's a formalized claim: $\forall n \in \mathbb{N},\ n < 0 \implies n \text{ is prime}$. It will typecheck and prove trivially. Explain in one or two sentences why it's vacuous, and rewrite it so it actually asserts something about natural numbers.

### sorry_first_workflow (0.0s)

## Sorry First Workflow

You already know that a big proof rarely appears whole — you sketch a plan first, then fill it in piece by piece. Formal proof assistants like Lean or Coq give this instinct a name: **sorry**. Instead of pretending you've proven something you haven't, you write `sorry` as an honest placeholder wherever a step is still missing, and the system happily accepts your whole outline as a "proof" — with a loud warning attached to every `sorry`.

This flips the usual order of work. Normally you'd write one lemma, prove it fully, then move to the next. The sorry-first workflow says: state *every* theorem, lemma, and helper fact you'll need, chain them together with `sorry` in place of each unfinished proof, and check that the whole architecture actually builds and type-checks. Only after the skeleton compiles do you go back and replace each `sorry` with real reasoning.

The payoff is structural. Since the system tracks every `sorry`, your warning list becomes an automatically generated to-do list — nothing gets forgotten, and you can measure progress as "warnings remaining." It also catches design errors early: if your final theorem's statement doesn't type-check against your lemmas, you find out before wasting hours proving lemmas you didn't actually need. Formally, if $T$ is your target theorem and $L_1, \dots, L_n$ are supporting lemmas, sorry-first checks the *implication structure* $L_1, \dots, L_n \vdash T$ first, deferring the individual proofs $\vdash L_i$.

**Practice:** Suppose you want to prove "every rectangle's diagonal is longer than either side." Write out, as `sorry`-stubbed statements only (no proofs yet), the two lemmas you'd need before proving the theorem itself.

## Ai Assisted Proving

You've seen the formalization gap — the distance between "I have an idea" and "Lean accepts a proof." You've seen the automation tactics that close small gaps automatically. Now put them together: an LLM can draft entire proofs, and Lean's kernel checks every step. This partnership is the payoff of the whole workflow.

Here's the loop. You ask an AI system to propose a theorem statement and a candidate proof, written in Lean's language. The AI is good at pattern-matching: it has seen millions of proofs and can guess plausible tactic sequences. But the AI can also be wrong — it might state a false theorem, or write a proof with a gap. That's fine, because the AI never gets the final word. Lean's kernel does. If a step doesn't follow from what came before, Lean throws an error, and that error message becomes the next prompt: "fix this step." The AI revises, resubmits, and the cycle repeats — propose, check, repair — until the kernel accepts the complete proof or you decide the statement itself is wrong.

This matters because it fixes a real weakness of AI: language models can sound confident while being incorrect. Lean supplies the one thing they lack — an incorruptible check. Mathematician Terence Tao has argued this is how AI should enter mathematics: not as an oracle to be trusted, but as a fast idea-generator paired with a verifier that cannot be talked into accepting a false step.

$$\text{AI proposes} \;\rightarrow\; \text{Lean checks} \;\rightarrow\; \text{error} \;\rightarrow\; \text{AI repairs} \;\rightarrow\; \cdots \;\rightarrow\; \text{QED}$$

## Spl Machine Proved

You've already met the ladder of trust SPL uses: a statement can be *computable* (plug in numbers, get an answer) or *symbolically verified* (a system like Sage confirms an algebraic relationship holds in general). `spl_machine_proved` marks the top rung — a much stronger claim than either of those.

Here's the one new idea for this section: a **machine-checked proof**. Instead of a computer running numbers or manipulating symbols, a proof assistant called Lean checks a full chain of logical reasoning, one step at a time, and refuses to accept any step that doesn't follow correctly from the last. Formally, if a statement $P$ has a Lean proof $p : P$, that means Lean has verified, step by step, that $P$ is true — not "true for the cases we tried," but true, full stop. No gap in the argument can hide, because Lean simply won't accept it.

This is why `machine_proved` means something different from "an expert checked it" or "it worked on every example we tried." It means a machine verified the *entire logical structure* of the argument, with zero trust placed in the human who wrote it.

**Rule to remember:** computable $\subset$ symbolically verified $\subset$ machine-proved — each rung is a stricter, smaller category than the one before it.
