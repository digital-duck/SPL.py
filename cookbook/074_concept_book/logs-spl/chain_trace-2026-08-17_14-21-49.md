## Computer Network

A **computer network** is a collection of devices — computers, phones, servers, routers — connected by communication links so they can share data and resources. The defining idea is **packet switching**: instead of reserving a dedicated wire between sender and receiver (the way old telephone calls worked), data is broken into small, labeled chunks called packets. Each packet carries a destination address and travels independently through shared links, where routers forward it hop-by-hop until it arrives. The packets are reassembled in order at the destination. This design lets thousands of conversations share the same physical infrastructure simultaneously, which is why the internet scales to billions of devices.

Every device on a network is assigned an **IP address** — a numeric label such as `192.168.1.5` — that routers use to make forwarding decisions. Routers consult a routing table at each hop, choosing the next best path toward the destination. This is the primitive that makes global connectivity possible: you don't need a direct wire to every machine you talk to, only a path through intermediaries that each know a little about the topology.

**Worked example — sending a message across a LAN.** Two laptops on the same Wi-Fi network share an access point. Laptop A wants to send a file to Laptop B at `192.168.1.7`. A breaks the file into packets, each stamped with B's IP address. The access point reads each destination address and forwards packets directly to B. B's operating system buffers arriving packets and reassembles the original file once all have arrived. No packet reserves the channel; other devices on the same network transmit their own packets between A's.

**Problem-solving application.** Laptop A cannot reach Laptop B on the same network. Start with the simplest possible check and move up:

```
1. Are both machines connected to the same access point?
2. Does `ping 192.168.1.7` return a reply?
3. Do both machines have IP addresses in the same subnet
   (e.g., both 192.168.1.x with mask 255.255.255.0)?
4. Is a firewall on B blocking incoming traffic?
```

Working through these checks in order prevents the common mistake of blaming software when the problem is a misconfigured address — packet switching only works when every device knows where it lives on the network.

## Partial View

A **partial view** is a named query stored in a database that exposes only a filtered or column-restricted slice of an underlying table. Instead of giving users or applications access to a full table, you define a view that shows exactly the rows and columns relevant to a particular purpose. The full data still lives in one place; the view is just a lens — a saved `SELECT` statement that behaves like a table.

Partial views serve two goals simultaneously: **access control** (hide sensitive columns from certain users) and **cognitive clarity** (show analysts only the data they need, reducing mistakes from irrelevant noise).

### Worked Example

Suppose a hospital database has an `encounters` table with columns `patient_id`, `ssn`, `diagnosis_code`, `visit_date`, and `billed_amount`. A billing analyst needs visit dates and charges but must never see diagnosis codes or SSNs. You create a partial view:

```sql
CREATE VIEW billing_encounters AS
SELECT patient_id, visit_date, billed_amount
FROM encounters
WHERE visit_date >= '2024-01-01';
```

The analyst queries `billing_encounters` as if it were a real table. The `ssn` and `diagnosis_code` columns are invisible to them — not hidden by a permission rule they could work around, but simply absent from the view definition. The `WHERE` clause further restricts rows, so legacy records from before 2024 do not appear at all.

### Problem-Solving Application

Consider this scenario: you have a `users` table with columns `user_id`, `email`, `password_hash`, `subscription_tier`, and `last_login`. A customer-success dashboard needs to show subscription tier and last login grouped by week, but engineers building the dashboard should never touch raw credentials.

**Step 1 — Identify what to expose:** `user_id`, `subscription_tier`, `last_login`. Exclude `email` and `password_hash`.

**Step 2 — Add any row filter:** perhaps only active accounts (`last_login > NOW() - INTERVAL 90 DAYS`).

**Step 3 — Create the view and grant access:**

```sql
CREATE VIEW active_user_summary AS
SELECT user_id, subscription_tier, last_login
FROM users
WHERE last_login > NOW() - INTERVAL '90 days';

GRANT SELECT ON active_user_summary TO dashboard_role;
```

**Step 4 — Query through the view:**

```sql
SELECT subscription_tier,
       DATE_TRUNC('week', last_login) AS week,
       COUNT(*) AS active_users
FROM active_user_summary
GROUP BY 1, 2
ORDER BY 2 DESC;
```

The dashboard role cannot `SELECT * FROM users`; it can only see the view. Partial views are most valuable when you need repeatable, auditable data boundaries — security policies encoded directly in the schema rather than scattered through application logic.

## Overlay Network

An **overlay network** is a virtual network built on top of an existing physical network infrastructure. Rather than requiring new cables or hardware, an overlay network uses software to create logical connections — called *tunnels* or *virtual links* — between nodes, treating the underlying physical network simply as a delivery mechanism. The overlay defines its own addressing, routing, and topology independent of what sits beneath it.

The internet itself gave rise to overlay networks as a practical tool: when engineers needed capabilities the base network lacked — privacy, fault tolerance, content distribution — they layered new logic on top rather than redesigning the infrastructure from scratch.

**Worked example: a VPN as an overlay**

A corporate VPN is a classic overlay. Suppose an employee works from home and needs to access an internal file server at `192.168.1.50`, an address that only exists inside the company's private network. The employee's laptop connects to a VPN server over the public internet. That connection is a *tunnel*: packets destined for `192.168.1.50` are wrapped inside ordinary internet packets (a process called *encapsulation*), routed across the public internet to the VPN server, unwrapped, and forwarded to the file server. From the employee's perspective, they appear to be on the local network. From the public internet's perspective, they are simply exchanging encrypted packets with a server — the private addressing and topology are invisible.

```
[Laptop] --encrypted tunnel--> [VPN Server] --> [File Server 192.168.1.50]
          (public internet)        (private LAN)
```

**Problem-solving application**

Overlay networks are the right tool when you need a capability the physical network cannot provide directly. Consider three scenarios:

1. **Privacy**: A journalist in a censored region uses Tor, an overlay that routes traffic through multiple volunteer nodes, obscuring the origin of requests.
2. **Scalability**: A content delivery network (CDN) overlays thousands of edge servers globally; when you stream a video, the CDN routes your request to the nearest cache node, not the origin server.
3. **Peer-to-peer resilience**: BitTorrent overlays a distributed routing table (DHT) on the internet so that files can be located without any central directory server.

When designing or debugging a system that uses an overlay, the key questions are: *Where does encapsulation and decapsulation happen? What is the overlay's routing logic? And what latency or bandwidth overhead does the extra wrapping introduce?* Measuring those costs — against the capability gained — is how engineers decide whether an overlay is the right architecture for a given problem.

## Structured Overlay Network

A **structured overlay network** is a peer-to-peer (P2P) system in which every participating node is assigned a position in a mathematically defined topology, and the routing rules for finding any piece of data are deterministic rather than probabilistic. The word *overlay* means the logical network sits on top of the physical internet — nodes that are logically adjacent may be geographically distant. The word *structured* means the placement of data and the paths between nodes follow an explicit algorithm, not random gossip.

The dominant design is the **Distributed Hash Table (DHT)**. In a DHT, each node and each data item is assigned an identifier by hashing: a node's ID might be `SHA-1(IP:port)` and a file's key might be `SHA-1(filename)`. A simple rule — *the node whose ID is numerically closest to a key is responsible for storing it* — turns an uncoordinated collection of machines into a coherent lookup service.

**Worked example — Chord DHT.** Imagine 8 nodes arranged in a circle numbered 0–7 (a "ring"). Node IDs and file keys land on this ring by hashing modulo 8. If file key = 5 and nodes 3, 6, and 7 are live, then node 6 is responsible because it is the first node at or after position 5 going clockwise. Each node maintains a small *finger table* — pointers that jump ahead by powers of 2 — so any lookup reaches the correct node in $O(\log n)$ hops, where $n$ is the total number of nodes. With 1 million nodes, that is only about 20 network hops to locate any file.

**Problem-solving application.** Suppose you are designing a decentralized content-delivery system and need to answer: *what happens when a node fails?* In a structured overlay, each node also tracks a *successor list* — the next $k$ nodes clockwise. When node 6 disappears, node 3 detects the gap during a periodic heartbeat, promotes node 7 as the new successor, and node 7 inherits responsibility for key 5. Because the structure is deterministic, recovery is algorithmic: no central coordinator is needed, and the system self-heals in $O(\log n)$ messages.

This combination — $O(\log n)$ lookup, $O(\log n)$ routing table size, and systematic fault recovery — makes structured overlay networks the backbone of systems like BitTorrent's Mainline DHT, the InterPlanetary File System (IPFS), and enterprise key-value stores that must scale to millions of nodes without a single point of failure.

## Successor

In mathematics, the **successor** of a natural number $n$ is simply $n + 1$ — the next number in the counting sequence. Written $S(n)$ or $n'$, the successor function maps every natural number to the one immediately after it: $S(0) = 1$, $S(1) = 2$, $S(2) = 3$, and so on. This seems almost too simple to name, yet it is the foundational operation from which all of arithmetic is built.

The importance of the successor function comes into full view through the **Peano axioms**, a minimal set of rules that define the natural numbers precisely. Two of the most consequential axioms are: (1) $0$ is a natural number, and (2) if $n$ is a natural number, then $S(n)$ is a natural number. Together these two rules generate the entire infinite sequence $0, 1, 2, 3, \ldots$ without needing to assume anything else. Addition itself is defined recursively using the successor: $n + 0 = n$ and $n + S(m) = S(n + m)$. Multiplication follows from repeated addition, and from there all of elementary arithmetic emerges.

**Worked example.** Verify that $2 + 3 = 5$ using only the successor definition of addition.

$$2 + 3 = 2 + S(2) = S(2 + 2) = S(2 + S(1)) = S(S(2 + 1)) = S(S(2 + S(0))) = S(S(S(2 + 0))) = S(S(S(2))) = S(S(3)) = S(4) = 5$$

Each step applies one of the two recursive rules. The result is $5$, exactly as expected.

**Problem-solving application.** The successor function appears directly in programming. In Python, a recursive function that computes the $n$-th Fibonacci number implicitly uses the successor structure: every recursive call reduces the problem by peeling off one successor step toward the base case. More concretely, implementing arithmetic in a proof assistant like Lean or Coq requires defining addition through `Nat.succ` — the software equivalent of $S(n)$. When you write `n + 1` in any language, you are invoking the successor function; understanding its recursive definition explains why overflow errors occur at fixed bit-width boundaries: the hardware has a largest representable $n$, so $S(n)$ wraps around or errors rather than producing a valid natural number.

### finger_table (18.4s)

## Finger Table

In a distributed hash table (DHT) built on the Chord protocol, every participating node is responsible for storing certain keys. The naive approach — each node knowing only its immediate neighbor — forces a lookup to hop through every node in the ring, which scales terribly as the network grows. A **finger table** solves this by giving each node a compact set of "shortcuts" that allow any key to be located in $O(\log N)$ hops, where $N$ is the number of nodes.

Each node in Chord occupies a position on an identifier ring of size $2^m$ (typically $m = 160$, using SHA-1 hashes). Node $n$'s finger table has $m$ entries. The $i$-th entry stores the identity of the first node that is at least as far along the ring as position

$$n + 2^{i-1} \pmod{2^m}, \quad i = 1, 2, \ldots, m.$$

The first entry is simply the immediate successor. Each subsequent entry jumps roughly twice as far around the ring, so the table covers the entire identifier space with exponentially increasing strides.

**Worked example.** Suppose $m = 4$, giving a ring of size $2^4 = 16$. Node $6$'s finger table entries point to the first live node at or after positions $7, 8, 10,$ and $14$. If the ring currently has nodes at $\{1, 3, 6, 10, 13\}$, then node $6$'s table is:

| $i$ | Start position | Successor stored |
|-----|---------------|-----------------|
| 1   | 7             | 10              |
| 2   | 8             | 10              |
| 3   | 10            | 10              |
| 4   | 14            | 1               |

**Problem-solving application.** Say node $6$ must locate the key hashed to position $12$. It checks its finger table for the largest entry whose start position does not exceed $12$ — that is entry 3, pointing to node $10$. It forwards the request to node $10$, which now checks *its* finger table. Node $10$'s table has an entry pointing to node $13$, which owns position $12$. The lookup reaches the correct node in two hops instead of potentially traversing all five nodes sequentially.

When a new node joins or an existing node leaves, only $O(\log N)$ finger table entries across the network require updating — preserving the protocol's efficiency without a global rebuild. This makes finger tables a foundational example of how a small, carefully structured local index can yield globally efficient behavior in a decentralized system.

## Chord

A **chord** is a set of three or more distinct pitches sounded simultaneously. In Western tonal music, chords are built by stacking intervals — most commonly thirds — above a starting note called the **root**. The quality of those intervals (major or minor) determines whether the chord sounds bright, dark, tense, or stable.

The simplest and most important chord type is the **triad**, built from three notes: a root, a third, and a fifth. A **major triad** stacks a major third (4 semitones) and then a minor third (3 semitones) above it. A **minor triad** reverses that order — minor third first (3 semitones), then major third (4 semitones). The interval from root to fifth is a perfect fifth (7 semitones) in both cases.

**Worked example — building a C major and C minor triad**

Start on C (MIDI pitch 60, or the frequency $f = 261.6$ Hz). Count upward in semitones:

| Note | Semitones above C | C major | C minor |
|------|------------------|---------|---------|
| Root | 0 | C | C |
| Third | 3 or 4 | E (4 — major) | E♭ (3 — minor) |
| Fifth | 7 | G | G |

Strum {C, E, G} and you hear major — open, resolved. Swap E for E♭ to get {C, E♭, G} and the chord turns inward, minor.

**Problem-solving application**

Suppose you are writing a melody harmonizer in Python. Given any MIDI root note `r`, you need to generate the major triad automatically:

```python
def major_triad(root: int) -> list[int]:
    return [root, root + 4, root + 7]

def minor_triad(root: int) -> list[int]:
    return [root, root + 3, root + 7]

# G major triad: root = 67 (G4)
print(major_triad(67))   # [67, 71, 74]  →  G, B, D
```

From here you can extend the pattern: a **dominant seventh** chord adds another minor third on top of a major triad (`root + 4 + 3 + 3 = root + 10`), giving the characteristic tension that resolves back to a tonic chord. Understanding chord construction as interval arithmetic makes it straightforward to generate any chord quality programmatically — major, minor, diminished, augmented, or extended — without memorizing each case separately.
