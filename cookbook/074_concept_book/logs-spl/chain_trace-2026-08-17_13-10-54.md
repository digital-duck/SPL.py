## Computer Network

A **computer network** is a collection of devices — computers, phones, servers, routers — connected by communication links so they can share data and resources. The defining idea is **packet switching**: instead of reserving a dedicated wire between sender and receiver (the way old telephone calls worked), data is broken into small, labeled chunks called packets. Each packet carries a destination address and travels independently through shared links, where routers forward it hop-by-hop until it arrives. The packets are reassembled in order at the destination. This design lets thousands of conversations share the same physical infrastructure simultaneously, which is why the internet scales to billions of devices.

Every device on a network is assigned an **IP address** — a numeric label such as `192.168.1.5` — that routers use to make forwarding decisions. Routers consult a routing table at each hop, choosing the next best path toward the destination. This is the primitive that makes global connectivity possible: you don't need a direct wire to every machine you talk to, only a path through intermediaries that each know a little about the topology.

**Worked example — sending a message across a LAN.** Two laptops on the same Wi-Fi network share an access point. Laptop A wants to send a file to Laptop B at `192.168.1.7`. A breaks the file into packets, each stamped with B's IP address. The access point reads each destination address and forwards packets directly to B. B's operating system buffers arriving packets and reassembles the original file once all have arrived. No packet reserves the channel; other devices on the same network transmit their own packets between A's.

**Problem-solving application.** Laptop A cannot reach Laptop B on the same network. Start with the simplest possible check and move up:

```
1. Are both machines connected to the same access point?
2. Does `ping 192.168.1.7` return a reply?
3. Do both machines have IP addresses in the same subnet
   (e.g., both 192.168.1.x with mask 255.255.255.0)?
4. Is a firewall on B blocking incoming traffic?
```

Working through these checks in order prevents the common mistake of blaming software when the problem is a misconfigured address — packet switching only works when every device knows where it lives on the network.

## Partial View

A **partial view** is a named query stored in a database that exposes only a filtered or column-restricted slice of an underlying table. Instead of giving users or applications access to a full table, you define a view that shows exactly the rows and columns relevant to a particular purpose. The full data still lives in one place; the view is just a lens — a saved `SELECT` statement that behaves like a table.

Partial views serve two goals simultaneously: **access control** (hide sensitive columns from certain users) and **cognitive clarity** (show analysts only the data they need, reducing mistakes from irrelevant noise).

### Worked Example

Suppose a hospital database has an `encounters` table with columns `patient_id`, `ssn`, `diagnosis_code`, `visit_date`, and `billed_amount`. A billing analyst needs visit dates and charges but must never see diagnosis codes or SSNs. You create a partial view:

```sql
CREATE VIEW billing_encounters AS
SELECT patient_id, visit_date, billed_amount
FROM encounters
WHERE visit_date >= '2024-01-01';
```

The analyst queries `billing_encounters` as if it were a real table. The `ssn` and `diagnosis_code` columns are invisible to them — not hidden by a permission rule they could work around, but simply absent from the view definition. The `WHERE` clause further restricts rows, so legacy records from before 2024 do not appear at all.

### Problem-Solving Application

Consider this scenario: you have a `users` table with columns `user_id`, `email`, `password_hash`, `subscription_tier`, and `last_login`. A customer-success dashboard needs to show subscription tier and last login grouped by week, but engineers building the dashboard should never touch raw credentials.

**Step 1 — Identify what to expose:** `user_id`, `subscription_tier`, `last_login`. Exclude `email` and `password_hash`.

**Step 2 — Add any row filter:** perhaps only active accounts (`last_login > NOW() - INTERVAL 90 DAYS`).

**Step 3 — Create the view and grant access:**

```sql
CREATE VIEW active_user_summary AS
SELECT user_id, subscription_tier, last_login
FROM users
WHERE last_login > NOW() - INTERVAL '90 days';

GRANT SELECT ON active_user_summary TO dashboard_role;
```

**Step 4 — Query through the view:**

```sql
SELECT subscription_tier,
       DATE_TRUNC('week', last_login) AS week,
       COUNT(*) AS active_users
FROM active_user_summary
GROUP BY 1, 2
ORDER BY 2 DESC;
```

The dashboard role cannot `SELECT * FROM users`; it can only see the view. Partial views are most valuable when you need repeatable, auditable data boundaries — security policies encoded directly in the schema rather than scattered through application logic.

## Overlay Network

An **overlay network** is a virtual network built on top of an existing physical network infrastructure. Rather than requiring new cables or hardware, an overlay network uses software to create logical connections — called *tunnels* or *virtual links* — between nodes, treating the underlying physical network simply as a delivery mechanism. The overlay defines its own addressing, routing, and topology independent of what sits beneath it.

The internet itself gave rise to overlay networks as a practical tool: when engineers needed capabilities the base network lacked — privacy, fault tolerance, content distribution — they layered new logic on top rather than redesigning the infrastructure from scratch.

**Worked example: a VPN as an overlay**

A corporate VPN is a classic overlay. Suppose an employee works from home and needs to access an internal file server at `192.168.1.50`, an address that only exists inside the company's private network. The employee's laptop connects to a VPN server over the public internet. That connection is a *tunnel*: packets destined for `192.168.1.50` are wrapped inside ordinary internet packets (a process called *encapsulation*), routed across the public internet to the VPN server, unwrapped, and forwarded to the file server. From the employee's perspective, they appear to be on the local network. From the public internet's perspective, they are simply exchanging encrypted packets with a server — the private addressing and topology are invisible.

```
[Laptop] --encrypted tunnel--> [VPN Server] --> [File Server 192.168.1.50]
          (public internet)        (private LAN)
```

**Problem-solving application**

Overlay networks are the right tool when you need a capability the physical network cannot provide directly. Consider three scenarios:

1. **Privacy**: A journalist in a censored region uses Tor, an overlay that routes traffic through multiple volunteer nodes, obscuring the origin of requests.
2. **Scalability**: A content delivery network (CDN) overlays thousands of edge servers globally; when you stream a video, the CDN routes your request to the nearest cache node, not the origin server.
3. **Peer-to-peer resilience**: BitTorrent overlays a distributed routing table (DHT) on the internet so that files can be located without any central directory server.

When designing or debugging a system that uses an overlay, the key questions are: *Where does encapsulation and decapsulation happen? What is the overlay's routing logic? And what latency or bandwidth overhead does the extra wrapping introduce?* Measuring those costs — against the capability gained — is how engineers decide whether an overlay is the right architecture for a given problem.
