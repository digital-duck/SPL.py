### http (15.8s)

## Http

**HyperText Transfer Protocol (HTTP)** is the request-response protocol that powers communication on the web. When your browser loads a page, it sends an HTTP request to a server; the server processes it and returns an HTTP response. Every interaction — fetching HTML, submitting a form, calling an API — follows this same pattern.

An HTTP message has two parts: **headers** (metadata about the message) and an optional **body** (the actual content). Requests include a method that signals intent:

| Method | Purpose |
|--------|---------|
| `GET` | Retrieve a resource |
| `POST` | Send data to create or process |
| `PUT` / `PATCH` | Update a resource |
| `DELETE` | Remove a resource |

Responses carry a **status code** that tells you what happened: `200 OK` (success), `404 Not Found` (resource missing), `500 Internal Server Error` (server crashed), and so on.

**Worked example.** Suppose you want to fetch JSON data from a public API using Python:

```python
import requests

response = requests.get(
    "https://jsonplaceholder.typicode.com/posts/1",
    headers={"Accept": "application/json"}
)

print(response.status_code)   # 200
print(response.json())        # {'userId': 1, 'id': 1, 'title': '...', ...}
```

The `requests.get` call assembles a GET request with an `Accept` header telling the server you want JSON back. The server's response object exposes the status code and parsed body separately, which mirrors the two-part structure of HTTP itself.

**Problem-solving application.** Most real bugs in web work come from ignoring what the response actually says. A disciplined pattern: always check the status code before touching the body, and read headers when something unexpected happens.

```python
def fetch_post(post_id: int) -> dict:
    url = f"https://jsonplaceholder.typicode.com/posts/{post_id}"
    response = requests.get(url, timeout=5)
    response.raise_for_status()   # raises HTTPError for 4xx/5xx
    return response.json()

try:
    data = fetch_post(9999)       # non-existent post → 404
except requests.HTTPError as e:
    print(f"Request failed: {e}")
```

`raise_for_status()` turns a silent bad response into a loud exception, which is almost always what you want: fail fast, with a message, rather than quietly processing an empty or error body as if it were valid data. Understanding HTTP's request-response contract — method, headers, status code, body — gives you a mental model that applies equally to browser debugging, API design, and backend service integration.

### url (33.6s)

## URL

A **Uniform Resource Locator (URL)** is a standardized address that identifies a resource on a network and specifies how to retrieve it. Every URL encodes three things at once: the protocol to use, the server to contact, and the path to the resource on that server. Understanding URL structure is essential for web development, API design, and debugging network requests.

A URL follows this general anatomy:

```
scheme://host:port/path?query#fragment
```

- **scheme** — the protocol (`https`, `http`, `ftp`, `mailto`)
- **host** — the domain name or IP address of the server
- **port** — optional; defaults to 80 for HTTP and 443 for HTTPS
- **path** — the hierarchical location of the resource on the server
- **query string** — key-value pairs after `?`, used to pass parameters
- **fragment** — after `#`, identifies a section within the page (handled by the browser, never sent to the server)

**Worked example.** Dissect this URL:

```
https://api.weather.io:443/v2/forecast?city=Austin&days=5#summary
```

| Part | Value |
|---|---|
| Scheme | `https` |
| Host | `api.weather.io` |
| Port | `443` (explicit, but default for HTTPS) |
| Path | `/v2/forecast` |
| Query | `city=Austin&days=5` |
| Fragment | `summary` |

The server receives everything up to but not including `#summary`; the fragment is purely client-side.

**Problem-solving application.** When building a Python script that calls a REST API, hardcoding query strings is fragile. Use `urllib.parse.urlencode` to construct the query safely:

```python
from urllib.parse import urlencode

base = "https://api.weather.io/v2/forecast"
params = {"city": "Austin", "days": 5}
url = base + "?" + urlencode(params)
print(url)
# https://api.weather.io/v2/forecast?city=Austin&days=5
```

This approach correctly percent-encodes special characters — a space in `"New York"` becomes `New+York`, preventing a malformed request. Hardcoding `?city=New York&days=5` directly into a string would produce an invalid URL that many servers reject. The same principle applies in reverse: when your code receives a URL and needs to read its parameters, resist the temptation to split on `?` or `&` manually, since query values can themselves contain encoded characters that make naive splitting unreliable. Treating a URL as a structured object rather than an opaque string is one of the most effective habits for avoiding subtle, hard-to-reproduce bugs in web applications.

## World Wide Web

The **World Wide Web** (WWW) is a system of interlinked hypertext documents and resources accessed via the Internet. It is not the Internet itself — the Internet is the underlying network of connected computers — but rather an application layer built on top of it. The Web operates through three core technologies: **URLs** (Uniform Resource Locators) that identify resources, **HTTP/HTTPS** (HyperText Transfer Protocol) that governs how clients and servers communicate, and **HTML** (HyperText Markup Language) that structures the content delivered to browsers.

When you type a URL into a browser, a precise sequence unfolds. The browser performs a **DNS lookup** to translate the human-readable domain name (e.g., `example.com`) into an IP address. It then opens a TCP connection to the server at that address and sends an HTTP request. The server responds with a status code and, if successful (200 OK), the requested resource — typically an HTML file. The browser parses the HTML, discovers additional resources (images, stylesheets, scripts), fetches those, and renders the complete page.

**Worked example.** Consider a student visiting `https://en.wikipedia.org/wiki/Python`. The browser contacts a DNS resolver and learns the server's IP. Because the URL uses HTTPS, it also performs a **TLS handshake** to establish an encrypted connection before any data is exchanged. It then sends:

```
GET /wiki/Python HTTP/1.1
Host: en.wikipedia.org
```

The server returns a 200 response whose body is the HTML for that page. Embedded `<img>` and `<link>` tags trigger additional GET requests for images and CSS. The browser assembles all pieces into the rendered page the student sees.

**Problem-solving application.** Suppose a developer's webpage loads slowly. Diagnosing it requires understanding the Web's layered model. Using browser developer tools (Network tab), they can inspect each HTTP request: which resources are largest, which take longest, and whether any return error codes (404 Not Found, 503 Service Unavailable). Fixes might include compressing images or serving assets from a CDN located geographically closer to users. Each intervention maps directly to a bottleneck in the request-response cycle — no fix is meaningful without understanding the underlying flow.

## Web Graph

A **web graph** is a directed graph in which each node represents a webpage and each directed edge represents a hyperlink from one page to another. If page A contains a link to page B, the graph includes a directed edge A → B. This structure captures the entire navigable topology of the web (or any subset of it) in a form that algorithms can analyze.

The web graph has two defining structural properties. First, it is **sparse**: most pages link to only a handful of others, so the number of edges is much smaller than the theoretical maximum of $n^2$ for $n$ nodes. Second, it exhibits a **power-law degree distribution**: a tiny fraction of pages (news sites, Wikipedia, major social platforms) attract an enormous number of inbound links, while the vast majority of pages receive almost none. This skew is captured by the observation that the fraction of nodes with in-degree $k$ scales roughly as $k^{-\alpha}$ for some exponent $\alpha \approx 2$–$3$.

**Worked example.** Suppose you are building a small crawler that visits five pages and records their links:

- `home.html` → `about.html`, `blog.html`
- `blog.html` → `post1.html`, `home.html`
- `about.html` → `home.html`
- `post1.html` → `blog.html`
- `post2.html` → `home.html`

Represent this as an adjacency list. The in-degree of `home.html` is 3 (from `blog`, `about`, and `post2`), making it the hub. `post2.html` has in-degree 0 — a dangling node that nothing links to, a common artifact in real crawls.

**Problem-solving application.** Web graphs are the foundation of link-analysis algorithms such as PageRank, which assigns each node an importance score based on how many high-quality pages point to it. In practice, you build the web graph incrementally during a crawl: start from a seed URL, fetch the page, parse all `<a href>` tags, add directed edges to your graph, and enqueue unvisited targets. Efficient implementations represent the graph as a compressed sparse row (CSR) matrix because storing $10^{12}$ edges as an explicit adjacency list is infeasible. Detecting **strongly connected components** (sets of pages mutually reachable from each other) within the web graph reveals the famous "bow-tie" structure of the web: a giant core, upstream nodes that feed into it, and downstream nodes that can only be reached from it.

## Bowtie Structure

When researchers at Altavista mapped the early web in 2000, they expected a tangled, uniform graph. What they found instead was something with a clear shape: a dense, tightly interconnected core flanked by two large wings, with smaller outlying clusters attached. They called it the **bowtie structure** — a pattern that has since appeared in biological networks, supply chains, citation graphs, and ecosystems.

The bowtie divides a directed graph into four named regions. The **strongly connected component (SCC)**, or "core," is the knot at the center: every node in it can reach every other node by following directed edges. The **IN** set contains nodes that can reach the core but cannot be reached from it — they feed into the center. The **OUT** set contains nodes reachable from the core that cannot send anything back — they receive from the center. Everything else falls into **tendrils** (nodes hanging off IN or OUT without passing through the core) or isolated components. Plot these four regions and the shape is unmistakable: two broad triangles meeting at a central knot, forming a bowtie.

**Worked example.** Consider six web pages: A → B → C ↔ D → E, with C → B closing a cycle, and F → C. The SCC is {B, C, D} because each can reach the others. Page A feeds into B without any back-path, so A is IN. Page E receives from D but has no outgoing links, so E is OUT. Page F points into C but is unreachable from the SCC (no path from D, B, or C leads to F), so F is a tendril hanging off the IN side.

**Problem-solving application.** Suppose a logistics company models its warehouse network as a directed graph where edges represent one-way truck routes. An analyst wants to know which warehouses are "mission-critical" — disrupting them would sever the most supply paths. The answer lies in the SCC: removing any core node can disconnect IN from OUT entirely, because all cross-network routing passes through the core. By contrast, removing an IN or OUT node only strains one wing. To find the SCC programmatically, run Kosaraju's or Tarjan's algorithm (both $O(V + E)$) on the adjacency list, then classify remaining nodes by reachability. Warehouses landing in the core are high-priority for redundancy; those in OUT are candidates for consolidation if utilization is low.
