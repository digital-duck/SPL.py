## Edge Coloring

**Definition.** An *edge coloring* of a graph $G$ assigns a color to each edge so that no two edges sharing a common endpoint receive the same color. The minimum number of colors needed to achieve this is called the *chromatic index*, denoted $\chi'(G)$. Every vertex can be thought of as a "conflict zone": all edges meeting there must be distinctly colored, so $\chi'(G) \geq \Delta(G)$, where $\Delta(G)$ is the maximum degree (the largest number of edges at any single vertex).

A fundamental result narrows how much higher $\chi'(G)$ can go:

**Vizing's Theorem.** For any simple graph $G$, $\Delta(G) \leq \chi'(G) \leq \Delta(G)+1$.

This theorem is genuinely surprising: no matter how complicated the graph, you never need more than one extra color beyond the obvious lower bound. Graphs achieving $\chi'(G) = \Delta(G)$ are called *Class 1*; those needing the extra color are *Class 2*.

**Worked example.** Consider the cycle $C_5$ (five vertices in a pentagon). Every vertex has degree 2, so $\Delta = 2$. Vizing's theorem says $\chi'(C_5)$ is 2 or 3. Try using 2 colors: label edges $e_1, e_2, e_3, e_4, e_5$ around the cycle. Alternating red and blue works fine on an even cycle, but with five edges the pattern must wrap around—the last edge conflicts with the first. Three colors suffice (color $e_5$ with a third color), confirming $C_5$ is Class 2. Even cycles $C_{2k}$ are always Class 1.

**Problem-solving application.** Edge coloring models any scheduling problem where shared resources create conflicts. Suppose a school must assign time slots to exams, and two exams conflict whenever they share a student. Model students as vertices and exams as edges; an edge coloring gives a valid schedule using $\chi'(G)$ time slots—no student sits two exams at once. To find a practical coloring, use a greedy algorithm: process edges in any order and assign the lowest-numbered color not already used by an adjacent edge. This greedy approach may use up to $2\Delta - 1$ colors in the worst case, but for dense, regular graphs it often achieves close to the Vizing bound. When exact minimality matters—say, minimizing the number of rounds in a tournament bracket—exact solvers or specialized algorithms for bipartite graphs (which are always Class 1) are the right tool.

## Edge Chromatic Number

The **edge chromatic number** of a graph $G$, written $\chi'(G)$, is the minimum number of colors needed to color every edge of $G$ so that no two edges sharing a vertex receive the same color. This is distinct from vertex coloring: here the constraint is on edges meeting at a common endpoint, not on adjacent vertices.

A key theoretical anchor is **Vizing's Theorem**: for any simple graph $G$ with maximum degree $\Delta(G)$, the edge chromatic number satisfies

$$\Delta(G) \leq \chi'(G) \leq \Delta(G) + 1.$$

This means every graph falls into exactly one of two classes. **Class 1** graphs achieve $\chi'(G) = \Delta(G)$; **Class 2** graphs require one extra color. Complete graphs $K_n$ with $n$ even are Class 1; complete graphs with $n$ odd are Class 2.

**Worked example.** Consider $K_4$, the complete graph on four vertices. Each vertex has degree 3, so $\Delta(K_4) = 3$. Vizing's theorem says $\chi'(K_4) \in \{3, 4\}$. Label the vertices $1, 2, 3, 4$. Assign colors as follows:

- Color 1: edges $\{1,2\}$ and $\{3,4\}$
- Color 2: edges $\{1,3\}$ and $\{2,4\}$
- Color 3: edges $\{1,4\}$ and $\{2,3\}$

Every vertex touches exactly one edge of each color, and no two edges at the same vertex share a color. Three colors suffice, confirming $\chi'(K_4) = 3$, so $K_4$ is Class 1.

**Problem-solving application.** Edge coloring models scheduling problems where shared resources create conflicts. Suppose five teams must each play every other team once in a tournament. The schedule forms $K_5$; each vertex has degree 4, so $\Delta = 4$. Since $K_5$ has an odd number of vertices, it is Class 2, giving $\chi'(K_5) = 5$. This tells you immediately that **at least five rounds are required** — no clever bracket can compress it to four. Each color class is a set of games that can be played simultaneously (no team appears twice), which is exactly one round. The edge chromatic number thus gives a provable lower bound on the tournament length before you ever try to build the schedule.

## Storage Load Balancing

**Definition.** Storage load balancing is the process of distributing read and write requests across multiple storage nodes so that no single node becomes a bottleneck. In a distributed system — a database cluster, a cloud object store, or a file server array — workloads are rarely uniform. Without balancing, some nodes saturate while others sit idle, degrading overall throughput and increasing latency. The goal is to spread demand evenly enough that the system's aggregate capacity is the effective limit, not the capacity of its hottest node.

The two primary strategies are **static partitioning** and **dynamic rebalancing**. Static partitioning assigns data to nodes up front, often using consistent hashing: a hash function maps each data key to a position on a virtual ring, and nodes own arcs of that ring. Dynamic rebalancing monitors load in real time and migrates data or reroutes requests when imbalance exceeds a threshold.

**Worked example.** Suppose you have four storage nodes and a consistent hash ring divided into 360 virtual slots. Each node owns 90 slots. A key like `"user_profile_42"` is hashed to slot 217, so it lands on the node owning slots 181–270. If that node starts receiving 60% of all requests — because popular keys cluster in its range — the balancer can insert *virtual nodes*: give the overloaded node only 45 slots and redistribute the remaining 45 to the underloaded nodes. The clients never change their hash function; the ring topology changes instead.

**Problem-solving application.** Consider a photo-sharing service where Monday morning brings a surge in uploads. A naive round-robin balancer distributes writes evenly at intake, but read traffic skews heavily toward the 1,000 most-viewed photos, which happen to live on two nodes. Throughput tanks on those two while six others are nearly idle.

The fix is a two-tier approach: keep consistent hashing for writes, but add a **read replica layer** where hot objects are cached on multiple nodes. A load monitor tracks request rates per key prefix; when any prefix exceeds a threshold (say, 500 requests/second), the orchestrator provisions an additional replica and updates the routing table. Reads are then fanned out across all replicas for that prefix.

```python
def route_read(key, replica_map, default_node):
    prefix = key.split("_")[0]
    nodes = replica_map.get(prefix, [default_node])
    return min(nodes, key=lambda n: n.current_load())
```

This pattern — static hashing for placement, dynamic replication for hot spots — is the backbone of systems like Amazon S3 and Apache Cassandra's token-aware routing.
