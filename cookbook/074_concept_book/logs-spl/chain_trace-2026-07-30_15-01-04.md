## Big Data

**Definition.** A dataset is said to exhibit *big data* characteristics when its volume, velocity, or variety (the "three Vs") exceed the processing capacity of conventional single-machine systems. More precisely, let $N$ denote the number of records, $d$ the number of features per record, and $\tau$ the arrival rate (records per second). A dataset is operationally classified as big data when any one of the following conditions holds:

$$N \cdot d > M_{\text{RAM}}, \qquad \tau > \lambda_{\text{disk}}, \qquad \text{or} \quad \dim(\mathcal{S}) \text{ is heterogeneous},$$

where $M_{\text{RAM}}$ is available memory, $\lambda_{\text{disk}}$ is sustainable write throughput, and $\mathcal{S}$ is the schema space. The hallmark challenge is that standard $O(N)$ or $O(N \log N)$ algorithms become infeasible when $N \sim 10^9$ or larger, forcing a shift to distributed or streaming paradigms.

**Worked Example.** Suppose a retailer logs $N = 10^9$ transactions, each described by $d = 50$ floating-point features stored as 64-bit doubles. The raw storage requirement is

$$S = N \cdot d \cdot 8 \text{ bytes} = 10^9 \times 50 \times 8 = 4 \times 10^{11} \text{ bytes} = 400 \text{ GB}.$$

A workstation with 32 GB of RAM cannot load this dataset into memory; a naive pandas `read_csv` call would raise a `MemoryError`. The solution is to partition the data into $k$ shards of size $\lceil N/k \rceil$ each, process each shard independently, and aggregate partial statistics. For the sample mean $\bar{x}$, the aggregation is exact:

$$\bar{x} = \frac{1}{N} \sum_{i=1}^{k} n_i \bar{x}_i, \qquad n_i = \left\lceil \frac{N}{k} \right\rceil.$$

**Key Theorem (Embarrassingly Parallel Reduction).** Let $f: \mathbb{R}^d \to \mathbb{R}$ be a *decomposable* statistic, meaning $f(\mathcal{D}) = g\!\left(f(\mathcal{D}_1), \ldots, f(\mathcal{D}_k)\right)$ for some aggregator $g$. Then the total computation time satisfies $T_k = T_1 / k + T_{\text{comm}}$, where $T_{\text{comm}}$ is network overhead. When $T_{\text{comm}} \ll T_1$, near-linear speedup is achieved. Sum, count, min, max, and histogram bin counts are all decomposable; median and exact quantiles are not.

**Lab Cell.**

```python
import sympy as sp

N, k, n_i = sp.symbols('N k n_i', positive=True)
x_bar_i   = sp.Symbol(r'\bar{x}_i')

# Symbolic mean aggregation formula
x_bar_global = sp.Rational(1, 1) * sp.Sum(n_i * x_bar_i, (sp.Symbol('i'), 1, k)) / N
sp.pprint(sp.Eq(sp.Symbol(r'\bar{x}'), x_bar_global))

# Concrete shard size example
shard_size = sp.ceiling(sp.Integer(10**9) / 32)
print(f"Records per shard (32 shards): {shard_size}")
```

## Cloud Computing

**Definition.** Cloud computing is the on-demand delivery of computing resources—processors, memory, storage, and software—over a network, typically the public internet, with usage billed in proportion to consumption. Rather than owning physical hardware, a consumer rents capacity from a provider who operates large-scale data centers. The three canonical service models are *Infrastructure as a Service* (IaaS), which exposes raw virtual machines; *Platform as a Service* (PaaS), which abstracts the operating system and runtime; and *Software as a Service* (SaaS), which delivers fully managed applications. Resource allocation is governed by an *elasticity* principle: capacity scales up or down automatically in response to workload, subject to provider limits and a cost function.

Formally, let $D(t)$ denote the computational demand at time $t$ (measured in CPU-core-seconds per unit time) and let $C(n)$ denote the hourly cost of provisioning $n$ virtual cores. For a provider offering linear pricing, $C(n) = c \cdot n$ for some rate constant $c > 0$. The total cost over an interval $[0, T]$ is

$$
\text{Cost} = c \int_{0}^{T} n(t)\, dt,
$$

where $n(t) = \lceil D(t) \rceil$ is the number of cores allocated at each instant, assuming the scheduler rounds demand up to the nearest integer.

**Worked example.** Suppose demand follows a sinusoidal pattern: $D(t) = 50 + 30\sin\!\bigl(\tfrac{2\pi t}{24}\bigr)$ cores over a 24-hour period, with $c = \$0.05$ per core-hour. The average demand is $\bar{D} = 50$ cores, so the expected daily cost is approximately $c \cdot \bar{D} \cdot T = 0.05 \times 50 \times 24 = \$60$. A fixed on-premises deployment sized for peak demand ($80$ cores) would cost $0.05 \times 80 \times 24 = \$96$, a 37.5 % premium.

**Key theorem (Cost–Elasticity Trade-off).** For any non-constant demand signal $D(t) \geq 0$ and linear pricing $C(n) = cn$, elastic provisioning satisfies

$$
\int_{0}^{T} C\!\bigl(\lceil D(t) \rceil\bigr)\, dt \;\leq\; C\!\bigl(\max_{t} D(t)\bigr) \cdot T,
$$

with equality only when $D(t)$ is constant. Elastic clouds therefore weakly dominate static provisioning in cost.

**Lab cell.**

```python
import sympy as sp

t, T, c = sp.symbols('t T c', positive=True)
D = 50 + 30 * sp.sin(2 * sp.pi * t / 24)

# Average demand over one day
avg_demand = sp.integrate(D, (t, 0, 24)) / 24
elastic_cost = c * avg_demand * 24
static_cost  = c * 80 * 24          # peak-sized fixed deployment

print("Elastic cost :", sp.simplify(elastic_cost))
print("Static cost  :", static_cost)
print("Savings ratio:", sp.simplify(1 - elastic_cost / static_cost))
```

Running this cell confirms the 37.5 % savings derived analytically and demonstrates how symbolic integration makes cost-model reasoning tractable before any real workload data is collected.
