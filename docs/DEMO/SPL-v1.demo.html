SPL — Structured Prompt Language

A declarative language for agentic AI workflows: SQL for LLMs.

Published as spl-llm 3.4.1 · Apache-2.0


wen.gong.research@gmail.com

PyPI package: spl-llm
SPL is a declarative language for agentic LLM workflows. SQL abstracts over databases, and SPL abstracts over language models in the same way. The Python runtime is published on PyPI as spl-llm, version 3.4.1, under Apache-2.0.

    The problem: glue code around every LLM call

    Most agentic frameworks need hundreds of lines of imperative Python to wire up prompts, manage context, handle errors and switch LLM providers.

    ConcernFramework approachSPL approach
    Provider switchRewrite adapter glue code--adapter ollama → --adapter momagrid
    Retry logicTry/except boilerplateRETRY / EXCEPTION WHEN
    Sub-agent callsAsync queue + callbacksCALL workflow_name() INTO @result
    Parallel agentsasyncio.gather + coordinationCALL PARALLEL ... END
    Token budgetsManual prompt trimmingOPTIMIZE ... WITHIN 2000 TOKENS
    This table comes from the README. Each row is a concern that frameworks handle in imperative code. SPL handles each one with a single declarative construct or a run-time flag.

    The idea: declare what, not how

    • The same .spl file runs on Ollama, Claude, OpenAI, Gemini or Momagrid without changing a line.
    • DODA: Design Once, Deploy Anywhere.
    • The .spl file is the logical specification. It is the same whatever the runtime, adapter or deployment.
    • Provider, parallelism and infrastructure are chosen at run time with --adapter and --model.

    Rule

    ✔ No provider-specific logic in .spl files
    ✔ Physical choices are made at execution time
    The central design pattern is DODA, Design Once, Deploy Anywhere. A workflow file never names a provider. Which provider, how much parallelism and which machines are all decided when you run it.

    Three paradigms in one language

    LayerInspirationSPL construct
    DataSQLSELECT, WITH, GENERATE
    LogicPythonCALL, @spl_tool, typed variables
    OrchestrationLinux shellWORKFLOW composition, IMPORT
    SPL combines three programming paradigms. The data layer borrows from SQL, the logic layer from Python with tools and typed variables, and the orchestration layer from shell-style composition and imports.

    A workflow in SPL: self_refine

    WORKFLOW self_refine
    INPUT:  @topic TEXT
    OUTPUT: @essay TEXT
DO
    GENERATE draft(@topic) INTO @essay
    CALL critique(@essay) INTO @feedback
    GENERATE refine(@essay, @feedback) INTO @essay
    COMMIT @essay
END
    spl3 run cookbook/005_self_refine/self_refine.spl \
  --llm ollama:gemma3 --param task="What is vibe coding?"
    This is the condensed self_refine workflow from the README. It declares its inputs and outputs, generates a draft, calls a critique, refines the draft and commits the result. One command runs it on a local Ollama model.

    Core language constructs

    Steps and units

    GENERATE ... INTO @var: one LLM call, result kept in a variable
    WORKFLOW / PROCEDURE: named units with INPUT: / OUTPUT:
    CALL name(...) INTO @var: run a sub-workflow
    CALL PARALLEL ... END: run branches at the same time
    IMPORT 'file.spl': resolved at parse time

    Control and exit

    EVALUATE @var WHEN ... END: the LLM judges the condition, not string equality
    WHILE condition DO ... END: refine in a loop
    EXCEPTION WHEN Type THEN ... END: typed recovery from errors
    COMMIT @var WITH STATUS = '...': a non-complete status raises WorkflowCompositionError in the caller
    These are the constructs the executor handles. Note that EVALUATE is semantic branching: the condition is judged by an LLM, not by string comparison. COMMIT with a status other than complete turns into an error in the calling workflow.

    Execution pipeline

    .spl source
  → Lexer      spl/lexer.py            chars → tokens
  → Parser     spl/parser.py + spl3/parser.py  → AST
  → Executor   spl/executor.py + spl3/executor.py
      → Adapter          spl3/adapters/
      → WorkflowComposer spl3/composer.py
                         CALL / CALL PARALLEL dispatch
    Source text becomes tokens, then an AST, then LLM calls. The executor sends generation to an adapter. Workflow composition, meaning CALL and CALL PARALLEL, goes through the WorkflowComposer.

    Two runtimes, one package

    • spl/ is the SPL 2.0 base: lexer, parser, executor, adapters, storage.
    • spl3/ extends it by inheritance: SPL3Executor(SPL2Executor), SPL3Parser(SPL2Parser).
    • v3 features never go into spl/. They are overrides in spl3/.
    • The spl3 CLI is permanent and always points to the highest available runtime layer.

    Later versions

    ✔ spl4/, spl5/ are planned as new subpackages next to spl/ and spl3/
    ✔ spl/cli.py stays for backward compatibility
    The 2.0 to 3.0 extension is clean inheritance, so both packages ship in the same wheel. New features are added by overriding in spl3, never by editing the base.

    Adapters and the dd-llm bridge

    • Four mandatory adapters: ollama, claude_cli, openrouter, momagrid.
    • The interface has two methods: generate(...) and generate_multimodal(...).
    • generate_multimodal is used when an INPUT is IMAGE, AUDIO or VIDEO.
    • All providers live in dd-llm and are reached through DDLLMBridge / MultiModalDDLLMBridge.
    • Only echo (a test double), liquid and snap are in this repo.
    AdapterStage
    ollamaLocal prototyping
    claude_cliBest-model validation
    openrouterBroad model coverage
    momagridProduction grid
    Together the four mandatory adapters cover the path from local prototyping to grid deployment. Any new runtime port must implement them before it counts as feature-complete. Provider behaviour is changed in dd-llm, not in this repo.

    Momagrid: CALL as a system call

    export MOMAGRID_HUB_URL=http://192.168.1.10:9000

# single recipe on the grid
spl3 run cookbook/005_self_refine/self_refine.spl \
  --llm momagrid:llama3.2

# whole cookbook, queue filled so every node gets work
python cookbook/run_all.py --adapter momagrid --workers 5
    • Each CALL becomes a Hub-dispatched system call, and CALL PARALLEL sends branches to different nodes.
    • The hub result is nested ({"state": "COMPLETE", "result": {...}}) and must not be flattened.
    Momagrid is a hub that dispatches inference across a LAN grid of GPU nodes. SPL 3.0 treats it as a compute OS, where workflow calls are system calls. The adapter relies on the hub's nested result shape.

    The verifier ladder: SOLVE and ASSERT

    RungVerifiesTrust badge
    NumPynumeric spot-check
    SymPy / SageMathan exact instancemachine_verified
    Lean 4 + mathliba statement, proof-checkedmachine_proved
    • No new SPL constructs: SOLVE/ASSERT are the same at every rung.
    • The backend is chosen at run time: spl3 run <file.spl> --kernel --kernel-name sagemath
    An instance check says that this particular eigenpair satisfies A v equals lambda v. A Lean proof covers the universally quantified statement. Both use the same two constructs, and only the backend behind them changes.

    Persistent kernel for deterministic Python

    • Before: run_python started a fresh subprocess on every call and lost all state.
    • Now: a persistent IPython kernel owned by the executor (spl3/kernel.py).
    • New capability comes from pip install + import, not from new stdlib tools.
    • CREATE TOOL_API bodies and run_python share one namespace.

    Boundaries

    ✔ The executor stays the source of truth for @variables
    ✔ GENERATE stays on the adapter path and never reaches the kernel
    ✔ The subprocess fallback is used when no kernel is present
    The design rule is that SPL owns orchestration, typed state and the IR, and the kernel owns Python execution. Prompts go to adapters and deterministic code goes to the kernel. The two never mix. The design note says the first slice is implemented.

    Text2SPL with Code-RAG

    cookbook/*.spl
  └─► spl3 describe    → *-spec.md   (Section 0 = description)
       └─► code-rag seed  → vector store
            └─► spl3 text2spl → nearest examples as few-shot
                 └─► new .spl workflow
    • No fine-tuning: SPL is a new language with no training data, so examples are retrieved when it compiles.
    • ChromaDB with all-MiniLM-L6-v2 embeddings, in .spl/code_rag/chroma.sqlite3.
    • The store is one SQLite file, so no server process is needed. Back it up by copying the directory.
    The cookbook is used to bootstrap generation. Each recipe gets a prose spec, the specs are indexed, and text2spl retrieves the nearest ones as few-shot context.

    Compile to other frameworks: splc

    spl3 splc compile <file.spl> --lang <target>

# show the LLM prompt without making a call
spl3 splc compile agent.spl --lang python/pocketflow --llm --prompt

    Framework targets

    go, ts, python
    python/langgraph, python/crewai, python/autogen
    python/pocketflow, python/liquid

    Textbook targets (python/<domain>)

    python/linalg, python/intro_geometry
    python/domain_textbook
    splc takes the logical .spl view and turns it into a physical target in another framework. The --prompt flag prints the system and user prompts and exits, so it costs nothing.

    Real example: concept-book

    YAML graph → learning navigator (HTML)
           → content generator (SPL) → verified lesson
    • Ten domain graphs are authored, including linear algebra, geometry, mechanics and music theory.
    • linalg_graph.yaml has 37 nodes and 51 edges.
    • The math is verified by SymPy / Sage / Lean, and the LLM writes the narrative.
    # scripts/concept_graph.py
python concept_graph.py \
  --domain linalg_graph.yaml \
  path spectral_theorem
python concept_graph.py \
  --domain linalg_graph.yaml \
  visualize --format html
    A concept-book takes its curriculum from a graph of concepts and their prerequisites. In a demo session, the Gram-Schmidt learning path was traced in 11 steps and the HTML output was checked in a browser.

    Demo: one workflow, two backends

    # 1. local models
spl3 run cookbook/005_self_refine/self_refine.spl --adapter ollama \
  --param task="Explain vibe coding" \
  --param writer_model="gemma3" --param critic_model="llama3.2"

# 2. the same file on the grid
spl3 run cookbook/005_self_refine/self_refine.spl --llm momagrid:llama3.2

# 3. execution plan, dry run, no LLM
spl3 util explain cookbook/005_self_refine/self_refine.spl
    Demo Run step 1, then step 2 without editing the file, then step 3 to show the plan.
    The point of the demo is that the .spl file does not change between steps 1 and 2. Only the flag changes. Step 3 shows the execution plan without making any LLM call.
