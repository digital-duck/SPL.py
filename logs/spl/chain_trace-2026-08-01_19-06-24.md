## Big Data

You already know data means information — names, temperatures, prices, likes. But at some point, the *amount* of data itself becomes the problem. That shift is what "Big Data" is really about.

**What makes data "big"?** Engineers use the **3 Vs** as a framework:

- **Volume** — the sheer size. A single social media platform processes over $10^{18}$ bytes (one exabyte) per day. A regular laptop holds about $10^{12}$ bytes (one terabyte) — so we are talking roughly a million laptops' worth.
- **Velocity** — how fast new data arrives. Stock prices update thousands of times per second; a self-driving car's sensors stream gigabytes every minute.
- **Variety** — data comes in messy forms: structured tables, free-text reviews, images, audio clips, GPS coordinates.

The core challenge is that traditional tools (a single spreadsheet, one database on one machine) break under these conditions. Solutions involve **distributing** the work across many computers at once.

A useful rule of thumb: if processing time scales as $O(n)$ on one machine, splitting across $k$ machines can bring it toward $O(n/k)$ — not perfectly, because coordinating the machines adds its own overhead, but roughly.

**Why it matters to you:** Nearly every recommendation system, weather forecast, and medical diagnosis tool you encounter is powered by large-scale data pipelines.

## Cloud Computing

You've probably heard that photos, music, and documents can be "stored in the cloud." But the cloud isn't a magical floating place — it's a network of real computers, housed in large buildings called **data centers**, that you access over the internet. Instead of running a program on *your* laptop, you send a request across a network, a powerful server somewhere does the work, and sends back the result. Your device is mostly just a window.

**The structure underneath.** Cloud computing is built on three stacked ideas. At the bottom is raw hardware — processors, memory, and storage. Above that sits a **virtual machine** layer: software that pretends to be a separate computer, so one physical machine can run dozens of isolated "guest" computers simultaneously. On top of that live **services** — databases, file storage, machine-learning platforms — that developers rent by the hour instead of buying outright. This layering is often called the *IaaS → PaaS → SaaS* stack (Infrastructure, Platform, Software as a Service).

A key concept is **elasticity**: a cloud provider can allocate more servers to your application when traffic spikes, then release them when demand drops. If $n$ is the number of users at any moment, the cloud tries to keep cost proportional to $n$ rather than sized for the worst-case peak. Formally, cost scales as $O(n)$ instead of $O(n_{\max})$.

**Simple pattern to remember:** cloud = shared hardware + virtualization + pay-as-you-go pricing.
